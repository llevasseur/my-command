description: Turn claude-proxy session suggestions into implemented, evidence-backed workflow improvements — judge every unjudged bucket against its transcripts first, compose criteria from confirmed findings only, escalate suggestions whose previous fix did not hold, dispatch defective rules back at claude-proxy, build named accepted ideas on request with one pull request each, and mark only shipped work done.

# Improve Agent Workflows

Parse `--range <spec>`, `--regressed`, `--idea <slug>[,<slug>...]`, `--ideas`, `--dry-run`, task workspace flags, and optional scope. Read `CLAUDE_PROXY_STORE`; its parent log directory and repository define the suggestions CLI. Stop rather than guessing when the variable or checkout is unavailable.

A rule firing is not the same as something having gone wrong, so nothing here is composed from unjudged rule output. Criteria come from **confirmed** suggestions only, and step 2 is what makes them confirmed.

There are two inputs with two evidence standards. A suggestion is counted from transcripts. An accepted **idea** is invented by the ideation workflow and made actionable by a recorded human sign-off. **The idea track is opt-in and its default is off**: `--idea` names the accepted slugs to build, the bare `--ideas` takes every accepted idea for the repository, and with neither flag no ledger is read and no idea becomes a criterion. Both flags govern the idea track alone — the suggestion track runs unchanged whether or not either is given.

1. List pending suggestions for the selected buckets as structured data. Keep each row's recurrence state and its resolved claim, which names the bucket, date, and note of the fix already applied to that rule. Group duplicates by underlying rule while retaining evidence and source sessions.
2. Identify the **dirty** buckets in the range — complete and unjudged — and judge them with `$judge` before composing any criteria, then re-read the suggestions so they carry their verdicts. If none are dirty, every bucket already has verdicts and this step is done. Two hard limits. **A failed judge run stops the command**: an errored call, a bucket recording fewer verdicts than it had fired suggestions, or a judge run that could not finish means stopping and bringing the user in — never fall back to composing criteria from unjudged output, because the dirty flag is the record that nobody has checked and a silent fallback makes a failed judge run indistinguishable from a clean bill of health. **And cap it at five buckets**: more than five dirty buckets in the range means stopping and telling the user to narrow the range or run an explicit amnesty backfill, since the default range is every bucket and an uncapped first run reads megabytes of transcript before composing a single criterion. A dry run does not skip this step — judging records verdicts about transcripts rather than claims that a fix shipped, and criteria are only worth reporting if they came from confirmed findings.
3. Compose from confirmed rows only. **A dismissed row is excluded entirely** — not as a weaker criterion and not as a note on another one, because a dismissal is a verdict that the finding was never true. Where a confirmed row carries a judge enrichment note, **that note is the criterion's reason**: it was written from the transcripts by an agent that read the nodes the rule pointed at, which makes it better evidence than the rule's generated detail string. Where such a note says there was nothing to add beyond that detail, use the detail.
4. Split the remaining rows by recurrence. A regressed row means a dated fix already shipped for that rule and later sessions tripped it anyway; it forms a separate criteria block that leads the brief. Status alone cannot make this split, because a regressed row is still pending. A mixed row spans the fix date and proves nothing, so it stays an ordinary finding. `--regressed` narrows the run to the regression block alone.
5. For every regressed row, read the prior fix named in its resolved note, including when that note points at another repository. Record the files it changed and what it changed, then classify its mechanism on this ladder: prose rule in a repository instruction file; step written into the workflow that needs it; mechanical gate such as a hook, script, verification check, or changed default; removal of the affordance itself. Require the new fix to climb at least one rung, and forbid restating the previous rule at the same rung. A regressed row whose prior fix cannot be recovered has nothing to differ from, so treat it as an ordinary finding. A dismissed row never enters this track: regressed means a dated fix did not hold, dismissed means there was never anything to fix, and escalating a rung against a finding that was never true builds a gate to prevent something that did not happen.
6. Recheck every suggestion against current source and repository history. Drop obsolete or already-fixed findings and never invent improvements not supported by evidence.
7. Compose the remaining set into precise task criteria, naming the repository each change lands in. Dry run reports buckets, evidence, prior fixes with their rungs, and criteria without editing or marking. It also reports the ideas it would act on and the ledger tier it read them from, or that it read none because no idea flag was given, and an unresolved named slug stops a dry run exactly as it stops a real one.

   Ask the tooling which rules it reports as **defective** — a rule that keeps firing on things the transcripts do not support is a defect in claude-proxy's own rule code, not noise to dismiss bucket after bucket forever. Dispatch each one as an ordinary criterion against the claude-proxy checkout's suggestions rule module, naming the buckets it was dismissed in and the dismissal reasons themselves as evidence: those reasons say what the rule counted versus what was happening, and that gap is the specification for the fix. Ask for the match to narrow so the dismissed cases stop firing without silencing the confirmed ones in the same buckets. This needs no new dispatch machinery, since the dispatch step already runs one subagent per repository on the suggestion track and claude-proxy is one of those repositories. A suggestion whose fix belongs to claude-proxy's dashboard or recurrence model rather than its rule code still stays pending and is reported as out of scope.

8. Run this step only when `--idea` or `--ideas` was given; otherwise read no ledger at all and carry one line to the report saying no ideas were read and which flags read them. Do not read the ledger merely to report a count, because a run that reads it ends up acting on what it found. When a flag was given, list the ideas **available to build** for this repository, identifying the repository by its git remote slug rather than a checkout path, because the ideas store is device-wide. Ask the ledger for its available set rather than for accepted ideas alone: available means accepted plus the ideas whose claim has expired, which is exactly the set a run may take. Accepted alone can never recover an idea a run picked up and then died holding, since that entry now reads claimed and no sweeper will restore it, while accepted-plus-claimed hands you one out from under a run still building it. **This does not loosen the sign-off rule**: claimed is reachable only from accepted, so every available row was signed off, and a later reader must not narrow the query back. Resolve the store through the same waterfall the ideation workflow writes to, reading every tier that exists: the log directory's ideas store through its CLI, then the repository's own committed ideas document, then the device-local ledger for that repository slug. An absent CLI means that tier is absent and the run falls through saying so; a tier that exists and fails to read is a stop. **Nothing outside that set is ever read** — proposed is invention nobody signed off on, rejected is invention turned down, shipped is already done, and a live claim belongs to another run — and naming a slug selects from the available set rather than admitting anything into it. The bucket range never applies to ideas, so a narrowed range narrows suggestions alone.

   **The listing has no slug filter, so select in this workflow against what it returned.** The bare flag takes every returned row; the named flag matches each given slug exactly, where a near-miss is a miss. **A named slug that does not resolve stops the run and is never skipped silently.** Report an unknown slug with the tiers searched and the available slugs that do exist, and report a slug found in another status with the status it actually holds, since proposed, rejected, and shipped each mean something different and only one is fixable here. A slug held by a live claim is the one exception and is a skip rather than a stop, reported with its holder and since-when: nothing is wrong, the claim expires or is released, and the answer is to wait rather than to fix anything. Stop on the first unresolved slug, before dispatching anything: a silent skip turns a request to build three ideas into a run that quietly builds two, and the missing one is indistinguishable from one nobody asked for.

   Compose each selected idea as its own criterion, labelled idea-sourced, stating the sign-off as its evidence: the slug, its rationale, and the evidence the idea itself cited with paths, because the subagent cannot read the ledger. An idea is a proposal and not a specification — pass a named mechanism through, and where none is named say what is undetermined rather than inventing a design the sign-off does not cover. **One idea is one criterion group.** Never merge two ideas because they share a repository or a file, and never add an idea to that repository's suggestion criteria.

9. **Claim each idea in the ledger before dispatching it**, never at pull-request time — the claim exists because two runs once built one idea eleven minutes apart, both reading it as free right up until the first pull request appeared, and one was closed unmerged. Decide the branch name this dispatch will cut, in the task workflow's own type-and-summary shape derived from the slug, and claim under that branch as the holder. **The branch name is the holder for a reason**: it is the one string a second run can check for itself against the remote branch list, telling a claim backed by real work from one left by a run that vanished, where a run identifier or a person's name would tell it nothing. Put that branch in the brief so the subagent cuts exactly it. **A refused claim means another run holds the idea**: skip it, name the holder and since-when in the report, and never build it anyway or retry under a different holder string, which would hide the collision rather than resolve it. Only an accepted idea — or one whose claim is stale or already yours — can be claimed at all, so claiming can never route around a human sign-off. A dry run claims nothing, because a claim is a write; it reports what it would have claimed. Once a dispatch returns a pull request, re-claim the same slug under the same branch with that pull request attached: claiming is idempotent for the same holder, and a claim carrying a pull request never expires, which matters because the expiry is sized to writing the change while the long part of an idea's life is review.

   Then dispatch the two tracks on different units. For suggestions, group criteria by target repository and invoke `$task` once per repository with that repository's criteria. For ideas, invoke `$task` once per idea with that single criterion — one idea, one branch, one pull request — never batched with another idea and never merged into a repository's suggestion brief. A repository appearing in both tracks therefore receives one suggestion invocation and one invocation per idea landing in it, which is the intended shape rather than duplication. Give every invocation its explicit checkout path as the working directory and the forwarded workspace flags. **Run every invocation one at a time and read each result before starting the next**, across both tracks: they open separate pull requests, but a later one's criteria may reference what an earlier one did, and two task runs racing in one checkout is what this rule has always prevented. Run the suggestion track first, because an idea building on a suggestion fix that just landed is likelier than the reverse. Most runs target one repository; the ladder makes more than one possible, because the rung that answers a regression often lives in a different checkout than the rule that failed.
10. From each task result and pull request, map only actually shipped criteria back to suggestion IDs. Mark those `done`; leave dropped, deferred, or failed items pending. Never mark a dismissed suggestion at all — done would claim a fix that does not exist, and a deliberate skip would record a real finding deferred. A criterion whose fix spanned repositories is marked only after every one of them has landed. For a suggestion that had regressed, the note records the attempt number, the rungs climbed from and to, the new pull request, and the prior one it supersedes, because the stored claim keeps only the most recent fix.
11. Mark each shipped idea in the ideas store, never the suggestion store, one call per idea, **with that idea's own pull request as the note**. Each idea was dispatched alone, so there is no shared run-wide URL to write, and a slug pointing at a pull request that built something else is a false record that reads as a true one and that no later run can detect. An idea whose pull request did not land stays accepted and returns next time, and because the pull requests are separate, one idea failing marks nothing against the others. A run given no idea flag marks nothing in the ideas store. Never move an idea back to proposed or rejected: this workflow implements advice and does not overturn a human's sign-off. Marking shipped keeps the claim, deliberately — it becomes the record of which branch built the thing, beside the pull request in the note — and shipped still means the work landed, which is what it went back to meaning once the claim took over saying that somebody is building it.
12. Report implemented, already satisfied, deferred, and still-pending suggestions, which buckets were judged with how many confirmed versus dismissed, any defective rule dispatched, how many were regressed, whether the idea track ran at all and under which flag, how many ideas were selected and from which ledger tier, the pull request for each repository on the suggestion track and for each idea on the idea track listed separately, and which ideas were marked shipped against which pull request. Say what happened to each claim as well: which slugs this run claimed and under which branch, which it skipped because another run held them with the holder and since-when, and which it released on the way out — a skipped idea and an idea nobody selected look identical in a report that counts only what shipped, and the first one is coming back on the next run.

## Closing turn

**Release every claim this run still holds, in the same turn as its last piece of real work.** An idea this run claimed and did not ship is marked back to accepted explicitly, rather than left to expire: every mark other than shipped drops the claim, which is what makes that the release. It belongs here because every ending routes here — the run that gives up, is refused, hits a failing gate, or is abandoned as wrong is in each case a run holding an idea it will not build, and hooking the release to the closing turn is what makes it happen on the exits nobody plans for. Without it the idea reads as taken for the full six-hour expiry and every run in that window skips it, blocked by a holder that went away rather than by any real work. Release only what did not ship: an idea that landed already carries its pull request and was marked shipped, and releasing it would discard the record of who built it, while a run that opened a pull request but stopped before marking should leave the claim alone, since a claim carrying a pull request does not expire and shows the next run that the work exists.

Close the run in a text-only turn: one final message carrying text and zero tool
calls, sent after the last tool call returns rather than alongside it. A run's
outcome is recorded only from a message with no tool call in it, so ending on one
— or bundling the report into one — records no outcome at all. Every ending owes
that turn, including one that stops early, is blocked or refused, or hands work
back to an invoking workflow.

Anchor that turn before the first tool call: put "close the run in a text-only
turn" in the todo list as its own final item, because the todo list is live
session state that a compaction carries forward and this prompt is not. Resolve it in the same tool-call turn as the run's last piece of real work,
so the list is already clean when that turn returns and the only thing left
to do is speak. Never leave marking it as a call of its own after the work
ends: a run whose last scheduled action is a bookkeeping tool call ends on
that call — the mark lands every time, and the message meant to follow it
never arrives. A
compaction boundary is a checkpoint, not an ending — a recap prompt, a
background-task notification, or a session-continuation preamble each mean the
run is still owed its turn, so answer in text alone, say where the run stands,
and restore the todo item if it did not survive. Each side of a boundary
records its own standing, because a run split across two transcripts is two
runs to the record. Every message from the
user opens a task in the same transcript, and only a reply carrying text
and no tool call closes it, so answer a mid-run question, correction, or
recap in text before returning to tool calls. A reply to another session is
not that turn either: SendMessage is a tool call, so send the reply, let it
return, then close in text alone.
