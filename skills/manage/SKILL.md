# Orchestrate a Multi-Part Goal

Parse `--delegate task|god|fb|work|work:god`, `--parallel <n>`, `--sequential`, `--dry-run`, `--mesh`, a merge target for the units that merge, every flag forwarded to the delegated task workflow — working in place, a base branch, a draft pull request, a subagent clean-and-pull-request stage, and added-command entries — and the goal text.

Take one multi-part goal, decompose it into units of work, and hand each unit to an **existing** workflow running in its own subagent — in parallel where the units are independent, in sequence where they are not.

This workflow owns planning, routing, dependency ordering, batching, failure handling, and the final synthesis. It owns **none** of the implementation. `$task` already owns branch → worktree → implement → verify → clean → pull request → teardown, and `$god` adds the merge last mile. So this workflow **never branches, commits, opens a pull request, merges, or tears down a worktree itself**: doing any of it here means two owners for one branch, and the delegate is the one holding the worktree. **The unit of delegation is one invocation of one existing workflow, and nothing smaller** — never "have a subagent edit these three files".

## Flags

- `--delegate <workflow>` — `task` (default), `god`, `fb`, `work`, or `work:god`. **`task` is the default because it stops at an open pull request and leaves a human the merge.** This workflow multiplies whatever it delegates, so eight unattended merges out of one invocation is a different risk from one, and `--delegate god` must be typed rather than inherited. **`fb` is the one delegate that cannot cut a branch**: the feedback workflow applies to the branch it is already on, or to a branch that **already exists** when one is named as its target. So an `fb` unit's branch comes from the goal rather than the plan, and is passed as that workflow's target — handing it a branch name this run invented gets either a branch that does not exist or the orchestrator's own branch, which is the collision the batching exists to prevent. A goal that cannot name an existing branch for an `fb` unit is a stop, not a new branch. **`work` cuts no branch either, for the opposite reason: it cuts many.** The ideas workflow claims each accepted idea under the branch name it is about to cut and then dispatches its own downstream run per idea, so branch naming lives *inside* the unit. A `work` unit is therefore planned around **one area** rather than one branch, and its file scope is not knowable when the plan is printed. **`work:god` puts every one of those downstream runs in the merging mode** — the ideas workflow's own merging delegate — so one invocation can merge areas × ideas without a human; like `god` it must be typed and is never inherited.
- `--parallel <n>` — units in flight at once. Default three, hard cap eight; a larger value is clamped and the clamp is reported.
- `--sequential` — dispatch one unit at a time regardless of independence.
- `--dry-run` — print the routing plan and spawn nothing: no task list, no subagent, no branch. The plan prints each unit's full invocation, its branch, the base it is cut from and the merge target it lands in, the forwarded flags it carries, and the ones dropped for it.
- `--mesh` — opt into peer-to-peer messaging between workers. Off by default.
- `--into <branch>` — the **merge target** each merging unit's pull request is merged into, forwarded verbatim to every `god` unit. It is owned here rather than inherited from the task workflow, which **does not document it**: that workflow stops at an open pull request and merges nothing, so it has no merge target to name. A merge target given alongside any other delegate is dropped and reported per unit like any flag the resolved delegate cannot parse, and that drop reads as a sign the merging delegate was meant. Given none, a merging unit names no target and falls back to the default branch, exactly as before the flag existed.
- **Every flag the delegated task workflow accepts and this one does not own is forwarded to each `task`, `god`, and `work` unit** — working in place, a base branch, a draft pull request, a subagent clean-and-pull-request stage, and added-command entries. Read the task workflow's own flag list rather than restating it here; nothing here interprets a forwarded flag beyond the three rules below.
- Anything not a recognized flag is part of the goal.

### The `work on` form

**A goal of the shape `work on <area 1>[, <area 2>, ...]` selects the `work` delegate and takes the comma-separated list as the areas** — one unit per area, one ideas-workflow invocation scoped to that area each, dispatched in the ordinary waves. Naming the delegate outright with a goal that names areas means the same thing; typed together they do not conflict.

- **The area is the unit and the lane.** Each idea on the ledger is filed under exactly one area, so two units selecting different areas select disjoint ideas. Never compose a per-idea selector here — picking ideas is the ideas workflow's job and doing it in the plan splits one selection across two owners.
- **A `work` unit's file scope is undetermined at plan time**, so the batching cannot prove two areas disjoint. Every idea still lands in its own worktree through the task workflow, so the failure mode is two pull requests to reconcile rather than one corrupted branch — say so in the plan, and use one-at-a-time dispatch when two areas are adjacent enough to matter.
- **The in-flight cap bounds units, not ideas per unit**, and the ideas workflow's own cap does not apply to an area-selected run. A run over five areas can therefore have many more runs alive than the cap names.
- **An area that does not exist is the ideas workflow's stop**, not this one's, and comes back as one failed unit like any other.

### Forwarded flags

A forwarded flag is typed once, on this invocation, and lands in each unit's own run rather than this one. That is what separates it from a constraint written into the goal: the goal is prose a planner can honour loosely, while a forwarded flag is composed into the unit's invocation at dispatch and printed in the plan first. **So a behaviour the task workflow already has a flag for is asked for with that flag, never described in the goal.**

**A delegate is never handed a flag it does not accept.** Compare the forwarded set against the resolved delegate's own documented flags, and for one it does not document: **drop it from that unit's invocation and report the drop in the plan**, per unit and per flag, naming the delegate that cannot parse it. **Never pass it anyway** — a delegate does not error on an unknown flag, it reads it as criteria, so a draft flag becomes a word in the request. And **never re-express it in the criteria**, which reintroduces the prose constraint the flag replaced and hides it inside text that reads like scope.

- The **task** workflow takes the whole set **except a merge target**, which it does not document, because it stops at an open pull request and merges nothing. One given with this delegate is dropped and reported per unit like any other.
- The **god** workflow takes working-in-place, a base branch, a **merge target**, and added-command entries; it adds the subagent stage itself, so forwarding that one is redundant rather than dropped. **A draft pull request under `--delegate god` is a stop before planning**, not a per-unit drop: that workflow rejects a draft because a draft cannot merge, so dispatching it would be one stop per unit. Say to delegate to the task workflow instead.
- The **ideas** workflow — `work` and `work:god` — takes working-in-place, a base branch, a draft pull request, and added-command entries, which it documents as its own pass-through set, plus the area the plan fills from the goal. The subagent stage is dropped, since it dispatches its own subagent per idea. A **merge target** is dropped for a plain `work` unit and **kept for `work:god`**, whose downstream runs merge. **A draft pull request under `work:god` is a stop before planning**, exactly as under `god` — it would become one stop per idea — and the answer is a plain `work` unit.
- The **feedback** workflow takes a target branch alone, which the plan already fills from the goal, so **no forwarded flag survives an `fb` unit** — each is dropped and listed as dropped. It cuts no branch and hands its own work-in-place to the task workflow internally, so the flags that would matter are already settled by what it is.

**A base branch given here sets the root of the branch plan, and only the root.** It replaces the default branch that unit branches are otherwise named against, and it reaches the units at the root of the dependency graph — those waiting on nothing. **A stacked unit keeps the base the batching gave it: the branch of the unit it depends on, never the default branch and never this root base.** Cutting a stacked unit from the root instead leaves it without the interface it consumes and buys a conflict at merge time. So a root base moves where the plan starts and never collapses the per-unit bases; the plan prints every unit's base so a root one and an inherited one are told apart before anything spawns. **That inheritance is for the delegates that do not merge. Under the merging delegate a stacked unit is cut from the run's merge target instead**, because that workflow merges each unit's pull request and then deletes its remote branch — and waves run in order, so the branch a stacked unit would inherit is already deleted **before that unit is dispatched**, not merely before it merges. Cutting from it would name a branch that no longer exists, and nothing is lost by cutting from the merge target: the dependency's pull request merged into it, so the interface the stacked unit consumes is already there, which is the only thing the inheritance was ever for.

**A merge target is uniform across every unit, and is never inherited down a stack.** A base branch and a merge target look like a pair and behave nothing alike: **every merging unit carries the same merge target, the one given on this invocation, whether it waits on nothing or is stacked three deep.** A stacked unit does **not** merge into the branch it was cut from. Three reasons, the third deciding it. The merge workflow defines the two as independent — the base is the cut point, the merge target is where the work lands, and it never inherits one from the other; inheriting here because the base inherits would re-couple exactly what that separation exists to keep apart. A base inherits for a reason that is only about the cut point: a stacked unit must be **cut** from the branch carrying the interface it consumes or it cannot build against it, and nothing equivalent holds for the merge target, since that unit already holds its dependency's commits by having been cut from them. And under the merging delegate — the only one that accepts a merge target — the branch a stacked unit would inherit is already gone: waves run in order, the merge workflow merges each unit's pull request and then deletes its remote branch, so by the time a stacked unit reaches its own merge step the unit it depends on has merged and its branch has been deleted. An inherited merge target would name a branch that no longer exists; the run's single merge target is the only branch guaranteed to still be there. The reader-facing consequence is what the plan prints: **cut points fan out down the stack while merge targets all read the same**, and two units showing different merge targets is a planning bug rather than a stack.

**Working in place forces one-at-a-time dispatch and collapses the branch plan.** What makes concurrency safe is that the task workflow cuts a fresh worktree per run, so two units are two working trees; working in place removes exactly that and puts every unit in one checkout on one branch. Units therefore go out singly regardless of independence, no per-unit branch is planned, and the run yields one branch and one pull request rather than one per unit — state all of it in the plan and the closing report. A base branch is ignored alongside it; **a merge target is not**, since the run still merges under the merging delegate and that one branch and one pull request still need somewhere to land.

## Steps

1. **Settle the preconditions without asking a question you can answer yourself.** Read live repository state in one call for the current branch, the default branch, and the checkout root; never a session's startup snapshot. That default branch is this run's **root base** unless a base branch was given, in which case the given one is. Resolve the named delegate against what is actually installed on this device — an unresolvable delegate is a stop, not a silent fallback. **Then settle the forwarded flags against that resolved delegate before planning anything**: which it accepts, which are dropped for it, and whether any is refused outright — a draft pull request under `--delegate god` or `work:god` is the one stop, and working in place forces one-at-a-time dispatch. Record the surviving set, because dispatch composes it into every invocation and the plan prints it alongside every drop; a flag's fate is read from the delegate's own flag list, never guessed from its name. Then confirm the goal is genuinely multi-part: **a goal that decomposes into fewer than three units is not worth an orchestrator**, so say so and hand it to the delegate as one run instead of wrapping a single run in a planning layer. Under the `work on` form the units are the areas, so **fewer than three areas is one ideas-workflow invocation**, which already selects the union of several areas by itself. Reserve a clarifying question for a true branch point — an irreversible action the goal does not authorize, or a requirement genuinely missing rather than merely unstated.

2. **Decompose the goal, recording four facts per unit, all decided before anything is spawned.** The **workflow invocation** it runs, with its flags and criteria — its flags being this run's forwarded set minus whatever the resolved delegate does not accept, with the drops written down here rather than noticed at dispatch. The **branch it runs on and the base it is cut from**, the branch in the task workflow's own type-and-summary shape — except an `fb` unit, which takes an existing branch named by the goal, because the feedback workflow applies onto work that is already there — the base being this run's root base for a unit that waits on nothing and the branch of the unit it depends on for a stacked one — the run's merge target instead for a stacked one under the merging delegate, whose dependency branch is merged and deleted before that unit is dispatched — with no branch planned at all when the run works in place, and none for a `work` unit either, which is planned around its **area** because the ideas workflow names a branch per idea when it claims it; every parallel unit gets its own branch and its own worktree, because two implementation runs sharing a branch is a corrupted run where the second one's commits land on the first one's half-finished tree and neither pull request describes what it contains; the plan assigns the names up front rather than letting two delegates derive the same name from similar criteria. The **files it touches**, as concretely as the goal allows, which is the input to the batching rather than documentation — a `work` unit is the one that cannot answer it, since its area is its scope and the paths behind that area are the ideas workflow's to discover. And **what it depends on**, if anything.

   **Three to eight units.** Below three there is nothing to orchestrate. Above eight the plan stops being holdable — the failure is not the spawning but that nothing left in the run can still say what the whole thing was for — so a larger decomposition is planned in full and dispatched in successive waves, never fanned out at once.

3. **Batch the units into waves.** Exactly two things make one unit wait for another. **File-scope overlap**: units whose scopes intersect are sequenced however independent they look, because two branches editing one file buy a conflict per unit, paid later by a human at merge time — which is why "what files does this unit touch" is part of planning. And **a stated dependency**, where one unit needs the interface, migration, or surface another introduces. A clean textual merge is never evidence of independence. Everything else is independent and goes out together.

   Give every unit in a wave an explicit **lane**: the paths it owns and the paths it must not touch. The lane goes in that unit's prompt, because a subagent cannot see its siblings' plans.

   **Record the dependency graph in the harness task list, not in a file** — one task per unit, then link the dependencies once every task exists, since a link needs both identifiers. The task list is live session state that a compaction carries forward and this prompt is not, so after a summary it is the only surviving record of what was dispatched and what is still owed. That is the same reasoning behind anchoring the closing turn, and it is why this workflow builds **no second task store, no progress file, and no status dashboard**. A dry run prints the plan and stops here, before any task is created. **The printed plan is what makes a forwarded flag checkable rather than hoped for**, so per unit it names the full invocation dispatch would compose with its flags in order, the branch, the base it is **cut from** and the merge target it **lands in** as two separately named fields rather than one "base" — they are the two things a reader most needs told apart before a subagent exists, and the words for them are otherwise interchangeable, which is the whole reason a plan is printed — the lane, what it waits on, and every forwarded flag dropped for it with the delegate that cannot parse it; a merging unit — `god` or `work:god` — prints the run's merge target, or the default branch when none was given, while any other unit prints no merge target and shows it among its drops, and a `work` unit prints its **area** where the others print a branch and a cut point, saying that its file scope is undetermined until the ledger is read — then, for the run, the resolved delegate, the waves, the in-flight cap with any clamp, and any flag that changed the schedule rather than a unit.

4. **Dispatch each wave as multiple subagent invocations issued together**, one subagent per unit, in a star topology where every worker talks to this session and to nothing else. **Do not wire the workers to each other.** Peer messaging between agents costs roughly 2.4 to 2.7 times the tokens of the equivalent fan-out — about 150K versus 400K for a three-agent review, and 500K versus 1.2M for an eight-agent feature — because every worker pays to read every other worker's traffic. That price is worth paying only when workers must negotiate a cross-cutting concern mid-flight, and here they have nothing to negotiate: each runs a self-contained workflow on its own branch in its own worktree, and the concern they would negotiate was already resolved into lanes. `--mesh` is the escape hatch for the case where a human knows better; it stays off unless typed.

   A `work` unit's prompt names its **area** instead of a branch — the ideas workflow invoked for that area alone, told never to select an idea filed under another unit's area, plus its surviving forwarded flags and any extra context from the goal. Under `work:god` that invocation also names the ideas workflow's merging delegate, carrying the run's merge target when it has one. Every idea is claimed in the ledger before any code is written, so two units racing for one idea resolve there rather than here.

   **Keep each delegate prompt minimal.** Every delegate is a workflow already self-contained through its own file, which the subagent loads when it is invoked. Pass the invocation of the **resolved** delegate — not the default one — with that unit's surviving forwarded flags exactly as the plan printed them, its criteria, its branch and the base it is cut from, and its lane, then stop. A base branch in that invocation carries **this unit's** base, the root base for a unit waiting on nothing and the branch it depends on for a stacked one — or the run's merge target for a stacked one under the merging delegate, whose dependency branch has already been merged and deleted by the wave before it — while a merge target carries the **run's**, identical in every merging invocation and never swapped for that unit's own base — the one flag in the set that does not vary per unit; never re-derive the flag set at dispatch and never add one the plan did not show — restating the whole plan into every subagent prompt puts a second set of instructions in front of the workflow's own, competes with them for attention, and makes completion less reliable rather than more.

   **Dispatching independent units one after another is the specific failure this workflow exists to prevent.** It is the shape a run falls into by default, because each unit reads as the natural next thing to do, and it turns a wave into a queue while reporting success either way.

5. **Collect the whole wave, then isolate the failures.** One failed unit must not cancel its siblings or end the run. Record the failure with its **cause**, not just its name; spend **at most one retry**, and only when the cause is something a retry can change rather than criteria the repository contradicts; carry everything else forward. Four successes and one stated failure is a good outcome, and dying on the first failure is not — the siblings' work is already done and is thrown away for nothing. **The replanning loop is bounded at one round**: a unit whose retry fails is reported as failed and the run moves on, never decomposed again, rerouted to another delegate, or replanned around. An orchestrator that replans until everything succeeds does not terminate, and the second replan is where a run stops being able to say what it did.

6. **Synthesize, because raw subagent reports are not the deliverable.** A subagent's report is never visible to the user and is never the run's outcome. End with **one** summary naming, per unit: the workflow that ran with the forwarded flags it actually carried, the branch and the base it was cut from when that was not the run's root base, the pull request number or URL — **one line per idea it built, with the slug, for a `work` unit, since that unit is a fan-out rather than a single pull request** — and the outcome: shipped, merged, failed with its cause, or never dispatched. Then one line for the run as a whole: how many units, how many landed, and what is left for a human. **Name every forwarded flag that was dropped and for which units**, because a flag typed on the invocation and silently missing from a unit's run is indistinguishable, in a report of outcomes alone, from one that was honoured. **Never batch-merge the resulting branches onto the default branch**; if the run was meant to land as one thing, merge the unit branches onto an integration branch, verify there, and open one pull request from it.

## Closing turn

Close the run in a text-only turn: one final message carrying text and zero tool
calls, sent after the last tool call returns rather than alongside it. A run's
outcome is recorded only from a message with no tool call in it, so ending on one
— or bundling the report into one — records no outcome at all. **A subagent's
report is never that turn**, which matters more here than anywhere: the whole run
is subagents, and the outcome belongs to the session that dispatched them. Every
ending owes that turn, including a run that stops early, is blocked or refused, or
hands work back to an invoking workflow.

Which turn that is depends on how this run was invoked, and there are exactly
three cases. Invoked directly by the user, this is the outermost run and it
closes in a text-only turn as above. Invoked inline by another command in the
same session, as a step of that invoker's own pipeline, it hands back without
spending a text-only turn: the report and the return marker go out as text in
the same message that carries the invoker's next tool call, so the turn
continues into the invoker's next step instead of returning control to the user.
A text-only turn there ends the whole assistant turn and strands every step the
invoker still owes, which is how a live pipeline comes to read as abandoned.
Dispatched as a subagent, it closes in its own text-only turn like an outermost
run, because its final message is a report to the parent session rather than a
turn in the parent's conversation. The return marker is written exactly once in
all three cases, alone on the last line of the message that hands control back —
never weakened, deferred to a later message, or dropped because the turn
continues.

Anchor that turn before the first tool call: put "close the run in a text-only
turn" in the todo list as its own final item, because the todo list is live
session state that a compaction carries forward and this prompt is not. Resolve
it in the same tool-call turn as the run's last piece of real work, so the list
is already clean when that turn returns and the only thing left to do is speak.
Never leave marking it as a call of its own after the work ends: a run whose last
scheduled action is a bookkeeping tool call ends on that call — the mark lands
every time, and the message meant to follow it never arrives. A
compaction boundary is a checkpoint, not an ending — a recap prompt, a
background-task notification, or a session-continuation preamble each mean the
run is still owed its turn, so answer in text alone, say where the run stands and
which units are still in flight, and restore the todo item if it did not survive.
Each side of a boundary records its own standing, because a run split across two
transcripts is two runs to the record. Every message from the user opens a task in
the same transcript, and only a reply carrying text and no tool call closes it, so
answer a mid-run question, correction, or recap in text before returning to tool
calls. A reply to another session is not that turn either: sending a message is a
tool call, so send the reply, let it return, then close in text alone.
