# Build Accepted Ideas

Parse `--idea <slug>[,<slug>...]`, `--area <area>[,<area>...]`, `--repo <slug>`, `--max <n>`, `--dry-run`, task workspace flags, and optional extra context.

This workflow is the ideas half of what used to be one command. `$improve` is the advice half and is now advice only; nothing there reads the ideas ledger and nothing here reads the suggestions store. **The accepted ideas are the criteria**: every change traces back to a recorded human sign-off, this workflow adds no ideas of its own, and it never acts on an idea still proposed or already rejected.

## Selection

`--idea` and `--area` are the two selectors, and giving both selects the **union** of what each matches, never the intersection; the report says which selector brought each slug in.

- `--idea` names slugs, never titles, and is both repeatable and comma-separated. A near-miss is a miss.
- `--area` takes areas from the ledger's own free-text vocabulary — the seeded `ui-ux`, `infrastructure`, `code-quality`, `services`, `commands`, plus any area an ideation run invented — and `Unfiled` selects the area-less legacy rows. The listing matches **exactly one** area, so a comma list is filtered in this workflow against one unnarrowed read rather than by looping the CLI.
- **No selector at all is the default, and it means every available idea for the repository.**
- `--repo <slug>` overrides the repository filter, which otherwise comes from the git remote slug. **Never an absolute checkout path**: the ledger is device-wide and a path names a different thing on another machine.
- `--max <n>` caps how many ideas one run dispatches, default five, and applies **only to a run with no selector**. Over the cap the run stops and reports the available count, the per-area breakdown, and that an area, a slug, or an explicit cap narrows it. An explicit selector means a person named the work, so named slugs are never truncated.
- `--dry-run` reports the selection, each idea's file scope and stated dependencies, and the dispatch schedule that would be used, then stops. It claims nothing, because a claim is a write.
- Task workspace flags are forwarded verbatim and not interpreted here, except that an in-place workspace flag forces serial dispatch.

## Steps

1. Resolve two independent things, and fail on them separately. **The ledger is hosted and has no local fallback by design**: a device that cannot reach it does no ideas work, and never falls back to a repository's committed ideas document, a device-local ledger, or a log-directory JSON file — a private copy that looks complete is exactly what hosting the ledger removed. Require the operator Worker's address and token, accepting the concepts address and token as fallbacks for each since ideas and concepts are one dataset behind one Worker. A device missing either **stops, naming both variables**. Read the address to confirm it is set; **never print the token**, only check that it is non-empty. Separately, resolve `CLAUDE_PROXY_STORE` for the checkout the ideas CLI runs out of — its parent is the log directory and the directory above that is the repository — and stop the same way when it is unset or the checkout is missing.
2. List the ideas **available to build** for this repository as structured data, in one unnarrowed read. Available means accepted plus the ideas whose claim has expired, which is exactly the set a run may take. Accepted alone can never recover an idea a run picked up and then died holding, since that entry now reads claimed and no sweeper will restore it, while accepted-plus-claimed hands you one out from under a run still building it. **This does not loosen the sign-off rule**: claimed is reachable only from accepted, so every available row was signed off, and a later reader must not narrow the query back. **Nothing outside that set is ever read.** Do not pass an area to this read: the CLI matches one area, a run may have been given several, `Unfiled` is not filterable at all, and only an unnarrowed read can tell an empty area from a misspelled one.

   Select in this workflow against what the read returned, since the listing has no slug filter. No selector takes every returned row; a named slug matches exactly; an area selects by membership; both together take the union.

   **A named slug that does not resolve stops the run and is never skipped silently.** Report an unknown slug with the available slugs that do exist, so a typo is one glance from fixed, and report a slug found in another status with the status it actually holds — proposed needs a sign-off on the dashboard's Advice page, rejected was turned down and is not overturned here, shipped already landed and carries its pull request. Stop on the first unresolved slug, before anything is claimed: a silent skip turns a request to build three ideas into a run that quietly builds two, and the missing one is indistinguishable from one nobody asked for. **An area that does not exist is a stop too**, decided against the areas actually on the ledger for this repository rather than against the seed list, because a misspelled area selects nothing and looks identical to an area with no available ideas — the run would dispatch nothing and report success. Name every area that does exist with its available count. An area that exists but has nothing available is **not** a stop; that is an honest empty selection. **A slug held by a live claim is a skip with a named holder**, not a stop: nothing is wrong, the claim expires or is released, and the answer is to wait.

3. **Take each idea's brief from the ledger rather than re-deriving it.** Ask the ideas CLI to compose the prompt for that slug: it already assembles the title, the rationale in the ideation workflow's fixed bullet order, every citation, the claim lines, and the human's **comment**, quoted verbatim as build criteria that **override the rationale where the two disagree**. Re-deriving a brief per subagent is how two briefs for one idea drift apart, and the comment is a signer's build instruction that reaches the subagent no other way. **An idea is a proposal and not a specification** — a named mechanism passes through, and where none is named the brief says what is undetermined rather than inventing a design the sign-off does not cover. **One idea is one brief**; never merge two ideas because they share a repository or a file.

   Compose only two things around that prompt, because they are facts about this run's schedule rather than about the idea: the **lane** and the **base branch**. Name the repository and its absolute checkout path as well.

   Record two more fields per idea, because the dispatch step schedules from them and cannot recover them later. **File scope**: the paths the idea is expected to create or change, as concretely as its rationale and cited evidence support — exact files where it names them, an area where it names one, undetermined where it names neither. An undetermined scope is the widest scope there is, not an empty one, so it overlaps everything else in its repository. **Stated dependencies**: whether the idea's own rationale says it consumes something another selected idea introduces — design tokens, a control primitive, a shared component, an API or command-line surface, a configuration key — naming the idea it depends on. Only a dependency the idea itself states counts; one inferred because two ideas sound related is a guess, and a sign-off covers a guess about sequencing no more than it covers a guess about design. Ideas in different repositories never share a scope, since identical relative paths in two checkouts are two different files. A dry run stops here and reports.

4. **Claim each idea in the ledger before dispatching it**, never at pull-request time — the claim exists because two runs once built one idea eleven minutes apart, both reading it as free right up until the first pull request appeared, and one was closed unmerged. Decide the branch name this dispatch will cut, in the task workflow's own type-and-summary shape derived from the slug, and claim under that branch as the holder. **The branch name is the holder for a reason**: it is the one string a second run can check for itself against the remote branch list, telling a claim backed by real work from one left by a run that vanished, where a run identifier or a person's name would tell it nothing. Put that branch in the brief so the subagent cuts exactly it. **A refused claim means another run holds the idea**: skip it, name the holder and since-when in the report, and never build it anyway or retry under a different holder string, which would hide the collision rather than resolve it. Only an accepted idea — or one whose claim is stale or already yours — can be claimed at all, so claiming can never route around a human sign-off. Once a dispatch returns a pull request, re-claim the same slug under the same branch with that pull request attached: claiming is idempotent for the same holder, and a claim carrying a pull request never expires, which matters because the expiry is sized to writing the change while the long part of an idea's life is review.

   Claim **every** idea in a wave before that wave is dispatched, one claim per slug, and dispatch only the ones whose claim succeeded — concurrency makes the claim matter more rather than less, since dispatching first and claiming afterwards widens the very window the claim closes to the size of the wave. A refused claim also drops whatever was stacked on it: the dependent idea has no base to build on, so it is skipped and reported as blocked by that skip, never re-based onto the default branch to keep it moving.

   Then invoke `$task` once per idea with that single brief — one idea, one branch, one pull request — never batched with another idea, and **least of all because two ideas were found independent**, since independence is what lets them run side by side rather than a reason to fold them together. **Ideas that do not conflict are dispatched concurrently**, as a wave of simultaneous invocations whose results are all read before the next wave opens; ideas that genuinely depend on one another run in order, and **a dependent idea branches off the branch it depends on rather than off the default branch**, dispatched only once that branch exists and its run has returned, with its brief saying which branch it is built on and that its pull request targets that branch.

   **Exactly two things make one idea wait for another.** Their file scopes overlap inside one repository — the same file, or one's area containing the other's paths, with an undetermined scope overlapping everything in that repository. Or one's own rationale states that it consumes what the other introduces, in which case it waits even when the two touch no common file, because the value has to exist before it can be referenced. Nothing else is a conflict: sharing a repository is not, sounding related is not, and coming from one ideation run is not. **A clean textual merge is never evidence of independence** — a stacked idea merges without a single conflict marker while referencing a token, property, or endpoint that does not exist on its base, so the break appears at build time rather than in the diff. Where the two tests disagree, the stricter wins, and where it is unclear, serialize: an unnecessary wait costs one run's latency, while a wrong parallel costs two branches whose merge order changes the result.

   **Give every concurrently dispatched invocation an explicit lane** — the paths that idea owns and may write, and the paths it must not touch, which are the scopes of every other idea in flight named as such. A subagent that needs a file outside its lane stops and reports rather than taking it. The lane is what makes two live branches unable to collide, and a subagent widening its scope in good faith is that collision arriving anyway; it cannot see the others, so anything about them it must respect belongs in its own brief. Serialized invocations get a lane too, both because it is the cheapest place to say the idea it was stacked on already owns those paths and because lanes are not a parallel-only device.

   Give every invocation its explicit checkout path as the working directory and the forwarded workspace flags. Same-repository concurrency is safe only because the task workflow cuts a **fresh worktree per run**, so two concurrent ideas in one repository are two working trees — which is exactly what an in-place workspace flag removes. **When the forwarded flags ask the task workflow to work in the current checkout in place, dispatch one at a time regardless of scope**, and say in the report that the flag forced serial dispatch.

5. Mark each shipped idea in the ideas store, one call per idea, **with that idea's own pull request as the note**. Each idea was dispatched alone, so there is no shared run-wide URL to write, and a slug pointing at a pull request that built something else is a false record that reads as a true one and that no later run can detect. An idea whose pull request did not land stays accepted and returns next time, and because the pull requests are separate, one idea failing marks nothing against the others. Never move an idea back to proposed or rejected: this workflow implements advice and does not overturn a human's sign-off. Marking shipped keeps the claim, deliberately — it becomes the record of which branch built the thing, beside the pull request in the note. **Nothing is ever marked in the suggestions store**, which belongs to `$improve`; a slug is not a bucket-and-id.

6. Report how many ideas were selected and **which selector brought each one in**; the dispatch schedule actually used, naming which ideas ran concurrently, which waited, on which branch each stacked idea was based, and the reason for every serialization; the pull request for each idea listed separately; which ideas were marked shipped against which pull request; and what stays accepted with why. Say what happened to each claim as well: which slugs this run claimed and under which branch, which it skipped because another run held them with the holder and since-when, which were dropped because the idea they stacked on was skipped, and which it released on the way out — a skipped idea and an idea nobody selected look identical in a report that counts only what shipped, and the first one is coming back on the next run.

## Closing turn

**Release every claim this run still holds, in the same turn as its last piece of real work.** An idea this run claimed and did not ship is marked back to accepted explicitly, rather than left to expire: every mark other than shipped drops the claim, which is what makes that the release. It belongs here because every ending routes here — the run that gives up, is refused, hits a failing gate, or is abandoned as wrong is in each case a run holding an idea it will not build, and hooking the release to the closing turn is what makes it happen on the exits nobody plans for. Without it the idea reads as taken for the full six-hour expiry and every run in that window skips it, blocked by a holder that went away rather than by any real work. Release only what did not ship: an idea that landed already carries its pull request and was marked shipped, and releasing it would discard the record of who built it, while a run that opened a pull request but stopped before marking should leave the claim alone, since a claim carrying a pull request does not expire and shows the next run that the work exists.

Close the run in a text-only turn: one final message carrying text and zero tool
calls, sent after the last tool call returns rather than alongside it. A run's
outcome is recorded only from a message with no tool call in it, so ending on one
— or bundling the report into one — records no outcome at all. Every ending owes
that turn, including one that stops early, is blocked or refused, or hands work
back to an invoking workflow.

Anchor that turn before the first tool call: put "close the run in a text-only
turn" in the todo list as its own final item, because the todo list is live
session state that a compaction carries forward and this prompt is not. Resolve it in the same tool-call turn as the run's last piece of real work,
so the list is already clean when that turn returns and the only thing left
to do is speak. Never leave marking it as a call of its own after the work
ends: a run whose last scheduled action is a bookkeeping tool call ends on
that call — the mark lands every time, and the message meant to follow it
never arrives. A
compaction boundary is a checkpoint, not an ending — a recap prompt, a
background-task notification, or a session-continuation preamble each mean the
run is still owed its turn, so answer in text alone, say where the run stands,
and restore the todo item if it did not survive. Each side of a boundary
records its own standing, because a run split across two transcripts is two
runs to the record. Every message from the
user opens a task in the same transcript, and only a reply carrying text
and no tool call closes it, so answer a mid-run question, correction, or
recap in text before returning to tool calls. A reply to another session is
not that turn either: SendMessage is a tool call, so send the reply, let it
return, then close in text alone.
