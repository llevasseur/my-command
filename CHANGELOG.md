# Changelog

All notable changes to MyCommand are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com). There are no fixed release
versions — the plugin publishes continuously and installed copies track the
latest commit (SHA-based versioning), so changes are grouped by date.

## 2026-08-21

### Changed

- **`/cp` says which stash slot the copy landed in, so putting a clobbered copy back takes no counting.** The reply was `Done!` plus at most one line of context, and the ring entry it had just written went unnamed — so recovering that copy meant either trusting that a bare `--again` still pointed at it or running `stash list` and reading timestamps to work out how far it had rotated. The reply now carries the slot — `Done! 0` — and a `--again` run names the slot it restored, which is the number that goes straight back into `/cp --again <slot>`. It is read rather than assumed: `my-command-tools stash write` now reports a `slot` field alongside `path` and `bytes`, and its one-line status says `stashed N bytes in slot 0`, so the command names what the verb did instead of hardcoding what `slotPath` already decides — a reply naming a slot it guessed would be worse than one naming none. `stash restore` already reported its slot and is unchanged. Nothing about the ring moved: still five deep, still rotated inside the verb, still under `~/.claude` (or `$CLAUDE_CONFIG_DIR`) and nowhere else, and a fresh copy still lands in the newest slot, so bare `/cp --again` keeps working exactly as before. `skills/cp/SKILL.md`, `docs/features/cp.md`, and the README usage rows carry the same rule, including the one reply that names no slot — a `--again` against an empty slot, where the verb copied nothing and so has no entry to name, and `commands/` was regenerated rather than hand-edited.

## 2026-08-20

### Added

- **`/health` — report what is actually consuming this machine's CPU, memory, and energy, then fix the safe findings.**
- Rolls every process up to an **owner** (application, vendor, session manager, repo) before ranking. A per-process table puts system noise on top: 393 OS processes summing to 187% CPU sat above 15 endpoint-security processes summing to 141%, and only the rollup showed the security suite was the largest consumer by 8x.
- Ranks four axes — CPU now, memory read against the compressor rather than free pages (one run: 58 MB free, 7.4 GB compressed), energy, and watcher churn.
- **Energy is declared as a proxy.** Activity Monitor's Energy Impact is not available to an ordinary process and `powermetrics` needs root, so the column is cumulative CPU time and says so. `/health` never takes root.
- Output is two tables plus a fix list, each finding tiered `SAFE` / `CONFIRM` / `MANUAL` / `LEAVE` — a claim about safety, not value. The report is the deliverable; a healthy machine gets the same tables.
- Read-only by default. `--fix` acts, `-y` skips the prompt for `SAFE` only, `--top <n>` sets rows, trailing text focuses an owner without hiding a heavier one.
- **`--fix` re-measures before every signal**, because ownership moves: a recorded run saw the live backend change PID three times in twenty minutes and a port flip between two duplicate dev stacks, so a list built from the first reading would have killed the working server. Kills are guarded by command-line match rather than PID, run from a script file rather than inline shell, and every previously-serving port is re-checked after.
- Four refusals hold under `-y`: no stopping a supervised service (persistent login-state change, so it quotes the disable line instead), no closing unsaved work (asked of the application — one run cleared an editor as clean from an empty backup directory and found a dirty marker in the app's own window list a step later), no killing a process bound to a live port unless named, no root.
- Reports numbers that got worse. Load average climbs after a cleanup as the indexer and scanner react to the teardown; the run names them instead of hiding the spike.
- Carries a **Known patterns** section so the engine stays generic: duplicate dev stacks, supervised services read as strays, editors served over local HTTP into a shell window, managed security software, decorative work with no viewer, idle pre-warmed slots.
- macOS-first, degrading on Linux and naming the sections it cannot fill rather than printing a macOS-shaped number.
- Ships with the Codex skill, the feature doc, and both README tables.

## 2026-08-18

### Fixed

- **The outcome gate was armed and exempting itself out of every run it existed for.** Measured again over 13 later buckets, `Stop` had missed **eight** confirmed runs — a `/god --no-review` closing on `TaskUpdate(4)`, `TaskUpdate(5)`; two `/mc -t` runs closing on `worktree end` plus bookkeeping; `/task -b`, `/work --area`, `/ideate`, and two `/fb -t` runs, one of which failed at its seventh call with "branch does not exist locally or on origin", spent its last two calls listing branches, and never said so. The shape logic was never the problem; **three exemptions were**, and each is now gone or bounded. `stop_hook_active` returned outright, so the gate could speak at most once per session and a run that took the block and then ended on *one more* chore turn exited unreported — two buckets carry the injected "This run has not recorded its outcome" feedback **and** record nothing for their root. That return never prevented the loop: the per-turn denial key does, and a *different* turn is a decision made after being told, so it is judged again under a `MAX_REMARKS = 3` ceiling that guarantees a session can still end. `foreignTranscript()` had no business in `Stop` at all — only `Stop` is registered, never `SubagentStop`, so every event belongs to the session that owns the path, and its *recency* test ("a subagent transcript beside this one is newer") means "this run dispatched something" at a parent's stop, which is true of every delegated pipeline and is exactly where the misses are. `CLAUDE_JOB_DIR` stood the gate down on the assumption that a background job's harness requires its own outcome line; it does not, and a backgrounded command run is precisely the shape that was missing one. `CI` and `MY_COMMAND_NON_INTERACTIVE` stay. Separately, **the trailing-anchor gate had never been invoked**: the `PreToolUse` matcher read `Read|Grep|Glob|Bash|Edit|Write|NotebookEdit|MultiEdit`, and that gate judges `TodoWrite` — it shipped, was documented at rung 4, and was a file nobody executed. `check-commands.sh` now fails when the matcher does not name every tool a gate judges.
- **A `TaskCreate` that schedules the run's own closing message is refused.** One recorded run spent its last three calls creating tasks, one of them reading "Deliver the final report as a message with text and zero tool calls", and then sent nothing — creating the task is itself a tool call, so scheduling that message is the mechanism that loses it. Refused by subject, which `TaskCreate` carries and `TaskUpdate` does not. The `TodoWrite` anchor `/task` prescribes is untouched: it is written at the *start* of a run, and only completing it as a turn's sole content is refused.
- **Three refusals that were already firing now hand back the working form.** All three come from Claude Code itself, name no alternative, and are not once-per-subject, so each was paid for repeatedly. `shellProgram()` — until now deliberately unwired — is wired for a cwd under `.claude/worktrees/`, the only place the harness answers "too complex to verify that it stays inside the worktree"; one recorded worktree collected **nine** of them across four sessions and one run took five inside its first fifteen calls. `EnterWorktree` from a repository root is refused naming `workingRoot` and the absolute-path mode, since a dispatched run starts at a root by construction and it was recorded as one of the run's *first* actions in nine sessions. And a whole-file `Read` past 90KB is refused naming the `offset`/`limit` slice: six recorded refusals of "exceeds maximum allowed tokens (25000)" landed on files of 25,923–37,456 tokens and were rediscovered one file at a time by four separate sessions. That last is the one gate here that fires on a bound rather than a certainty — the cap is in tokens and a hook cannot tokenize — so a slice is never refused and the denial is once per path.
- **`grep --include=<glob>` is refused whatever its quoting, and `rg -g` is what comes back.** The unquoted-glob gate only fires when the pattern matches nothing, and hands back the same command with that pattern quoted — which for four of the recorded patterns is the **wrong** answer: they carried a stray trailing `;` (`*.tsx;`, `*.stories.tsx;`, `lib/aem-source/*.ts;`, `*.json;`), so quoting them as written turns an abort into a silent zero matches. `--include`/`--exclude` with a glob is now refused on its own terms across at least ten recorded sessions' worth of the shape, the stray separator is stripped from the replacement and reported as its own fact, and the unquoted-glob denial repairs it too.
- **The heredoc gate now sees every file composed in the shell, and speaks once per file.** It saw only a heredoc and keyed one denial per session, so `cat >` writing production source, `cat >` composing a commit-message file that `commit --message-file` takes directly, and `gh pr view` appended into a file all slipped past or were refused only once while a session composed several. Any redirect whose content the **shell itself supplies** — `cat`, `echo`, `printf`, or a heredoc feeding a redirect — is refused, keyed per target. A program capturing its own output (`pnpm test > log`) is not this shape and is untouched, and a target the shell computes is skipped, which keeps the `$CLAUDE_JOB_DIR` scratch write the job harness prescribes allowed.
- **`cd <dir>` issued from inside `<dir>` is told to drop the `cd`.** The denial used to walk up and name an absolute path to change into, which is beside the point when the cwd already *is* the target — recorded three times in a row in one session and in five others. It now hands back the command with the leading `cd` removed, plus where to read the cwd from instead.
- **The polling gate stopped reading a watch's arguments as its output.** `watchedPaths()` keyed on every filename-shaped token of a watch's command line and answered the shell half of the gate, so a **first** probe of `server.ts` and of `artifactDownload.ts` was refused because a `Monitor` command happened to name them. Both halves now ask the narrower question `watchedOutputs()` already answered for the `Read` half — the watch's own redirect, `tee`, or `tail` target — and the broad helper is removed rather than left for one caller.
- **A `grep`/`find` sweep of an OKF bundle is refused with `okq` named.** One recorded run issued three clusters of independent `find | xargs grep` sweeps over one `docs/` tree while its own system prompt said the bundle is queryable with `okq`. A bundle declares itself in its `index.md` frontmatter (`okf_version`), so the gate reads that off disk rather than guessing from a directory being called `docs`.

## 2026-08-17

### Changed

- **`/clean` runs `pnpm lint:anti-slop` early — before touching any comment — when the repo defines that script.** The comment pass judged slop by eye alone; repos that carry the anti-slop Oxlint plugin already flag it mechanically, and that signal arrived after the edits or not at all. `/clean` now checks the repo root `package.json` for a `lint:anti-slop` script as part of its batched Scope reads and, when present, runs it before the delete/tighten pass, treating each finding that lands on a line in scope as a candidate. The gate is the script's existence: absent, the step is skipped and the summary says so — `/clean` never adds the script, installs a plugin, or edits lint config to make it runnable. The lint's output is input, not a gate: non-comment findings and findings outside the diff stay out of bounds, so the command still only touches comments in scope. Frontmatter allowlists exactly `Bash(pnpm lint:anti-slop)`.

## 2026-08-16

### Added

- **`agents/` — MyCommand now ships subagent definitions, and every dispatch site names one.** Eight dispatch sites across seven commands all took the **default agent**, because no command file named a `subagent_type` — measured on this device, of 35 spawn records in `logs/sessions` 30 read `- agent: general-purpose` and 5 read `- agent: Explore`, with no custom agent type existing anywhere. The consequence was not just a generic delegate: with nothing to name, each dispatch prompt had to **restate the delegate's role in its own words**, once per site, drifting per site. `agents/` now holds one definition per **shape of delegation rather than one per command** — that sharing is the point, because it is the restatement across two sites doing the same kind of work that used to drift. Five shapes cover the eight sites: **`mycommand-delegate`** runs one whole workflow command end to end on its own branch (`/work`, `/manage`, `/improve`), **`mycommand-finisher`** runs `/clean` then `/pr` in one shared context on a worktree it does not own (`/task --sub`, and `/god` through it — `/god` always adds `--sub`, so it needs no site of its own), **`mycommand-reviewer`** reviews one PR without inheriting the authoring conversation's framing (`/review`), **`mycommand-doc-auditor`** audits one doc against the code it describes (`/docs`, `/truncate`), and **`mycommand-griller`** is a long-lived read-only interlocutor asking one question per round (`/dev`). Each declares a model, a tool list, and the role in full, so a dispatch prompt now carries **this run's specifics alone** — the branch, the path, the doc, the idea. The **`tools` list is a capability boundary, not a hint**: `mycommand-reviewer` ships without `Edit` or `Write`, which is what makes "report findings, never apply them" structural instead of advisory, and the griller and doc auditor are read-only for the same reason; `mycommand-delegate` takes `"*"` because the command it runs decides what it needs. `model: inherit` everywhere except the doc auditor, which pins `sonnet` because it is dispatched one per doc in parallel batches over inventory work. A definition that never reaches the device makes a correctly named dispatch behave **exactly like an unnamed one**, so all three Claude surfaces place them the way each already places commands: `install-personal.sh` symlinks them into `${CLAUDE_AGENTS_DIR:-~/.claude/agents}` so `git pull` updates them (an existing real file is skipped and reported, never overwritten), the npx wizard's `installAgents()` **copies** them on both Claude choices for the same reason `installHooks()` copies — npx runs from an ephemeral cache a symlink would dangle into — and `.claude-plugin/plugin.json` declares `"agents": "./agents/"`. **Codex is deliberately untouched**: it has no subagent mechanism, the same call the wizard already makes for hooks. `check-commands.sh` gains invariant 20, holding all three parts together because each is silent when it breaks alone — every definition declares its four frontmatter fields with `name` matching its filename (`subagent_type` resolves the name while the installer places the file), every definition is named somewhere, each of the eight dispatching commands still contains a `subagent_type`, every named type has a file, and both install surfaces plus the manifest still place them. `check-doc-snippets.mjs` now sweeps `agents/` too.
- **`my-command-tools worktree list` reports which worktrees are reclaimable.** The verb answered `root`, `path`, `branch`, and `head`, so nothing said whether a worktree had outlived the branch it was cut for — finding that out meant a `git merge-base --is-ancestor` per worktree, by hand, and the answer was usually that several had. This device held five in `my-command` and nine in `claude-proxy`; two of the five were already merged. Each entry now carries **`reclaimable`**, `true` when its branch is already an ancestor of `origin/<default-branch>` and removing the worktree therefore loses nothing. It is **tri-state on purpose**: `null` means the question could not be answered — a detached worktree has no branch whose merge could be read, a branch ref git can no longer resolve answers neither way (only git's exit 1 is a real "not merged"; any other exit is a failure to judge), and with no local `origin/<default>` there is nothing to compare against — because reporting `false` in those cases would read as "live work" when the truth is "fetch first", which is the one wrong answer a reclaim report can give. The ref every entry was judged against is reported once alongside them as **`comparedWith`**, so `null` there with `null` throughout is unambiguous. The **default branch is always `false`**, never `true`, even though it is trivially its own ancestor: `worktree` already refuses to target the default branch, and marking the main checkout reclaimable would contradict that guard. The verb stays **offline** — it reads the remote-tracking ref already on disk rather than fetching, so `list` remains a cheap local lookup whose answer is as fresh as the last fetch (`begin` fetches). There is deliberately **no size field**: `du` overstates a worktree by roughly seven times on APFS because pnpm clones package files from its store rather than copying them — a measured `pnpm install` producing a 197 MB tree cost 0 MB of real disk — so apparent size measures the store rather than what removing the worktree would return. The reclaim signal is the merged branch, not the apparent size. Existing fields and their names are unchanged; this is additive.
- **`/manage work on <area>[, <area>...]` and `/work --delegate task|god` — the `/manage` → `/work` → `/task`/`/god` flow now joins up at both ends.** Two additive changes to the existing command prompts, with every invocation shape that worked before unchanged. **`/manage` gains a `work` unit type** alongside `task`, `god`, and `fb`: `work on <area 1>, <area 2>, …` selects it and takes the comma-separated list as the areas, one unit per area, each dispatched as `/work --area <area>` in the same collision-free waves the other unit types already use (`--delegate work` with a goal naming areas means the same thing). A `work` unit is the mirror image of an `fb` unit on branches — **`fb` cuts none, `work` cuts many** — because `/work` claims each accepted idea under the branch name it is about to cut, so branch naming lives *inside* the unit and the plan is built around the **area** instead. That area is also the **lane**: every idea is filed under exactly one area, so two units select disjoint idea sets, and `/work`'s claim protocol is the backstop if they ever race. What the plan honestly cannot know is a `work` unit's **file scope** — the paths behind an area are `/work`'s to discover — so two adjacent areas can yield two PRs to reconcile rather than one corrupted branch (each idea still gets its own `/task` worktree), and the plan says so with `--sequential` as the escape hatch. `--parallel` bounds units in flight, not ideas per unit. **`/work` gains `--delegate task|god` / `-D`**, choosing the downstream command each accepted idea is dispatched to: `task` (default) stops at an open PR, `god` drives that PR green and **merges it without asking**, with `--into <branch>` forwarded as the merge target and dropped-and-reported under the default delegate. Because `/god` deletes each merged branch and waves run in order, a **dependent idea under `-D god` is cut from the merge target** rather than from a branch that no longer exists — the dependency merged *into* it, so the interface is already there. Shipping under `-D god` also means **merged, not opened**: a PR left open on a conflict, on red CI, or queued for auto-merge stays `accepted` and the stop is named in the report. The two compose as **`/manage --delegate work:god`**, which puts every downstream run inside every unit in god command mode — the most multiplying form the orchestrator has, areas × ideas, with the count unknown until the ledger is read — so like `-D god` it must be typed and is never inherited, `--into` is kept for it and dropped for a plain `work` unit, and `--draft` is a stop for both. Both Codex skills, both feature docs, and both README tables carry the new unit type and the downstream choice.
- **`/dev` — take one complex idea all the way to merged, unattended, and record every decision it made on your behalf.** One invocation runs four phases and reimplements none of the commands it composes. **Grill**: exactly **one** read-only adversarial griller subagent, spawned once with the idea plus `docs/specs/index.md` and `docs/adrs/index.md`, and messaged for every later round rather than respawned — so its repo context is paid for once instead of re-derived per round. It asks **one question at a time** (batching lets a weak answer hide among strong ones), and every answer is **grounded in an okq spec or ADR, cited by path**. One pass, on the idea only; ends at no open questions or 12 rounds, `--rounds <n>` overriding and `--no-grill` skipping. **Decision traceability** is the point of the command: an answer it could *not* ground is a decision `/dev` made itself, written immediately as a real ADR in `docs/adrs/` — never only in the wayfinder map, which is deleted when the campaign closes — carrying `decided-by: /dev`, `ratified: false`, the campaign slug, the grill round, and `needs-human: true` where the call is a human's to make. Status says it was proposed and not ratified; Context quotes the griller's question **verbatim**. `/dev` **never blocks and never asks**: it decides, marks the ADR, and the campaign PR body then **leads with the `needs-human` list**, so review is where those calls get made. Per [ADR 0003](docs/adrs/0003-dirty-flag-for-doc-density.md) the keys need no tooling change and are queryable — `okq --bundle docs find --where ratified=false`. **Chart**: `/wayfinder start` invoked **directly**, not through `/manage`, because the map already owns the branch names; its planning PR merges with `/god --into <default branch>`. **Build**: only the ticket set goes to `/manage`, one unit per ticket as `/wayfinder --unattended execute NN`, in **waves by default** — as many as the file-scope lanes allow, bounded by `/manage`'s hard cap of 8, because two tickets on one file is a conflict an unattended run pays with no human at the merge — each landing via `/god --base wayfinder/<slug> --into wayfinder/<slug>`, then `/wayfinder complete NN`. `--sequential` and `--parallel <n>` are the escape hatches. **Land**: `/wayfinder close` opens the campaign PR and `/god --into <default branch>` merges it. On failure, after `/manage`'s own single retry, exactly **one** more round — re-grill, re-plan, re-dispatch — and then a **fallback** that closes the campaign PR for review but merges nothing and keeps the map and the failed plan alive, so `/dev --resume <slug>` can finish it. Resume is always explicit. Ships with the Codex skill, the feature doc, [ADR 0005](docs/adrs/0005-agent-authored-decisions-are-marked-in-frontmatter.md), and both README tables.

- **`my-command-tools verify --wait [<verdict>]` — the blocking wait the busy-wait loop existed for.** `--background` shipped a *notified* wait: arm a watch, wait for its notice, then read the report — three calls and a watch, and a run with nothing else to do polled instead. Eleven judged buckets recorded it end to end: one session read the report roughly **twenty** times and then ran `wc -c` on it four turns running, stating four separate times that it had armed a monitor and would stop polling and then polling on the very next turn; another read it **fifteen** times between two nodes while interleaving `ps | grep -c vitest`; two sessions ended still inside the loop. The reason the loop never terminated on its own is that **the report does not exist until the run is over** — it is written to a temp file and renamed into place at exit, so every early read returned the same nothing, and the poller read that as "not yet" rather than as "unreadable by construction". `--wait` is one foreground call that blocks until the detached run exits and returns **the whole report and its exit status in that call's own result**, so there is nothing left to read afterwards. `--wait-timeout <seconds>` bounds it (default 570, inside the Bash tool's ceiling) and a timeout **kills nothing** — it says the run is still going and hands the same wait back. Bare `--wait` takes the most recent detached run; with none it names `verify --background` instead of blocking on a file that will never appear. `--background` now returns `wait.blocking` and a ready-to-send `wait.blockingCall` alongside the pre-existing notified pair, and the watched-condition and stale-probe denials in `pre-tool-use.mjs` hand back that exact command — a denial that supplies the wait rather than only refusing the poll. `/task` and `/review`, and both Codex skills, prescribe the detach-then-block pair and say the report is atomic at exit, which is what makes the poll provably useless rather than merely wasteful.
- **`my-command-tools stash write --consume` deletes the compose file it just read.** `/cp` writes `~/.claude/cp-compose.txt` at a fixed path and then `stash write`s it, and one recorded session hit the read-before-write error on that same file every time it ran, because nothing had ever read the copy left over from last time. Removing the file as part of the write closes it structurally: the next run always writes a path that does not exist, which is the case `Write` allows. `/cp` and its skill now pass the flag and say it is not optional — it is what lets the path be a fixed one.

### Changed

- **`/improve` judges whatever range you give it — the five-bucket cap is gone.** The cap turned a large backlog into a refusal: more than five dirty buckets and the run stopped, handing back a choice between narrowing `--range` and an amnesty backfill that records verdicts for transcripts nobody read. Both answers are worse than doing the work, and neither is a decision the command should be forcing at the point where it already knows the bucket list. The run now judges the whole range however large it is, and never narrows it or drops buckets on its own. What survives from the cap is the cost transparency and the batching it was standing in for: the dirty bucket count and rough read cost (~55 KB of transcripts per bucket, ~180 KB worst case) are stated before judging starts, and `/judge` is dispatched at most five buckets per call, sequentially, until the range is done — chunking that paces the reading and keeps a failure pointed at a small set rather than an unknown subset, without ever ending the run. `suggestions judge --amnesty` remains available and is now explicitly the human's call: `/improve` names it only when asked to skip the backlog and never runs it to shorten a run. The failure stop is untouched — a judge run that errors, under-records, or cannot finish still stops the command, and there is still no fallback to composing from unjudged output. Codex skill and feature doc carry the same rule.

### Fixed

- **`/cp` composes into a per-invocation filename, so its first `Write` no longer fails on every fresh session.** Step 3 prescribed one fixed path — `~/.claude/cp-compose.txt` — for every `/cp` run on the machine, and `Write` refuses to overwrite a file the current session has not read. Any leftover copy therefore turned the documented form into a guaranteed rejection followed by a `Read` of roughly two kilobytes of the *previous*, entirely unrelated, composed prompt, purely to earn permission to overwrite it — one wasted call plus a stale-context read on every invocation of the command whose whole stated purpose is to spend as few tokens as possible. `--consume` did not close that, and could not: it only removes the file on runs that **reach** the stash write, so a run that stopped between the two calls, or any copy predating the flag, still poisoned the next session. The path is now minted per invocation — `cp-compose-<UTC timestamp>-<random>.txt`, so `cp-compose-20260816-142455-9f2c.txt` — and a path that cannot already exist never meets the read-before-overwrite precondition at all, which makes the documented form the one that works instead of the one that fails first. Both properties the shape existed for are untouched: the entry still travels to `stash write --content-file <path>` as a **path** rather than a shell-composed string, because a `cat > … <<'EOF'` heredoc is refused outright inside an isolated worktree and an inline argument would need every quote, backslash, and newline escaped; and the **five-deep ring is unchanged**, still rotated inside the verb, since a loop-computed path can never be allowlisted. `--consume` stays mandatory, for a different reason than before — a unique name per run is precisely the shape that accumulates under `~/.claude` if nobody removes it — and the verb's usage text and comment now say that rather than the superseded "it is why the path can be fixed". `skills/cp/SKILL.md` mirrors the change in its own terms, `docs/features/cp.md` records why the path is unique, and `commands/` was regenerated rather than hand-edited.
- **The first `Read` of a watched log is allowed, so "is the watch still live?" is a question you answer by reading.** The watched-condition denial fired on *any* `Read` of a file a watch was following, and the previous round's fix only improved its wording — it still said "a watch armed earlier is already following this log" to a session that had never seen the file's contents. One recorded session was refused three times in a single run, and each refusal cost the same turn twice over: once to be refused, once to reason about whether the watch had already ended before daring to reissue the read. The gate now asks the question it always meant to ask. A `Read` is a **poll** only when this session has already read that path *and* the file has not been written to since — both halves, checked against the transcript and the file's mtime, with `CHANGED_GRACE_MS` covering the same-second write-then-read. Everything else passes: the first look, and any look after the log actually changed. The look-up is deliberately broader than the whole-file `lastFullReadOf` the re-read gate uses — a `Read` of a slice counts, because the question here is not "are these bytes already in context" but "has this file been looked at once already", which is exactly what separates a first look from a poll. A refused or errored read delivered no bytes and so is not a look. The practical effect is that **the read itself is the cheap liveness check**: read once, see where the log got to, and if it has not moved the gate says so and hands back the bounded wait. `docs/specs/workflow-gates.md` carries the narrowed rule and a row for the reasoning the old denial provoked.
- **`PreToolUse` refuses hand-rolled post-merge branch deletion and names `cleanup` in its place.** The `cleanup` verb shipped last round with the squash-merge case handled, and prose alone did not hold: one recorded session ran `git push origin --delete <branch>` (failing on a ref GitHub's auto-delete had already taken) and then `git branch -d <branch>` (failing with "not fully merged", because a squash merge puts none of the branch's commits on the target) — the exact pair the verb exists to answer, in sequence, in one run. A prior fix explicitly deferred gating it; it recurred, so it is gated now. Both halves are refused by shape and the denial names `my-command-tools cleanup --branch <branch>`, explaining which of `already-absent`, `squash-merged`, and `not-merged` it would have reported and that `not-merged` is the one refusal that still means something. **`git branch -D` and `--delete --force` are deliberately left alone**: `/merge-deps` prescribes the forced delete to make a branch be recreated from origin, and a gate at odds with the repo's own docs is worse than no gate. Anything the shell computes — a glob, a flag's value, an unreadable branch word — is not judged, and the standing one-refusal-per-subject rule means the same branch is never refused twice.

- **`my-command-tools stash` owns `/cp`'s ring, so the rotation is one allowlistable command instead of a snippet.** It registers beside `commit`/`concepts`/`doctor`/`identity`/`pr`/`prs`/`scope`/`state`/`verify`/`worktree` and prints JSON on stdout like every other verb. **The motivation is the allowlist, not tidiness** — the same reasoning that moved the concept store into `concepts` and heredocs into `commit --message-file` / `pr --body-file`: `Bash(my-command-tools:*)` is already allowlisted in `src/hooks/settings-fragment.json`, so a verb call is one approval-free command a gate can read, while an inline snippet is a different string every run and can never be allowlisted. `stash write --content-file <path>` rotates the ring, installs that file's bytes as the newest entry, and copies them to the clipboard; **the entry arrives as a path and never as an argument**, so a prompt containing quotes, backslashes, or newlines cannot be corrupted by shell quoting. `stash restore [<slot>]` puts a slot back, `stash list` reports the ring, and `--no-clipboard` does the file half only. The ring lives under `$CLAUDE_CONFIG_DIR` (or `~/.claude`) and nowhere else — nothing is written into the repository the session happens to be in. Nine unit tests sit beside the other verb tests, each pointing `CLAUDE_CONFIG_DIR` at a throwaway directory and passing `--no-clipboard`, so a test run never touches the developer's real stash or takes over their clipboard.

- **One installable `my-command-tools concepts` verb replaces the concept-store snippet that was pasted into every command that reads or writes the corpus.** The same ~40-line `node -e` block — read `CONCEPTS_URL` and `CONCEPTS_TOKEN` off `process.env`, fetch the hosted Worker, retry once on a `5xx`, print exactly one status line — sat in `src/commands/lookup.md`, `teach.md`, and `learn.md`, and each of those mirrors into a generated `commands/<name>.md` and a hand-written `skills/<name>/SKILL.md`, so the logic existed in **nine places** and any correction had to land in all nine. **The motivation is the allowlist, not tidiness.** `src/hooks/settings-fragment.json` already allowlists `Bash(my-command-tools:*)`, so a toolkit verb runs with no approval round-trip, while an inlined `node -e` block is not allowlistable — every `/lookup`, `/teach`, and `/learn` run paid an approval, and inside an isolated worktree the heredoc shape is refused by the `PreToolUse` gate outright, which is the environment `/task` puts every run in. The new `src/toolkit/verbs/concepts.mjs` registers beside `commit`/`doctor`/`identity`/`pr`/`prs`/`scope`/`state`/`verify`/`worktree` and carries three subcommands, each printing **one machine-readable status line on stdout and always exiting `0`**, because a caller must treat an unreachable store as a stated skip rather than a stop. `concepts lookup <term> [--field <field>] [--limit <n>]` is the three-outcome gate with its vocabulary preserved verbatim — `term hit:` followed by the stored sentence unmodified, `field hit:` followed by one `- term [field] sentence` line per neighbour, or `miss:` with the cause appended when the corpus could not be read — running the fixed probe order (`/api/concepts/concept`, then `/api/concepts/search`, then `/api/concepts?field=` when a field was given) inside a single call. **An exact term match is compared trimmed and without case, wherever the row was found, and a result that merely mentions the query stays a neighbour**, never promoted to a term hit to save a run. That "wherever" covers the field listing as well as the search: a concept the term probe missed and BM25 did not rank still *is* the exact term, and reporting it as a neighbour would invite `/teach` to name it a second time — the duplicate the gate exists to prevent. `concepts save` writes a record, and `concepts count <term> <skill>` re-reads the stored record, appends the skill, carries `notes`, `tips`, `sources`, and `surfacedSkills` forward unchanged, and posts a new version — never recording `find-skills`. `--json` returns the structured result where a caller wants fields rather than a line.
- **The secret is kept out of every observable surface, and the record travels as a file path for the same reason.** The verb reads both variables from `process.env` inside its own process: the token is never accepted as an argument or a flag, never echoed, never written to a file, and never put in a URL. **A record being saved is read as JSON from the path given to `concepts save --record-file <path>`**, with `save` still reading stdin when no path is given so a real pipeline keeps working. Either way no field of the record — not the sentence, not a tip, not a source — ever reaches a command line, which also means a sentence carrying quotes or backslashes cannot corrupt the record and no separator has to be reserved out of a tip. **`--record-file` rather than stdin is what the commands prescribe**, because it is the same shape `commit --message-file` and `pr --body-file` already settled on: write the JSON with the `Write` tool, hand over the path, and put no shell in between. Composing the record inline means a heredoc, and the `PreToolUse` gate refuses that shape inside an isolated worktree — which is the environment `/task` puts every run in, and therefore the environment the old `<<'CONCEPTEOF'` block in `/teach` would have been refused in. `IDEAS_URL` / `IDEAS_TOKEN` are read first with `CONCEPTS_URL` / `CONCEPTS_TOKEN` as documented fallbacks, matching what `/work` already describes, since ideas and concepts are one dataset behind one Worker — so `/work` can move onto this verb later without a second address scheme. A unit test asserts the token never appears in the child's `argv`, alongside tests for all three outcome lines and both unset-variable cases.
- **The environment contract is stated once, in `src/shared/concepts-store.md`, and included by the three commands that need it.** `/lookup`, `/teach`, and `/learn` pull it in with an `include-block`, so the never-print-the-token rule, the `IDEAS_*`/`CONCEPTS_*` precedence, the one-line-and-exit-`0` contract, and the "an unreachable store is a stated skip, never a stop" rule exist in one file rather than in three that drift. Each command's inlined block is gone, replaced by the one-line toolkit call and the reading of its output; `commands/` was regenerated rather than hand-edited.
- **Both installers ship the verb and neither writes a token.** `scripts/install-personal.sh` symlinks `src/toolkit` wholesale and the `npx` wizard copies it minus its tests, so the verb arrives through both paths with no extra step. What each gained is a **report**, not a write: they say only whether the address and token are both set, and when they are not, they print the two `export` lines for you to paste into your own shell profile. A wizard that wrote a token into `settings.json` or a dotfile would put a secret somewhere the user never chose and cannot easily audit, so it prints and stops.
- **Every read, claim, and mark against the hosted ideas ledger now goes through a store hook, and no command inlines a `node -e` block at the ledger any more.** Four hooks ship in `src/hooks/` beside the workflow gates and install to `~/.claude/my-command/hooks/`: `ideas-read.mjs`, `ideas-add.mjs`, `ideas-claim.mjs`, and `ideas-mark.mjs`, covering every `/ideate` and `/work` call at the ledger. **The reason is the permission boundary, and it is worth more than the tidiness.** `src/hooks/settings-fragment.json` allowlists each hook **by name**, so a ledger call runs without an approval round-trip, while an inlined `node -e` block is not allowlistable — it is a different string every time — and cost one round-trip on every read, every claim, and every mark. The entries are written twice on purpose: once as `{{HOOKS_DIR}}/<script>.mjs`, which the installer already substitutes to an absolute path across the whole fragment, and once as the literal `~/.claude/my-command/hooks/<script>.mjs` form a command doc actually writes. They are scoped per script rather than by an over-broad `Bash(node:*)`, which would allowlist every inline script in the suite to buy four calls.
- **One library decides the address, the retry, and the shape of the status line, rather than each call site re-deciding them.** `src/hooks/lib/store.mjs` resolves `IDEAS_URL` / `IDEAS_TOKEN` **with `CONCEPTS_URL` / `CONCEPTS_TOKEN` as the documented fallback** — the fallback `/work` already described, matched rather than reinvented as a second address scheme. **Both halves are read from `process.env` inside the hook's own process**: a token is never an argument, never a flag, never echoed, never written to a file or a dotfile, and never on a command line, where it would reach both the transcript and the shell history. The retry sits **inside** the call — one repeat on a network error or a `5xx`, replaying the identical request — so recovering by re-running a whole command is named as the mistake it is rather than left to be discovered.
- **Every hook prints at most one machine-readable status line and always exits 0**, so a caller reads the line and never the exit code. `read:`, `added:`, `claimed:` and `marked:` are the successes; a line beginning `not ` carries the cause after the colon — which variable was unset, the HTTP status with its short reason, or the network error. **An unreachable ledger stays a stated skip rather than a stop** on the terms the concept store already set, except in `/work`, where the read is a **stop** because building without the ledger risks duplicating claimed work. `ideas-read.mjs` and `ideas-add.mjs` print their JSON on the lines *after* the status line, so an empty ledger and an unread one can be told apart. `/work`'s claim step changed shape and the doc says so outright: the CLI signalled a refusal with a non-zero exit, the hook does not, so **`claimed:` on the first line is the permission to build and every other line is a refusal.**
- **What the hooks deliberately do not do is re-implement the Worker.** `--available` is passed straight through and answered server-side, so the six-hour claim TTL and the staleness rule are not duplicated here — two implementations would disagree the first time either changed. `ideas-add.mjs` takes a **path to a JSON file** rather than an inline array, because a rationale carries newline bullets and composing that on a command line is exactly the heredoc shape this repo's gates already refuse — the same reason `commit --message-file` and `concepts save --record-file` take paths. `ideas prompt` stays on claude-proxy's CLI and is named in the docs as the one ledger-adjacent call left there: it composes a brief client-side from the export rather than making a store call, so hooking it would mean reimplementing claude-proxy logic. `/improve` needed no change at all — after the `/work` split it makes no ledger call.
- **The concept store is deliberately not touched here.** The `/teach` write path and the `/learn` install-count path were in this change's original scope, but `my-command-tools concepts save` and `concepts count` landed first and cover them, so the two concept hooks were dropped rather than shipped as a second implementation of the same two calls. The ledger keeps its own hooks because the `concepts` verb does not address it, and `lib/store.mjs` retains the `CONCEPTS_*` fallback so the two stay reachable through one configuration.
- Tests live beside the existing gate tests in `src/hooks/store-hooks.test.mjs` and run a real HTTP server on a loopback port, covering **each hook's success line, its unset-variable line, and its error-status line**, plus the exit-0 contract on an unreachable ledger, the bearer header, the token never reaching stdout, and the two refusals spent locally rather than as a round trip (a status the ledger does not accept, and a `rejected` mark with no reason). The hooks are executed **by path** rather than through `node`, so the executable bit is part of what every case asserts — and `src/my-command.ts`'s `HOOK_SCRIPTS` list now carries all four, because a lost mode bit turns a ledger call into a "permission denied" that reads as an unreachable store. **`scripts/check-commands.sh` also asserts all eight `permissions.allow` entries are still in the fragment**, in both the `{{HOOKS_DIR}}` and the literal `~/.claude/my-command/hooks/` form: the allowlist is this change's entire point, nothing else inspects it — the existing fragment check and `hooks-status.mjs` both read only `hooks` — and a dropped entry costs an approval prompt per call while every gate stays green.

- **`/manage` orchestrates one multi-part goal across the commands that already exist, and implements none of it itself.** The gap it fills is narrow and real: a goal with three separable pieces has three commands that each know how to do one of them, and nothing that decides which commands, on which branches, in which order. `/manage` owns exactly that — planning, routing, dependency ordering, batching, failure handling, synthesis — and **never branches, commits, opens a PR, merges, or tears down a worktree**, because `/task` already owns that pipeline end to end and a second owner for one branch is how a run corrupts itself. **Its unit of delegation is one invocation of one existing command and nothing smaller**: "have a subagent edit these three files" is not a unit, since that subagent has no branch, no verification, and no PR. **The delegate defaults to `/task`**, which stops at an open PR and leaves a human the merge; `--delegate god` merges without asking and must therefore be typed, because this command **multiplies whatever it delegates** and eight unattended merges out of one invocation is a different risk from one.
- **The scheduling rules are stated with their reasons, because each of them is a failure someone already paid for.** **Every parallel unit gets its own branch and its own worktree**, with the names assigned in the plan **before** the fan-out rather than derived independently by two delegates from similar criteria — two `/task` runs sharing a branch means the second one's commits land on the first one's half-finished tree and neither PR describes what it contains. **Units whose file scopes overlap are sequenced however independent they look**, so "what files does this unit touch" is a planning field rather than a note, and a clean textual merge is never evidence of independence. **Independent units go out as one parallel batch** — multiple `Agent` calls in a single turn — and running them one after another is named outright as the mistake the command exists to prevent, because it is the shape a run falls into by default and it reports success either way. **Three to eight units**: below three there is nothing to orchestrate, and above eight the plan stops being holdable, so a larger goal is dispatched in successive waves rather than fanned out at once. **The topology is a star, not a mesh** — peer messaging costs roughly **2.4x–2.7x** the tokens of the equivalent fan-out (about 150K vs 400K for a three-agent review, 500K vs 1.2M for an eight-agent feature) and earns that only when workers must negotiate a cross-cutting concern mid-flight, which these workers cannot, since each runs a self-contained command in its own worktree and the concern was already resolved into lanes; `--mesh` is the named escape hatch and is off by default. **Delegate prompts stay minimal**, because every delegate is already self-contained through its own file and restating the plan into each subagent competes with the command's own instructions.
- **The dependency graph lives in the harness task list, and there is deliberately no second store.** One `TaskCreate` per unit, then `TaskUpdate --addBlockedBy` **after** every task exists, since a link needs both ids. The task list is live session state that survives a compaction and this prompt is not — the same reasoning the closing-turn anchor already runs on, reused rather than reinvented — so no progress file and no status dashboard were built. **Failure is isolated rather than fatal**: one failed unit does not cancel its siblings, the cause is recorded, **at most one retry** is spent, and the rest carries forward, because four successes and one stated failure is a good outcome while dying on the first failure throws away work that is already done. **The replanning loop is bounded at one round**, since an orchestrator that replans until everything succeeds does not terminate. And **synthesis is mandatory** — a subagent's report is never visible to the user and is never the run's outcome, which matters more here than anywhere because the whole run is subagents — so the closing turn names, per unit, the command that ran, the branch, the PR, and the outcome. The resulting branches are **never batch-merged onto `main`**: a run meant to land as one thing goes through an integration branch and one PR.
- **`fb` is the one delegate that cannot cut a branch, and the command says so rather than letting a run find out.** `/fb` applies feedback to the branch it is already on, or with `--target` to one that **already exists**, so an `fb` unit's branch is named by the goal rather than by the plan and the unit is dispatched as `/fb --target <that branch>` — handing it an invented `<type>/<kebab-summary>` gets either a branch that does not exist or the orchestrator's own branch, which is the collision the wave batching exists to prevent. A goal that cannot name an existing branch for an `fb` unit is a **stop**, not a new branch. `/fb` also takes no `--add`, so an `fb` unit is dispatched without the forwarded list and the omission is reported in the plan.
- Flags: `--delegate task|god|fb` (default `task`), `--parallel <n>` (default 3, hard cap 8), `--sequential`, `--dry-run` / `-n`, `--mesh`, and `--add` / `-a` forwarded to every `task` and `god` unit the way `/god` already forwards it.

### Changed

- **`/cp` calls the stash verb instead of prescribing a loop, with its documented behaviour unchanged.** Step 3 is now two calls rather than three — `Write` the composed line to `~/.claude/cp-compose.txt`, then hand that path to `my-command-tools stash write --content-file <path>` — and `--again` is `my-command-tools stash restore [<slot>]`. Everything the command promised still holds and is now a property of the code rather than a rule to recall: the ring is five deep with the oldest dropped, the stash is written on **every** platform while only the clipboard sink is detected (`pbcopy`, `wl-copy`, `xclip -selection clipboard`, `clip.exe`, in that order, inside the verb), a missing stash is **reported plainly rather than copied as an empty clipboard** — the verb leaves the clipboard alone, since clearing it is worse than whatever is on it — and the stash still lives only under `~/.claude` with nothing written into the repository the session is in. `skills/cp/SKILL.md` mirrors all of it, `commands/` was regenerated with `./scripts/build-plugin.sh` rather than hand-edited, and `docs/features/cp.md` records why the ring is a verb.
- **The worktree-isolation refusal is documented as the harness's, not this repo's, because it is not ours to narrow.** The intended third change here was to scope `pre-tool-use.mjs`'s isolation check to git operations and repo-relative writes, with an explicit safe-prefix allowance for `~/.claude/` and `$CLAUDE_JOB_DIR/`. **There is no such check to scope.** Neither the refusal's wording nor the rule it states appears anywhere in this repository — `src/hooks/pre-tool-use.mjs` has no worktree-isolation gate, and the heredoc refusal it *does* carry describes that external mechanism rather than implementing it. The sentence is emitted by Claude Code's own built-in gate, confirmed by reproducing it against a live Bash call from inside this run's worktree. What is available from this side is rung 4, which is what shipped: the `stash` verb means `/cp` no longer sends a shape that has to be judged, and the new invariant means no other command can start. `docs/specs/workflow-gates.md` records the finding beside the `$CLAUDE_JOB_DIR` entry, which is the same lesson from the other direction — that gate *was* ours, it refused the path the harness prescribes, and it was deleted rather than softened. Neither answer is teaching a parser to unroll loops.
- **`/manage` now takes the whole flag surface a delegated `/task` run accepts, so a flag meant for the units is typed on the invocation instead of described in the goal.** `--add` / `-a` was the only flag it forwarded; `--draft` / `-d`, `--sub` / `-s`, `--base <branch>`, and `--here` / `-h` had no pass-through at all, and since `/manage` composes each unit's invocation itself in its plan, the only way to ask for one was a sentence inside the goal text — which the planner reads as prose and nothing guarantees it honours. **The pass-through is stated the way `/work` already states its own**: anything `/task` recognizes and `/manage` does not own is forwarded to every `task` and `god` unit, with `/task`'s own Flags section as the list rather than a copy of it that can drift. `--add` keeps its comma-separated `<command> <prompt>` shape exactly, and is no longer special-cased at dispatch — it is one member of the forwarded set.
- **A delegate is never handed a flag it cannot parse, and the drop is reported rather than silent.** The rule the `--add`-on-an-`fb`-unit omission was always a case of now covers the whole set: each forwarded flag is compared against the **resolved** delegate's own Flags section, and one it does not document is **dropped from that unit's invocation and named in the plan** — per unit, per flag, with the delegate that cannot parse it. Two tempting alternatives are ruled out by name, because both fail quietly: passing it anyway does not error, since a delegate reads an unknown flag as criteria and `-d` becomes a word in the feedback request; and re-expressing it as a sentence in the criteria reintroduces the exact prose constraint the flag replaced, this time hidden inside text that reads like scope. `task` drops nothing. `god` drops nothing either but is two special cases: it adds `--sub` to its own `/task` call regardless, so forwarding that is redundant rather than dropped, and **`--draft` under `--delegate god` is a stop in Step 1** rather than a per-unit drop, since `/god` rejects a draft outright and dispatching it would be N units each stopping on their own. `/fb` documents `--target` alone, so **no forwarded flag survives an `fb` unit** — every one is dropped and listed.
- **A root `--base` moves where the branch plan starts without flattening the stack.** Step 1 named every unit's branch against `defaultBranch`, while a stacked unit is based on the branch of the unit it depends on and never on `main`, so a forwarded `--base` had two incompatible readings. It resolves as the **root base**: it replaces `defaultBranch` for the units at the root of the dependency graph — the ones waiting on nothing — and **a stacked unit keeps the base the wave batching gave it**. Cutting a stacked unit from the root instead would leave it without the interface it consumes and buy a conflict at merge time, which is the failure stacking exists to avoid. Each unit's base became part of the planning facts alongside its branch, and the plan prints it, so a root base and an inherited one are told apart before anything spawns. **`--here` is the other flag with a scheduling consequence**: it forces `--sequential` and collapses the branch plan, for the reason `/work` already gives — a fresh worktree per run is what makes same-repo concurrency safe, and `--here` removes exactly that — so the run yields one branch and one PR rather than one per unit, and says so.
- **Every forwarded flag is visible in the printed plan before a subagent exists.** `--dry-run` / `-n` prints, per unit, the full invocation Step 4 would compose with its flags in order, the branch and the base it is cut from, the lane, what it waits on, and every flag dropped for it; then, for the run, the resolved delegate, the waves, the `--parallel` cap with any clamp, and any flag that changed the schedule rather than a unit. Step 4's prompt-composition shape carries the surviving set instead of a hardcoded `--add <forwarded list>`, and the closing synthesis names the flags each unit actually carried plus every drop — a flag typed on the invocation and silently missing from a unit's run is otherwise indistinguishable, in a report of outcomes alone, from one that was honoured. `commands/manage.md` was regenerated rather than hand-edited, and `skills/manage/SKILL.md` and `docs/features/manage.md` carry the same rules in their own vocabulary.
- **Every behavioural claim about the concept store is unchanged — only where the code lives moved.** The three lookup outcomes, the append-only store whose reads resolve the newest version, the ULID-derived idempotent write returning `201` for new and `200` for a replay, the omit-an-empty-optional-field rule, `find-skills` never being recorded in either skill list, the never-print-the-token rule, and the unreachable-store-is-a-stated-skip rule all survive verbatim in the verb and in the shared include. `docs/features/lookup.md`, `teach.md`, and `learn.md`, and the README's store section, now describe the verb where they described the snippet. **`/work` is deliberately not migrated in this change** — it reads `IDEAS_URL` with `CONCEPTS_URL` as its fallback and is the fourth caller, but moving it is its own change and is noted as the follow-up.

### Fixed

- **A command invoked inline inside another no longer ends the parent's turn and strands the rest of its pipeline.** `src/shared/closing-turn.md` told every command to end its run with one message carrying text and **zero tool calls**, and in Claude Code a text-only assistant message ends the assistant's turn and hands control back to the user. On `/task`'s default (non-`--sub`) path, where Step 3 runs `/clean` and then `/pr` inline in the same session, each child's closing turn therefore terminated the whole turn: `/clean`'s `RETURN /clean` message returned control before `/task` could invoke `/pr`, and `/pr`'s returned control before `/task`'s worktree teardown and its closing report ever ran. **Observed end to end on this repo's PR #90** — both of `/task`'s remaining steps were stranded, and `src/hooks/stop.mjs` fired "This run has not recorded its outcome" mid-pipeline on top of it, demanding the very text-only turn that does the stranding. The gate was arguing for the defect. **Fixed once in `src/shared/`, so all twenty-five commands inherit it** rather than per command.
- **The rule is now stated per invocation case, and the snippet says how a run tells which case it is in.** Three cases, unambiguous: **outermost** — the user invoked it directly, as the prompt the turn is answering — closes in a text-only turn; **nested inline** — another command invoked it with the `Skill` tool in this same session, as a step of that parent's own pipeline — **hands back without spending a text-only turn**, emitting its report and its return marker as text in the same assistant message that carries the parent's next tool call, so the turn continues into the parent's next step; and **subagent** — dispatched with the `Agent` tool, via `--sub` or a delegated unit — still closes in its own text-only turn, because its final message is a report *to* the parent session rather than a turn *in* the parent's conversation, so nothing of the parent's is queued behind it and spending the turn strands nothing. `src/shared/closing-turn-anchor.md` follows: a nested run anchors "hand back to the invoking command in its next turn" rather than the text-only close, since an anchor that tells a nested run to close is an anchor for the failure.
- **The marker contract is untouched, which is the constraint the whole change had to work within.** `RETURN /<command>` is still written **exactly once**, still alone on the last line of the message that hands control back, still carrying whatever namespace prefix the invocation carried. Only the message it rides differs — a text-only close, or a handback riding the parent's next call — and it is never weakened, deferred to a later message, or dropped because the turn continues, because nested-span attribution in claude-proxy's commands eval depends on it being exact. `docs/specs/run-markers.md` gained the three-case table and `docs/specs/workflow-gates.md` an "Only the outermost run owes an outcome" section and invariant.
- **`src/hooks/stop.mjs` reads the same distinction off the transcript rather than being told it.** Two exemptions, both checked **before** `alreadyDenied` so a legitimate handback never spends the one-denial-per-subject budget a later real abandonment needs: a **handback is not an ending** (the last turn carries a tool call *and* text whose last line is a real `RETURN /<command>` marker — the angle-bracket placeholder the snippet is written with deliberately cannot match, so merely loading a command file has handed nothing back), and a **pipeline mid-flight is not an ending either** (`nestedRunOpen()` counts `Skill` calls since the last real prompt against markers seen since then, counted rather than paired because the parent issues the call and the child writes the marker, and one handback message carries the child's marker beside the parent's *next* `Skill` call). A **genuinely abandoned outermost run is still refused**, and the refusal now says outright that the outcome is owed there even if a nested command already reported. Two misses are accepted deliberately on the standing rule that a false denial costs more than a missed violation: an outermost run abandoned *while* a nested command is open, and one whose last message happens to carry both a tool call and a trailing marker — neither is separable from the legitimate case on the evidence, and no gate guesses. A subagent run needs no exemption at all, since `SubagentStop` is not registered and a dispatched run never reaches this gate.
- **All three surfaces are gated, the way invariants 6 and 15 already gate the closing turn and the return marker.** New invariant 18 in `scripts/check-commands.sh` asserts the canonical snippet states the handback and names both the `Skill` and `Agent` tools as how a run tells its case, that every generated `commands/<name>.md` carries the expanded rule (so the include actually reached the copy the plugin ships), that every one of the twenty-five hand-written `skills/<name>/SKILL.md` translations mirrors it — flattening whitespace first, since the phrase straddles a hard wrap — and that `stop.mjs` still reads both `returnMarker()` and `nestedRunOpen()`, so the gate cannot drift back into contradicting the prose beside it. Tests beside the existing gate tests in `src/hooks/hooks.test.mjs` cover the nested handback, the namespaced handback, a pipeline with a child still open, the **still-abandoned outermost run after both children returned**, a marker in earlier prose that excuses nothing, the placeholder never matching, and an open nesting counted only within the current task. No command's steps or flags changed.

## 2026-08-10

### Added

- **`/work` builds the ideas a human accepted, and it is now the only command that touches the ideas ledger.** `/improve` carried two inputs with two evidence standards — suggestions counted from transcripts, and ideas invented by `/ideate` and signed off by a person — and the seam between them had grown an entire apparatus whose only job was arbitrating which half of the command was allowed to run: the idea track was opt-in, an idea flag suppressed the judge and suggestion tracks outright, `--range` and `--regressed` became inert, and the report had to say the suggestion track was *deliberately skipped* rather than empty. **Splitting the command deletes all of it**, because after the split there is nothing to arbitrate: `/improve` reads the suggestions store and `/work` reads the ledger, no flag makes either do the other's job, and neither writes to the other's store. Everything that made the idea track trustworthy **moved rather than being rewritten** — the claim-before-dispatch protocol with the branch name as the holder, one idea one branch one PR, wave scheduling with its two conflict tests (file-scope overlap inside a repo, and a dependency the idea's own rationale states), the rule that **a clean textual merge is never evidence of independence**, explicit lanes for every concurrent subagent, `--here` forcing serial dispatch, marking each shipped idea against **its own** PR, and releasing every unshipped claim in the closing turn. **Selection is the genuinely new part and the point of the split.** `--idea <slug>[,<slug>...]` / `-i` names slugs, never titles; `--area <area>[,<area>...]` / `-A` takes every available idea filed under those areas, in the ledger's own free-text vocabulary, with `Unfiled` selecting the area-less legacy rows; the two together are a **union** and the report says which selector brought each slug in; and **no selector at all means every available idea for the repo**, which is what the old bare `--ideas` did — `--ideas` is gone rather than renamed, and is not carried over as an alias. `--repo <slug>` overrides the repo filter and is a **remote slug, never an absolute checkout path**, because the ledger is device-wide and a path names a different thing on another machine. `--max <n>` (default 5) caps only a **no-selector** run and otherwise **stops**, reporting the available count and the per-area breakdown, since an explicit selector means a person named the work. Two stops are stated outright and one skip deliberately is not: **an unresolved `--idea` slug is a stop**, reported with the status it actually holds, carried over verbatim from `/improve`; **an `--area` naming an area that does not exist is a stop too**, because an area typo selects nothing and looks identical to an area with no available ideas, so the run would quietly do nothing and report success — the stop names every area that does exist with its available count, while an area that exists and is empty is an honest empty selection; and **a slug held by a live claim stays a skip with a named holder**, because nothing is wrong and the answer is to wait. Because `ideas list --area` matches exactly one area, a comma list is filtered in the command against **one unnarrowed read** rather than by looping the CLI — which is also the only read that can tell an empty area from a misspelled one.
- **Three corrections were folded in while the material moved, each of which had gone stale when the ideas ledger became hosted.** The **tier-1/tier-2/tier-3 ledger waterfall is deleted**: the hosted ledger has **no local fallback by design**, precisely so an unconfigured device cannot keep a second divergent ledger that looks complete (claude-proxy's `docs/adrs/0006-host-the-ideas-ledger.md`), so `/work` reads one store and there is nothing to fall through to. **Step 1 resolves the ledger's own configuration rather than only claude-proxy's**: `IDEAS_URL` and `IDEAS_TOKEN` address the `operator` Worker, with `CONCEPTS_URL`/`CONCEPTS_TOKEN` accepted as a fallback for each since ideas and concepts are one dataset behind one Worker and one token, and a device with neither **stops naming both variables** in the same shape as the existing `CLAUDE_PROXY_STORE` stop — which is kept, because the `ideas` CLI still runs out of the claude-proxy checkout. And **each idea's brief is composed with `ideas prompt --slug <slug>` rather than re-derived**: `ideaTaskPrompt` already assembles the title, the rationale in `/ideate`'s fixed bullet order, every citation, the claim lines, and the human's `comment` — quoted verbatim as build criteria that **override the rationale where the two disagree** — so re-deriving per subagent is how two briefs for one idea drift apart, and reading `comment` is the only way a signer's build instruction reaches the subagent at all. Only the **lane** and the **base branch** are still composed in the command, because those are facts about this run's schedule rather than about the idea.
- **Every command now writes the two markers claude-proxy's commands eval already parses, so a run's steps and a nested run's span are read from what the run stated rather than guessed from its prose.** The eval places every node of a transcript against the command's declared steps, and until now it had nothing to read but narration: it matched a step number wherever the agent happened to mention one, ranked the match by how early in the line it fell, and had **no** signal at all for where a nested run ended — so each child ran to the next nested invocation, or to the end of the transcript for the last one, and a `/clean` nested under a `/task` was charged with everything `/task` did after `/clean` returned. Both halves are one missing emitter, and both are now emitted from `src/shared/`, which is what keeps twenty-one commands on one format. The new **`shared/step-marker.md`** is included by every command and says to open each step with `STEP <n>/<N>` on the first line of the message that enters it — `<n>` copied from the `## Step …` heading itself, fraction and all, and `<N>` the count of those headings, which is the same number the eval reports as `stepsDeclared`. The **return marker needs no new include**: it rides `shared/closing-turn.md`, which every command already ends through, so the closing turn's last line is now `RETURN /<command>` — the one place a nested run provably passes on its way out, which is what makes the span exact rather than approximate. `check-commands.sh` gained invariant 15 for both: the include in every command, and the marker's text in the closing turn.
- **One include per command rather than one per step, and placeholders rather than examples.** The snippet states the rule and carries no literal marker, so a command with nine steps holds one directive, two commands cannot drift to two formats, and a step added tomorrow is marked by the rule already present. A command with **no** `## Step …` headings has nothing to anchor against and writes no marker, and still carries the include for exactly that reason. The snippets write `STEP <n>/<N>` and `RETURN /<command>` with the angle brackets intact on purpose: a command file is itself part of a transcript, so a worked example with real digits in it would anchor a step in every run that merely loaded the command.
- **Two limits, both stated rather than papered over.** The **prose anchors stay** — every transcript recorded before the markers existed has none of them and must keep reading as it does, so the eval matches the marker first and still falls back to a narrated step number, and the step snippet requires the step to be named in words as well. And **a run that ends abnormally never reaches its closing turn**, so it writes no return marker and its span still runs to the end of the transcript: the marker makes the normal exit exact and leaves the abnormal one exactly where it was. Netting a nested run's cost out of its host's total is **unblocked by this and not done here** — that decision belongs to claude-proxy's index, and it needed the child's span to have a known end, which it now has. Both formats are written down in the new [`docs/specs/run-markers.md`](docs/specs/run-markers.md) so the reading side can be built against them.
- **`/lookup` reads the hosted concept store before a term is named, so a concept the corpus already holds is never named a second time.** `/teach` has written every settled concept to that store since it shipped, and nothing in this repo ever read one back — so a concept settled in March is settled again in August under a second wording, and the two sentences disagree while both claim to be the one term for the concept. `/lookup` is the **gate** that closes that, and it is **read-only: every request is a `GET`, and it writes nothing to the store, ever.** A lookup is not a search — it ends in exactly one of **three outcomes**, and the outcome rather than the row count is what a caller acts on. An **exact term hit** returns the stored Simplified Technical English sentence **verbatim**, copies it, and **stops**, because that sentence is the entire deliverable `/teach` exists to produce and re-deriving it is precisely the second wording the one-term-per-concept rule forbids. A **field hit with no term hit** returns the neighbours **as context for the naming step, never as the answer** — a stored concept in the same field is what `/teach`'s first naming source, an installed skill covering that field, is trying to approximate. A **miss** says so and exits, and **a miss is the only outcome that authorizes a `/teach` at all**. Only an exact `term` match, compared trimmed and without case, is the first outcome; a full-text result that merely mentions the query is a neighbour and belongs to the second, so search is a *means* of resolving a term hit rather than a fourth outcome, and a near miss is never promoted to save a run. The store resolves in a fixed order and the first probe that answers decides: `GET /api/concepts/concept?term=`, then `GET /api/concepts/search?q=`, then `GET /api/concepts?field=` when `--field` was given. Both halves of the address come from the environment exactly as the save side reads them — `CONCEPTS_URL` and `CONCEPTS_TOKEN` — read from `process.env` inside a `node` process, so the token never reaches a command line, a transcript, or the shell history. **An unreachable store is a miss with a stated cause, not a stop**, on the same terms `/teach` already sets for the save side: the run names which variable was unset, the status code and short reason the store returned, or the network error. That line is load-bearing rather than housekeeping, because a corpus that holds nothing and a corpus that was never read produce the same outcome, and only the second one means a following `/teach` may duplicate a stored term. **The placement is the point.** The gate sits at `/teach`'s new step 1.5 — after the field is placed, **before the naming step, never after it** — and **replaces the unconditional re-derivation the command used to open with**, because past the naming step the term has already been invented and the duplicate already exists. Flags are `--field` / `-f <field>`, which scopes the neighbours, and `--limit` / `-l <n>`, which caps how many are listed.
- **`/learn` leases a skill for one task and gives it back, and counts the install on the concept record `/teach` already writes.** `/teach` names the skills a concept belongs to and is forbidden from installing any of them, so the last mile — install it, use it, remove it — was done by hand every time or not at all. `/learn` is that last mile, and it takes the install as a **lease** rather than as an installation: the run records the skill, the concept it came from, and the task it was installed for, then removes it on the way out. **The removal rides the closing-turn anchor these command files already carry**, so a run that gives up, is refused, or hits a failing gate returns the skill instead of leaving it behind — the same release path `/improve` settled for an idea claim, **reused rather than invented**, and the thing that makes a temporary install trustworthy enough to be the default. **The removal is conditional on this lease having done the installing**: the probe (`npx skills list -g --json`) runs *before* the install rather than after it, so the lease records whether the install was real or a no-op, and **a skill the user already had is never removed** — not on a failing task, not on a refusal, not for tidiness. **What it declines to add is a download counter, and that is the part worth having on the record.** `/teach` already writes `skills` and `surfacedSkills` per concept, and claude-proxy already indexes `field` and `skill` with a `concept_skill` table built precisely so a listing can group without unpacking every document, and no view reads them yet — so **an install is counted by writing the concept record `/teach` writes anyway**: one `POST` appends the leased skill to that record's `skills` and carries every other field forward, and "how often did we download this" becomes exactly the group-by that substrate was built for. A counter of this command's own would be a second answer to a question the existing columns already answer, and the two would disagree the first time either missed a write; the keep-or-discard threshold is therefore a **reading** question answered by a person on claude-proxy's concepts page, and this command maintains no number and issues no verdict. A **repeat** lease and a **no-op** install both still write a row, deliberately, because the row counts an install rather than a distinct skill. The `POST` re-reads the stored record inside the same call and writes it back with the skill appended rather than the run retyping the fields — reads resolve the newest version, so a version written without `notes`, `tips`, `sources`, or `surfacedSkills` would lose them for every later reader, and carrying them forward inside the call makes that mechanical rather than remembered; `find-skills` is never recorded, on `/teach`'s existing rule. **`/lookup` is the first step**, and its outcome decides what the rest of the run can do: a **term hit** hands over the record whose `surfacedSkills` name the candidate skills — the list `/teach` fills with skills a run *discovered* rather than applied, which until now had no reader — and whose row the count is written on; a **field hit** names the field for the search; a **miss** points at `/teach` as the way to create the record a future lease would count on. **Neither a field hit nor a miss stops the lease** — the skill is still found, leased, and returned, and only the count is skipped with the cause stated in one line, because an uncounted install is invisible to the group-by and a false count is worse than an invisible one. Three things the idea left open are decided here and stated as decisions. **The lease lives in the harness todo list**, as its own item immediately before the closing-turn item, because that list is the only run state a compaction carries forward — the same reason the anchor lives there; a scratch file was declined as a second place to look that only the todo list would ever remind the run to read, the duplicate-store mistake one scale down. **The task is identified by the branch** when there is one, read from `my-command-tools state` and tolerant of a run outside a repository, falling back to the task text — the same holder string an idea claim picks, and for the same reason, that it is the one identifier a later reader can check. **The flag surface follows its neighbours**: `--field` / `-f <field>` and `--concept` / `-c <term>` scope the lookup, `--skill` / `-s <pkg@skill>` leases a named package and skips discovery, `--keep` / `-k` makes the install permanent and says so, and `--dry-run` / `-n` reports the concept, the skill, and the lease while changing nothing. It writes no code and opens no PR, which is what makes it composable: `/task -a learn …` wraps the lease around an implementation, the way `/diagram` composes after `/pr`.

### Changed

- **`/ideate` and `/work` now point at the hosted ideas ledger, and the device-local file they described is gone from both.** (The repoint was written against `/improve`, which owned the ideas half at the time; the split above moved that half to `/work` and the repoint moved with it, so `/improve` carries none of it.) The ledger was `<logDir>/ideas.json`, a file per machine, behind a three-tier waterfall that fell through to the surveyed repo's own `docs/ideas.md` and then to `~/.claude/ideas/<repo-slug>.md`. It is now an **append-only event log** on the existing `operator` Cloudflare Worker over D1, reached with **`IDEAS_URL`** and **`IDEAS_TOKEN`** — claude-proxy PR #193, recorded in that repo's `docs/adrs/0006-host-the-ideas-ledger.md`. This is the deliberate **second step of that ADR's three-step sequence**: the service shipped first, these command files are repointed and synced to every device second, and only then does claude-proxy retire `logs/ideas.json`. Nothing here deletes a local ledger file, on purpose — retiring it belongs to claude-proxy and only after every device carries these commands. `pnpm --filter server ideas` is now a **client** of the hosted store rather than the owner of a file, so its verbs take **no `LOG_DIR`**; that variable still belongs on the `suggestions` verbs, which do read the proxy's logs. **All three tiers are gone and there is nothing to fall through to**, so neither command reads, writes, or reconstructs one.
- **An unconfigured device now REFUSES every ideas read and write, loudly, and both commands surface that as a setup problem rather than routing around it.** With `IDEAS_URL` or `IDEAS_TOKEN` missing there is no fallback, and **that absence is the design rather than an omission**: a device answering out of its own copy would keep a second ledger that looks complete from the inside, diverges from the shared one, and re-proposes the ideas the shared one already rejected — the exact failure the dedupe key exists to prevent. `/ideate` reports the refusal naming both variables and stops rather than surveying anyway and reporting proposals nothing deduped; `/work` stops the same way rather than building against a set it could not read. Neither retries it. Both also note that the same operations reach the store over MCP as **`ideas_list`** (with an `available: true` argument), **`ideas_add`**, **`ideas_claim`** and **`ideas_mark`**, which is what an agent in a cloud box with no checkout uses. For `/ideate`, claude-proxy stays an **optional** dependency and its absence now costs the run the `ideas` CLI and the judge-note evidence source — **not the ledger**, which is hosted.
- **`/work` reads an accepted idea's `comment` as build criteria, and lets it outrank the rationale.** The `comment` is a human's own words about the proposal, written when they accepted it, so where it and the rationale disagree the comment is the ask and the rationale is the pitch that preceded it — the rationale was composed by `/ideate` from evidence, and the comment is the person who signed off saying what they actually want built. It goes into the brief verbatim, marked as the accepting human's words, because paraphrasing re-describes the ask in the voice of the thing it was correcting. **`ideas prompt --slug <slug>` is now preferred over hand-assembling the brief**: it composes the whole ready-to-paste `/task` brief from the entry — rationale, cited evidence, that comment, and the claim lines — and hand-assembly is precisely where the comment gets dropped, being the one field a reader skims past. The run adds its own scheduling (the lane, the branch name, a stacked idea's base) to what the verb returns rather than rewriting the part already composed.
- **A claim held by someone else exits non-zero, and `/work` now says to read that exit status.** The claim already went in before any code was written — the gap that let claude-proxy PRs #139 and #140 build the same accepted idea eleven minutes apart, one closed unmerged — and the missing half was what a run does with a refusal. **A zero exit is the permission to build and anything else is not**, so the run walks away and picks a different idea rather than reading a non-zero exit as permission; the store now spans every device, so the holder may be a run on a machine this one has never talked to, and there is nothing local to check the refusal against. **Re-claiming as the same `--by` is idempotent, and that is how a run attaches `--pr <url>` later** — a different `--by` is a different holder and is refused like anyone else's.
- **Both commands now read the store as shared across every device rather than device-local.** `ideas add` reports near-duplicate slugs under **`similar`**, computed **server-side against every machine's ideas including rejected rows**, so `/ideate` looks at those hits before insisting on a slug: a non-empty list is a collision even when the exact slug is free, it can name an idea proposed on a machine this one has never seen, and a near-duplicate under a different name defeats the dedupe key exactly as completely as a repeat of it. **A free slug is not a clear field.** The dedupe read is the whole ledger every run, still never narrowed by `--area`, and the area vocabulary it teaches the run is now every device's rather than this one's. A repo is still recorded as its git remote slug, now because a checkout path names a different thing — or nothing — on the next *machine* that reads the row. `/work` keeps reading `ideas list --available` rather than `-s accepted`, and `/ideate` keeps choosing an `area` for every proposal and citing `command-gap`, the one locator-less evidence source, only under `commands`. Mirrored in both Codex skills and both feature docs.
- **`/improve` is advice only.** It keeps the suggestion track, the judge precondition, the regression track with its escalation ladder, and the `suggestions defects` exit, and it loses every trace of the idea half: the `--idea` and `--ideas` flags, the ledger read, idea-sourced criteria, the claim protocol and wave scheduling, the shipped-idea marking, and the claim release in the closing turn. It also loses **every** "exactly one of the two tracks runs" / "an idea flag makes this run idea-only" / "skipped is not empty" hedge — those existed solely to arbitrate between two tracks in one command, and a hedge kept past the thing it hedged is prose a later run has to reason about for nothing. The frontmatter description and `argument-hint` no longer carry the idea flags, the Notes say in one line that ideas are built by `/work` and that this command never reads the ideas ledger, and the marking step states outright that **nothing is ever marked in the ideas ledger from here** — a suggestion ID is a `bucket/id` rather than a slug, and a run that writes to the other store records a claim about work it did not do.
- **`/ideate` now points at `/work` as what turns an accepted proposal into a PR.** Its "never invent" reasoning still refers to `/improve`, because that rule is about the suggestion track's trace and is unchanged; only the sentences about who *builds* an accepted idea moved.
- **The shapes the gates keep refusing are no longer the shapes the toolkit and the commands advertise.** PR #63 armed the gates and added the branches; the judged transcripts since show them firing and being obeyed on the very next call, every time. That is a working gate standing next to a standing affordance, so each occurrence still cost one refused round-trip. This removes the affordances instead.
- **`commit --message-file <path>` and `pr --body-file <path>` are what the usage strings now advertise.** A multi-line commit message or PR body composed on the command line is a heredoc, and a heredoc composing a file is refused wholesale inside a worktree — which is where both verbs are called from. The file form pairs with the tool the refusal already names: write the prose to a path, pass the path. `--message -` and `--body -` still read stdin for a real pipeline. `/task` and `/pr`, their Codex skills, and the heredoc denial's own suggested alternative all name the file flags now.
- **`my-command-tools identity` answers the two-account question for the `gh` calls that are not `pr`.** The device is logged in as `llevasseur` and `llevasseurKG`, and the recorded workaround was `GH_TOKEN="$(gh auth token --user <login>)" <command>` — an assignment wrapping a substitution, refused on shape, and a guess at a login the remote already states. The verb reads the owner off the origin remote, reports it alongside the active account, and `--select` runs the one plain `gh auth switch --user <owner>`. `shared/gh-identity.md` no longer demonstrates the refused line, which is where every hand-rolled copy of it came from.
- **`/cp` writes its clipboard stash with `Write` instead of a heredoc.** The command's own step 3 demonstrated `cat > ~/.claude/cp-last.txt <<'CPEOF'`, and `/cp` is invoked from inside a worktree often enough that the demonstration cost a refused call before anything reached the clipboard. The ring rotation stays in Bash, the write moves to the tool, and `Write` takes the content literally — which is what the single-quoted heredoc was for. Mirrored in the Codex skill and the feature doc.
- **`/docs` and `/truncate` no longer tell a run to branch on `$?`.** That instruction is what made `(okq … ; echo "exit=$?") | tail` the natural composition of a health-check pass, and the compound line is refused. The harness reports each call's exit status on its own, so each check is now sent as its own plain call.
- **`/task` names a reachable fallback when `my-command-tools` is not on PATH.** It previously said to run `my-command-tools doctor`, which is the command that just failed. It now names the device install path to reach the same CLI through, and `doctor`'s `onPath` output as the fix to report.
- **`/ideate` now looks at the running page before it files a user-interface idea, so a proposal the product already shipped dies in the run instead of on the dashboard.** Every evidence source the command reads is a *written* one — an `## Open questions` entry, a written deferral, a CHANGELOG line — and each of them was true when somebody wrote it rather than when the survey reads it. So a question asked in March about a control that shipped in June still composes cleanly into a proposal, and the docs bundle contains nothing that could say otherwise. The new **Step 3.5** closes exactly that gap and nothing wider: for a proposal filed under `ui-ux`, or any proposal whose mechanism changes what a page renders, the run opens the surface and looks. Every other proposal — a CLI verb, a schema, a workflow gate — has no page to look at, and the step reports itself as not applicable rather than inventing something to open. **The browser is a check, not a sixth evidence source, and that boundary is the whole design.** "I saw it in the browser" cites nothing, is written down nowhere, and gives a reader no locator to open, so it can neither create a proposal nor rescue one that cites nothing — it can only confirm or kill one that already cites a person's writing. A **confirmed** check is carried in the entry's existing **`note`** field, naming the route and what was on screen, and never in `evidence`; a **killed** proposal is dropped with the route that settled it named, which is the outcome the step exists to produce; an **unavailable** check — nothing running to look at, or no Chrome extension connected — leaves the proposal standing on its written evidence and is **stated rather than omitted**, because a report that skips the line reads as a check that passed. The look is **read-only and stays read-only**: Chrome MCP rather than computer use, which is for native applications; a dev server that is already up or a deployed url the docs name, rather than standing a stack up in a command that implements nothing; no form submitted, no sign-in, no irreversible control clicked, non-essential cookies declined, page text treated as data rather than as instruction, and every tab it opened closed behind it. `--dry-run` still runs the check, since reading a page writes nothing and reporting a proposal the live page already killed reports something not worth reporting. **Four skills are wired in as the reading tools, at most one per proposal and only where the subject matches** — `emil-design-eng` for a control, menu, form, or state change; `apple-design` for gesture, spring, sheet, translucency, typography, and reduced-motion questions; `animation-vocabulary` so a rationale states the term for a motion effect instead of describing it, which is what makes two motion ideas comparable on a dashboard card; and `web-perf` so a claim that a surface is slow is measured before it is filed. **A skill informs the proposal and never turns the run into an implementation**: several of them describe how to build what they judge, and `/ideate` still opens no branch, writes no code, and commits nothing. The list is advisory — an uninstalled skill is skipped without comment, and its absence is not an unavailable check. The report gains a line per checked proposal: the outcome, the route, and any skill the check called. Mirrored in the Codex skill and the feature doc.
- **An idea's rationale is now a list of plain-English bullets instead of a paragraph.** `/ideate` wrote a one-paragraph rationale, and that paragraph is read by a person on claude-proxy's Advice page who is deciding one thing — accept, or reject — usually without having run the survey and usually with several cards open. Prose made that reader hunt for the claim they were deciding on, and made two ideas impossible to compare without reading both in full. The shape is now fixed and stated once in the new `shared/plain-rationale.md`: six literal `- ` bullets, in order — **what it is**, **the problem**, **how it works**, **what it replaces or simplifies**, **size**, and **depends on `<slug>`**, the last written only when the idea consumes something a named idea introduces. That sixth bullet gives `/improve`'s stated-dependency test a place to read rather than a paragraph to infer from, and its absence is now a statement rather than an oversight. Three of Step 3's five required statements live in the rationale; the evidence and the repo stay fields of their own. Each bullet follows [ASD-STE100](https://asd-ste100.org) Simplified Technical English — one idea per sentence and at most twenty words, active voice and present tense, one word per concept, no idiom, at most three nouns in a row, an article before each countable noun, and no pronoun pointing at another bullet, because a reader scans a card out of order. **This is deliberately stricter than `shared/rewrite-toward.md`**, which draws on the same standard and declines its word list, sentence cap, and simple tenses: that file governs command instructions, whose reader is an agent executing them and where a long sentence buys precision, while a rationale is a short pitch to a human about to click Accept or Reject. The bullets are written as real newline-separated lines rather than flattened to fit a command line, since JSON carries them and the dashboard renders them as a list. **Nothing rewrites a row it did not write:** a rationale already on the ledger as a paragraph stays a paragraph, and the dashboard renders both shapes.
- **`/improve` dispatches ideas in parallel when they do not collide, instead of serializing every one of them for no reason.** Step 5 required idea subagents to go out strictly one at a time with each result read before the next — a rule inherited from the suggestion track, where briefs really can reference each other, and applied to a track where each idea is already its own branch and its own PR. Five accepted ideas touching five unrelated areas cost five sequential `/task` runs. Ideas whose file scopes do not overlap now go out **together, one `Agent` call per idea in a single turn**, a wave at a time. Ideas that genuinely depend on one another still run in order, and the dependent one **branches off the branch it depends on rather than off `main`** — dispatched with `/task --base <branch>` once that branch exists, with its PR targeting that branch — because a stacked idea built on `main` compiles against tokens, props, or endpoints that are not there. **Two tests, and only two, make one idea wait**: file-scope overlap inside one repo, or a dependency the idea's own rationale states. Sharing a repo or a `/ideate` run is neither, an inferred dependency is a guess, and where the two disagree the stricter wins. **A clean textual merge is explicitly not evidence of independence** and is never scheduled on — a stacked idea merges without a conflict marker while referencing values that do not exist on its base, so the break surfaces at build time rather than in the diff. Step 4 now records the two fields this schedules from, each idea's **file scope** and its **stated dependencies**, so the decision reads written-down inputs rather than re-deriving them; an *undetermined* scope is treated as the widest one there is rather than an empty one, and ideas in different repos never share a scope. Every concurrent subagent gets an **explicit lane** — the paths it owns and the paths it must not touch, being the other in-flight ideas' scopes — and stops rather than reaching outside it, since it cannot see the others. Same-repo concurrency is safe only because `/task` cuts a fresh worktree per run, which is exactly what a pass-through `--here` removes, so `--here` forces serial dispatch regardless of scope and the report says so. When independence is unclear the run serializes: one wasted wait costs latency, one wrong parallel costs two branches whose merge order changes the result. **`ideas claim --slug --by <branch>` still precedes every dispatch, however scheduled** — a whole wave is claimed before any of it goes out — one idea is still one branch and one PR, and a refused claim now also drops whatever was stacked on it.
- **An idea flag now makes the run idea-only, rather than dragging the judge and suggestion tracks along with it.** `--idea` or `--ideas` used to run the full suggestion pipeline beside the idea track: pending suggestions read, dirty buckets judged, suggestion criteria composed. A run that asks for one named idea paid for a judge pass it did not ask for and could not use, and the final report listed an empty suggestion track that read like an empty backlog rather than a deliberate skip. Either flag now suppresses both tracks outright — no pending suggestions are read, **Step 3 does not run at all and leaves every bucket's dirty flag exactly as it was**, no suggestion criterion is composed, and nothing is written to the suggestions store. `--range` and `--regressed` are suggestion-track flags and are therefore inert under an idea flag, and `--dry-run` judges on a suggestion run and has nothing to judge on an idea-only one. The consequence the flag change implies is now stated where it matters: **exactly one of the two tracks runs in any given run**, so the prose that had the suggestion track going first, or a repo getting a suggestion subagent *and* one subagent per idea, is gone. Judging is a precondition of the **suggestion track**, not of the command. And the report must say the suggestion track was **deliberately skipped because an idea flag was given** — never that nothing was pending or nothing was judged, which are the sentences a later reader mistakes for an empty backlog — alongside the schedule the ideas actually ran on: which went out together, which waited on which and off what base, and why anything was serialized.
- **`/ideate` now knows the ideas ledger's area protocol, so the write it composes actually lands.** The command prose contained the word "area" zero times while the store requires an `area` on every entry on the same footing as its evidence — so the `ideas add` `/ideate` composed was refused at the parse boundary and the whole batch was thrown away. That was never a missing convenience; it was a write that did not land. A `--area <area>` flag now does **two jobs, and the run must not conflate them**: it constrains the survey to one area, and it supplies the required per-entry field. Its default is **absent, which is not "no area"** — with no flag, each proposal carries the area it belongs to, chosen per proposal at composition time from the areas the dedupe read returned, falling back to the store's advisory seed vocabulary (`ui-ux`, `infrastructure`, `code-quality`, `services`, `commands`) and opening a new kebab-case area only when nothing existing fits, saying so in the report. **One area is never assigned to a batch that spans several.** It is spelled exactly as the store spells it, with no short alias, because `ideas list --area` and `ideas file --area` take the same string and `-r` and `-n` are taken. The flag and the **fifth evidence source are one change**, not two: Step 2's four-source list is now five, the fifth being `command-gap`, which carries no locator, may stand alone as an entry's whole evidence, and is confined to the `commands` area — cited anywhere else the store refuses the batch rather than storing it elsewhere. **`ideas list` accepts `--area` and the dedupe read must never use it**: dedupe reads the whole ledger regardless, because a dedupe read narrowed to one area is precisely how a rejected idea comes back under a different one, and the unnarrowed read is also what teaches the run the area vocabulary it then chooses from. Step 3's five required statements became six — the new one being the area the idea belongs under — and Step 4's write carries it. A `similarAreas` hit is **reported and never refused**: the entry lands, the report names it, and the run does not re-file anything itself. Mirrored in the Codex skill and the feature doc.

### Fixed

- **Five behaviours that had already been "fixed" once and came back are now fixed a rung higher, because a rule restated at the rung it already occupied is what let them return.** The escalation ladder is prose, then a step in a command, then a mechanical gate, then removing the affordance, and each of these climbs at least one rung above its own prior attempt rather than repeating it. **Prose composed on stdin reaches rung 4 by losing the affordance:** `commit` and `pr` now take `--message-file <path>` and `--body-file <path>`, a `PreToolUse` gate refuses `--message -` / `--body -` outright and names the replacement flag in the refusal, and `check-commands.sh` invariant 17 asserts both flags exist and that no command or shared snippet teaches the stdin form. This was thirteen identical refusals across five buckets — every one mid-commit or mid-PR inside an isolated worktree, where a heredoc is refused wholesale, and every one reissued as write-then-path a turn later, so the file form was always where the run ended up and the only question was how many turns it cost to get there. **A JSON shape guessed rather than read reaches rung 3:** a `node -e` / `python3 -c` one-liner naming a `.json` this session never opened is refused, which is the second-largest share of a Bash failure rate that had climbed monotonically to 74% of all failed calls. **A second, path-narrowed diff reaches rung 4 on both sides:** `scope --diff` already returns every hunk with its line numbers in one call, so once it has run a `git diff -- <path>` or `gh pr diff <path>` is refused, and the new `shared/one-diff-call.md` — carried by `/clean`, `/review`, and `/fb`, and held there by invariant 16 — states the same thing in the prose, because a run told two different things follows the older one. The prior attempt shipped the payload and left the walk possible; a recorded review walked a PR diff one probe per turn for thirty-five turns with the enumeration already in hand. **The read-before-write rejection reaches rung 4 by naming the batch instead of asking for it:** the denial now derives the file's co-change set from up to forty commits of this repository's own history and hands it over as ready-to-send `Read({file_path: …})` lines, since a command file, its built copy, its skill, and the changelog move together every time and rediscovering that one rejection at a time was a removable cost rather than an unavoidable one. **Polling reaches rung 4 on the surface it had escaped through:** the watched-condition gate judged only Bash, so waiting on a backgrounded verify run became a `Read` of its log three times over, and `Read` is now judged on the same evidence. **And the closing turn's anchor may no longer be the last thing scheduled:** a `TodoWrite` that completes the closing-turn item and carries nothing else is refused, because in nearly every recorded case the message before the Stop hook fired was a complete, correct report that simply carried a bookkeeping call with it — the work landed and the outcome did not. `TaskUpdate` is deliberately not gated: its input carries a task id and a status, never the subject, so the gate would have to guess which item it completes.
- **Each of those new gates now refuses only the shape it was written for, because a gate that also refuses the shape the prose prescribes is a contradiction the run resolves by ignoring one of them.** Review found five boundaries drawn wider than their own stated purpose, and every one of them is now drawn at the purpose. **The one-diff-call gate stopped refusing the batched form:** `shared/batched-discovery.md` prescribes `git diff <base>...HEAD -- <path> <path> …` as *the* fix for walking a file list, and the gate refused it — as did the hook's own two denial messages, which recommend that exact call. A single call naming many paths is the opposite of the walk the gate exists to stop, so `perPathDiff` now exempts any `--` list of more than one path. It also exempts `--quiet`, `--exit-code`, `--shortstat`, `--summary`, and `-s` alongside the `--stat`/`--numstat`/`--name-*` family already there, since none of them carry content `scope --diff` could have returned instead, and it leaves `git diff --cached -- <path>` alone outright, because `scope --diff` reads the working tree and cannot answer a question about the index. **The JSON gate stopped firing on commands that merely contain a flag:** `inlineScriptJson` matched `-e` or `-c` anywhere after the runner token, so `node build.mjs | grep -e foo package.json` was read as a `node -e` one-liner; the flag must now belong to the runner itself, with any non-option token between them ending the search. It also skips a `.json` the one-liner only *writes* — a path passed to `writeFileSync` and friends is an output, and refusing a write for not having read the file first inverts the rule. **The `Read` half of the watch gate stopped refusing the script it was pointed at:** it keyed on `watchedPaths`, which returns every filename-shaped token of the watched command, so a backgrounded `node verify.mjs --config ci.json > verify.log` made a first look at the script or the config a refusal. The new `watchedOutputs` returns only what the watch actually writes or follows — a redirect target, a `tee` destination, a `tail -f` argument — and the comparison is now between fully resolved paths rather than basenames, so an `out.log` in another directory is a different file. `watchedPaths` is untouched and still backs the Bash-side probe, where its breadth is right. **And two invariants now assert what they claim.** Invariant 16's comment described a check it did not perform; it now states only what it checks, plus a new assertion that each carrying command's built copy actually contains the expanded rule. The agreement it *could not* express in a grep — prose quotes the shape it forbids, so no regex distinguishes a prohibition from a prescription — moved into `hooks.test.mjs`, which reads the prescribed call out of `batched-discovery.md` and runs the real `perPathDiff` over it, so the two can never drift apart again silently. Invariant 17's stdin grep now covers `skills/*/SKILL.md`, which is half of every paired bundle and was outside the sweep. Six new hook tests cover each corrected boundary.
- **The `npx` wizard now arms the workflow gates, instead of installing the commands and leaving every gate inert.** The gates spec already recorded the failure and named the cause without closing it: the gates shipped, were merged, and did not execute for a week on the device that motivated them, because "commands reach a device by a path that does not run `scripts/install-personal.sh`." That path is this wizard. It installed the commands and the toolkit and stopped, so a device set up with `npx @llevasseur/my-command` held only `bin`, `toolkit`, and `VERSION` under `~/.claude/my-command`, and `doctor` reported `hooks.armed: false` with the reason "no settings fragment". The payload was never the problem — `package.json` ships `src`, so the whole hook bundle was already on the device's disk inside the package. It was a missing install step. `installHooks()` now runs on both Claude paths beside `installToolkit()`, and does **both** halves, because either alone is a no-op: it puts the scripts at `<config>/my-command/hooks`, then calls the shipped `install-hooks.mjs` to merge the registration into `settings.json` — the harness runs only what `settings.json` names, so scripts without a registration are files nobody executes, and a registration without scripts points at nothing. It **copies** where `install-personal.sh` symlinks, and that difference is the whole reason this needed its own function rather than a call to the existing installer: the script links back into a git clone on purpose so `git pull` updates the gates, but npx runs from an ephemeral cache directory that is cleaned up the moment the wizard exits, so the identical link would dangle and every gate would silently disappear. `hooks.test.mjs` is skipped, on the rule `installToolkit()` already applies — tests belong to CI, not the device. The `.mjs` scripts are chmodded 755 explicitly, since a lost mode bit fails only at hook time and only silently: the harness cannot execute the file, and a hook that fails to run allows the call. Registration goes through the copy that just landed, imported rather than shelled out, so the entries name the scripts the harness will actually run, the fragment resolves from beside them, and the merge returns a real count to report.
- **Two things it deliberately does not do.** It **never removes** the hooks directory, where `installToolkit()` replaces its target wholesale — this repo's own history records the incident behind that: a directory there can hold a hook the user installed and registered independently, and deleting it aims their registration at a path this install does not provide, breaking an unrelated guardrail to install ours. And a hooks path that is **already a symlink** is registered but never written through, because that is what a dev install looks like and copying through the link would write into the user's checkout. The report follows `reportToolkit()` — where the scripts landed, how many hooks and permissions merged, `doctor` as the confirmation, `export MY_COMMAND_HOOKS=0` as the off switch, and `node <dest>/install-hooks.mjs --uninstall` as the removal — and a failure **reports itself rather than aborting**, since the commands are installed and useful with the gates missing. `check-commands.sh` gained invariant 12 to keep all of it: the copy, both call sites, and both escape hatches in the output.
- **The Codex install registers nothing, decided rather than overlooked.** Codex does have a hook engine, but it is a different mechanism end to end — opt-in behind a `[features]` flag in `~/.codex/config.toml`, configured as TOML or `hooks.json` rather than `settings.json`, gated by a per-hook trust review, and firing `PreToolUse` for the shell tool **only**, never for the Read/Edit/Write calls two of these three gates judge. These scripts also speak Claude Code's protocol (`stop_hook_active`, `{"decision":"block"}` on stdout) and parse a Claude transcript. So installing them from a Codex install would either write Claude settings out of a Codex run, or leave a `hooks` directory under `~/.codex` that nothing would ever execute — a device reporting gates it does not have is worse than one reporting none. A Codex-native port is its own piece of work, and the reasoning sits at the call site rather than only here.
- **`doctor`'s repair hint stopped naming a file that is not there.** It was hardcoded to `bash <…>/scripts/install-personal.sh` — a path that exists only inside a git checkout, so the surface this change fixes was told to run something it does not have, which is worse than being told nothing. The hint now follows the surface: a checkout still gets the installer script, a wizard-installed device gets `node <hooksDir>/install-hooks.mjs` because the scripts are already there and only the merge is missing, and a device with no hook bundle at all gets `npx @llevasseur/my-command`. The same install shape exposed a second false report: `hooks.armed` judged staleness by asking whether the hooks directory is a **symlink** into the checkout, so a wizard device — where the toolkit runs from beside the copy, making `hooksDir` and `hooksSrc` the same path — read as "a copy `git pull` does not update" and carried a hint while being perfectly current. Correct is `linked || same path`.
- **The toolkit now fails closed on a device whose gates are not armed, because reporting it was not enough.** PR #70 wrote the rule down again; the closing-turn regression came back anyway, across five recorded buckets, one of them ending on four consecutive `TaskUpdate` calls. The reason is structural rather than behavioural: `doctor.hooks.armed` reported the unarmed state and nothing a session calls reads `doctor`, so an unarmed device stayed fully runnable and the Stop gate was a file nobody executed. `state`, `scope`, `commit`, and `pr` — the verbs a workflow command opens with, before it has done anything — now exit non-zero there, naming the arming command and the way out. A run cannot begin on a device where the gate would not fire, which is the affordance removed rather than reported. One detector answers for both surfaces: `deviceHooksStatus()` resolves every path from where the toolkit file actually sits, `doctor`'s private copy of that logic is gone, and the two can no longer disagree. `armed: null` passes, matching the hooks' own fail-open rule — a Codex install registers nothing on purpose, and a detector that throws has no verdict. `doctor` is never gated, since it is how a refused device finds out what to run. The escape is explicit and never the default: `--unarmed`, `MY_COMMAND_REQUIRE_HOOKS=0`, or the existing `MY_COMMAND_HOOKS=0`. Invariant 13 asserts the fail-closed path exists and then runs the escape for real, so CI proves its own way out.
- **The job-directory guard is deleted, not softened: it refused exactly the path the harness prescribes.** The job harness tells a session to keep scratch under `$CLAUDE_JOB_DIR/tmp`, and the `PreToolUse` gate denied that path from inside a worktree — so the instruction and the gate contradicted each other, and the session had no scratch location at all. Worse, the refusal was not the same twice: one denial per subject meant an identical write was allowed early in a run and refused later. One recorded session had `cp src/my-command.ts "$CLAUDE_JOB_DIR/tmp/my-command.ts.bak"` refused, worked around it with `perl -0pi`, and then lost its own uncommitted edits to the `git checkout --` that followed — the gate caused the damage it existed to prevent. The write is not harmful: the job directory is outside the repository, cannot reach the worktree's index, and is cleaned up with the job. "The worktree is the only writable root" was always a claim about where *the work* belongs, and `task.md` now says so, so the prose and the gate cannot drift apart again. A test asserts the scratch command is allowed on the first call and the second.
- **`my-command-tools scope --diff` returns the branch's diff content, so `/clean` has nothing left to fetch per path.** `scope` handed back a file list and the caller went and diffed it — once per path, which is exactly the loop `AGENTS.md` names and exactly what recurred: a branch diff reissued per file, plus `sed -n` over three adjacent ranges of one file instead of a single `Read`. The prose telling it not to was rung 2 and had already failed, so the verb closes the loop instead. One read-only call now returns `diff.committed` (the branch's commits) and `diff.workingTree` (the uncommitted changes on top, current branch only), each as files of hunks, with every line annotated `<sign><line number>\t<text>` — the number being that line's own file, so a comment's location is known before anything is opened. Output is bounded by `--diff-limit` (200,000 characters by default), and a file past the cap is named in `diff.omitted` rather than cut in half, since a half-written hunk reads as a complete one. Still read-only: no checkout, no switch. `/clean` steps 1–3 now take the diff from that one call and forbid a second one outright. `diffStat` gained an optional head ref along the way, which also fixes `scope --branch <other>` reporting the *current* branch's working tree as that branch's files.

## 2026-08-08

### Added

- **`/diagram` draws the architecture a change *produces*, and attaches it to the PR that change is being reviewed in.** A reviewer opening a PR gets a diff and a description written from that diff, and neither says what shape the system is in afterwards — so the reviewer rebuilds the architecture in their head from the files, every time, and a change that moves a boundary reads the same as one that does not. The subject is therefore a **change, not a repository**: the diagram renders the system *after* the change, with the added or moved nodes marked by a `classDef` and untouched context left plain. A whole-repo redraw was the obvious alternative and is the thing to avoid — it is the same picture on every PR, so it carries no information about the one in front of you. The output is one fenced `mermaid` block between `<!-- diagram:start -->` and `<!-- diagram:end -->` under an `## Architecture` heading, which makes a re-run a **replacement** rather than a second copy stacked under the first, and makes the rest of a PR body — which a human may have written — off limits byte for byte. Destinations resolve in order: `--out <path>` to a Markdown file, `--dry-run` to the reply alone, the open PR's body, or `--comment` for a body owned by a template. `--target` / `-t` points at another PR or branch, `--kind` / `-k` forces the type over the one chosen from the change (`flowchart` for module and data flow, `sequence` where order is the point, `er` for schema, `class` for a type hierarchy, `state` for a lifecycle), and trailing text is a focus hint.
- **It opens no PR, which is what makes it composable into `/task` with `--add`.** `/task -a diagram …` has two positions and they behave differently on purpose. **After `/pr`** is the normal one — the PR exists, so the diagram lands in its body in a single pass. **Before `/pr`** there is nothing to attach to, and the answer is emphatically not to create something: the run produces the block, says plainly that it is unattached, and hands it to `/pr` for the description it writes, with a second `/diagram` afterwards as the fallback if it did not make it in. Either way `/diagram` never blocks the task — an unresolvable subject or a failed attachment is reported and the run carries on — and it commits nothing, pushes nothing, and touches no file other than an `--out` target.
- **Two rules keep the diagram from being confidently wrong.** Mermaid is validated before it is posted, because GitHub renders an invalid diagram as a **red error block** in the PR rather than degrading to source: labels holding brackets, parentheses, colons, or commas are quoted, `end` is never a node id, node ids stay bare identifiers with the path in the label, and no HTML beyond `<br/>` appears. `mmdc` validates it when it is already on PATH, and when it is not the command **does not install it** — it checks by inspection and says so in the reply, since a diagram tool download is not a side effect a diagram request authorizes. And every node must come from something actually read during the run, capped at roughly 5–20 nodes: a plausible box for a service the repo does not have is worse than no diagram at all, because a reviewer will believe it. A change with no architectural content — copy, a version bump, a comment cleanup — is a legitimate "nothing to draw", stated rather than padded into a diagram of two boxes.

### Changed

- **`/teach` saves concepts to the hosted concept store instead of appending to a file in whichever claude-proxy checkout the machine happens to have.** Step 7 now POSTs one JSON record to `$CONCEPTS_URL/api/concepts` with an `Authorization: Bearer $CONCEPTS_TOKEN` header, and no longer touches `CLAUDE_PROXY_STORE`, its log directory, or `logs/concepts.jsonl`. The corpus was stranded per device — a concept taught on one laptop was invisible on the other, an agent had no way to query the one body of knowledge the user had been building on purpose, and a cloud box with no filesystem could not reach it at all. claude-proxy's [ADR 0005](https://github.com/llevasseur/claude-proxy/blob/main/docs/adrs/0005-host-the-concept-store.md) records the decision and the nightly git backup that pays for making a database the source of truth. **Both values come from the environment and neither is ever hardcoded**; the documented `node` snippet reads them from `process.env` inside the process rather than taking the token as an argument, so the token stays out of the command line, the transcript, and the shell history. **The write is idempotent** — row ids are content-derived ULIDs, so the store answers 201 for a new concept and 200 for a replay — and the retry is *inside* the call, one repeat on a network error or a `5xx` against the same record, rather than a re-run of the command. That distinction is load-bearing and the docs say so: every run stamps a fresh `savedAt`, which changes the record and therefore the derived id, so re-running a failed save would write a second version rather than replay the first. Idempotency protects a repeated request, not a repeated run. The record contract is unchanged: the same five required fields and four optional ones, the same `put` helper omitting an empty string or empty list rather than writing `""` or `[]`, and the same newline-separated lists, because a tip reliably contains a comma and never a newline. **An unreachable store stays non-fatal and stops being silent.** Step 6 prints and copies the sentence before the save is attempted, so an unset variable or a failed POST costs the save and nothing else — but where the old behaviour was a quiet no-op that turned a broken store into invisible loss, the run now states the cause in one short line: which variable is unset, the status and reason the store returned, or the network error. **This is step 2 of a three-step rollout and the ordering is a correctness requirement**, so the command file, the Codex skill, the feature doc, and the README all carry the same manual per-device instructions — export `CONCEPTS_URL` and `CONCEPTS_TOKEN` in the shell profile, then `/sync` that device — and say plainly that claude-proxy may retire `logs/concepts.jsonl` and its schema only once every device reports `saved: 201`. Nothing automates that rollout, deliberately: a device still on the old `/teach` writes to a local file nothing will read, and deleting the file before every device is updated would silently drop those concepts. There is no dual-write.
- **`/improve` now claims an idea before it builds it, which is the half of claude-proxy's claim protocol that was never installed.** The ledger grew a full protocol — a `claimed` status carrying `{ by, at, pr? }`, a six-hour expiry so a dead run cannot park an idea forever, a claim carrying a `pr` that never goes stale, `list --available` for the takeable set, and `mark -s accepted` as the explicit release — and then nothing called any of it, because `/ideate` and `/improve` are command files in *this* repo rather than in the one that grew the mechanism. So the failure it was built for stayed live: claude-proxy PRs #139 and #140 both implemented `archive-aware-window-reader` against the same `accepted` entry eleven minutes apart, and one was closed unmerged. Checked against the live ledger while writing this, three accepted ideas that were actively being worked on still read `claim=None`. Three decisions the deferral did not carry are settled here. **`--by` is the branch name the dispatch is about to cut**, decided by `/improve` and named in the subagent's brief so the subagent cuts exactly it — the branch is the one holder string a second run can check for itself against `git branch -r`, which tells a claim backed by real work from one left by a run that vanished, where a run id or a person's name would tell it nothing. **The `--pr` re-claim happens when the subagent returns one**, as the same holder, since claiming is idempotent and a claim carrying a PR stops aging — the expiry is sized to *writing* a change while review is the long part of an idea's life. And **the release rides the closing-turn anchor both files already carry**, so a run that gives up, is refused, or hits a failing gate marks the idea back to `accepted` on its way out instead of parking it for the full six hours; every mark but `shipped` drops the claim, which is what makes that the release. Beside them the idea read changes from `-s accepted` to `list --available` — a replacement, not an addition — because `-s accepted` can never recover an idea abandoned by a dead run while `-s accepted,claimed` takes one out from under a live holder. The sign-off rule is untouched and the doc says so in as many words, since `claimed` is reachable only *from* `accepted`: every available row was signed off, and a later reader must not narrow the query back. A refused claim is a **skip with a named holder**, never a stop and never a reason to build it anyway or retry under a different `--by`, which would hide the collision rather than resolve it; `--dry-run` claims nothing, because a claim is a write. `shipped` keeps its claim as the record of which branch built the thing, and goes back to meaning only that the work landed. The report now says which ideas were claimed, which were skipped and by whom, and which were released. **`/ideate` needed no change and got none** — it proposes and never implements, and its dedup already reads the whole ledger, so `claimed` rows were always in front of it.

- **`/diagram` now looks for an installed diagramming skill before it draws anything, instead of treating its own syntax list as the whole of the rule.** The command shipped with a hand-written summary of the Mermaid forms that break most often, and that summary was the only authority a run had — so a device with `mermaid-diagrams` installed, carrying a `references/` directory of per-diagram-type syntax, got none of it, because nothing in the command told the run to load it and a skill fires only on an incidental description match. The fix is a **Step 0 that runs before the subject is even resolved**, on every run including `--dry-run`: check the skills the session actually offers for one covering Mermaid or software diagramming, and load the match with the `Skill` tool before any Mermaid is written. The check is against the live listing rather than a hardcoded name — `mermaid-diagrams` is named as the usual match, not as the thing to assume is there — so the step stays honest on a device that has something else installed or nothing at all. **Finding no skill is an expected answer, not a failure**: it is stated once and Steps 3 and 4 apply as written, and the run is explicitly forbidden from installing one, on the same reasoning that already stops it installing `mmdc`. Precedence is stated rather than left to the run, because the two sources genuinely own different things: where a loaded skill and the command disagree about **syntax or diagram-type choice** the skill wins, since it is maintained against Mermaid's grammar while the command's list only carries the failures seen so far; where they disagree about what the diagram is *for* — one claim about one change, marked nodes, 5–20 real names, the marker block — the **command** wins, because those rules are about the review and not about Mermaid. Step 4 now says outright that its list is the fallback, `Skill` is added to `allowed-tools`, and the closing report names the skill that was loaded or says that none covered diagramming, so a run that silently skipped the step is visible in its own output. The Codex skill and the feature doc mirror all of it.

### Fixed

- **The closing-turn anchor stopped prescribing a tool call as the run's last action, because that is how the anchor was killing the message it exists to protect.** The rule said to mark the todo item completed "with the run's **final tool call**" and to send the text-only message after that call returned — two constraints that read as compatible and are not, since the last instruction the run actually executes is then a tool call. The evidence is one-sided: six of ten sessions in a single bucket ended on exactly that `TaskUpdate` and stopped there, with four more in each of the two buckets before it, and the marking landed **every single time** while the message did not. Capture was never the problem — sessions that do send a text-only turn get their outcome line — so wording the same sentence more firmly, already tried twice, had nothing left to fix. The affordance is therefore removed rather than restated: the anchor is resolved **in the same tool-call turn as the run's last piece of real work** — the teardown, the final `verify`, the closing `gh` call — so the task list is already clean when that turn returns and the only thing the run has left to do is speak. Marking it as a call of its own after the work ends is now named as the failure rather than offered as the natural finish, and a still-open anchor is explicitly never a reason to end on a tool call.
- **Two endings that recorded nothing are now covered by name.** A run whose whole job was answering another session replied with `SendMessage` and stopped; that is a tool call, so the run recorded no outcome at all, and the rule now says a cross-session reply still owes a text-only turn of its own afterwards, even when it repeats what the reply already said. Separately, a run split by compaction shipped a PR across two transcripts and closed on neither side, which reads as two abandoned runs rather than one shipped one — so **each side of a boundary now records its own standing**, on top of the existing rule that a recap prompt is answered in text alone.
- **`/clean` no longer has a changed-file list to walk.** The command already carried the batched-discovery step and a stated gate, and still regressed across three buckets: a post-compaction run took eighteen paths from one `git diff --name-only` and opened all eighteen in eighteen separate single-`Read` turns before its first edit, with five- and three-file versions of the same shape elsewhere. The list was complete before the first read, so none of those reads depended on another — and an instruction not to loop cannot beat a workflow whose next obvious move is a loop. So the opportunity is removed instead: **the diff the command already ran is the comment context**, hunks included, and the file list is not a queue. A new step selects, from those hunks, the subset of files that actually carry an in-scope comment, and that subset — not the scope result — is the input to a **single batched `Read` block**, since `Edit` needs its target read first. A changed file with no comment in its hunks is never opened at all, which on a typical branch is most of them, and a file discovered mid-edit joins the next batch rather than taking a turn of its own. The rule is scoped to a list that arrived complete: iterative probing, where each result chooses the next path, is a real dependency and is explicitly untouched — the same suggestion was rightly dismissed in another bucket where both flagged runs were genuine dependent discovery.
- **The `EnterWorktree` call that follows `worktree begin` now has a prescribed working form, in a shared snippet the invariant gate keeps in place.** Three `/task` runs created a worktree and reflexively entered it; all three were refused, and each independently reinvented the same absolute-path-plus-`worktree end` workaround from scratch. Banning the tool would be the wrong lesson — other sessions called `EnterWorktree({path: <absolute worktree path>})` immediately after `worktree begin` and it worked — so the fix is to spell the working call out: the `path` form, with the path copied byte for byte from what the verb printed, entering a checkout that already exists rather than requesting a new one by `name`, and never a relative or reconstructed path. A refusal is named as a statement about how the worktree was created, so it is neither retried nor worked around from scratch. **Teardown is decided together with entry**, because it is not `ExitWorktree({action: "remove"})`: step out with `action: "keep"`, then run `my-command-tools worktree end --branch <branch>` from outside the path. `/task`'s own teardown step was corrected to match — it previously told the same-repo path to force `remove` with `discard_changes: true`, which is the wrong mechanism for a worktree `begin` created and discards exactly the commits the refusal is protecting. The snippet is carried by `/task`, `/task-bootstrap`, `/review`, `/fb`, and `/revive`, and `check-commands.sh` gained invariant 11 to keep it there; `/mc` and `/god` were checked and never enter a worktree, so neither changed.
- **No command prescribes `gh pr merge … --delete-branch` any more, because that flag reports a failure for a merge that succeeded.** The flag runs a *local* branch cleanup after the merge lands, and on any device that keeps the default branch checked out that cleanup dies with `fatal: '<default>' is already used by worktree at …` — so the PR is merged, the exit code is 1, and the run has to work out from the stderr that nothing is actually wrong. Two sessions hit exactly that on `gh pr merge 156 --squash --delete-branch`. The prescribed form is now the merge alone, with the branch deleted as its own separate call: `my-command-tools worktree end --branch <branch>` for the local worktree and branch, `git push origin --delete <branch>` for the remote ref, each in its own call and skipped entirely for a `--auto` merge that has not landed yet. `src/shared/merge-command-forms.md` carries the rule for `/god`, `/mc`, and `/merge-deps`, and `check-commands.sh` gained **invariant 12** asserting no command or shared snippet reintroduces the flag. The existing guidance that a *refused* remote-ref deletion is final, and is surfaced rather than re-expressed, is unchanged.
- **`my-command-tools pr` takes its title from the branch when `--title` is absent, instead of exiting 2.** A missing title was a pure usage error: it failed identically on every re-run, and the answer it wanted — the branch's first commit subject — was already in the branch the verb had just resolved. It now defaults to that subject, and refuses only when the branch genuinely has no commit to take one from. `--title` still wins when given, and `--retitle` still governs whether an existing PR's title is touched.
- **An optional environment variable is probed on its own, with `|| true`.** `printenv CLAUDE_PROXY_STORE; printenv CLAUDE_PROXY_ARCHIVE` exits on the *second* command's status, so one unset optional variable reported the entire probe as failed even though the required variable had resolved — a half-success read as a failure, and then re-run. `src/shared/claude-proxy-checkout.md` and `/revive` now prescribe one call per variable, with `|| true` on every optional one.

### Changed

- **`/improve` no longer sweeps accepted ideas into its run, and an idea it does build gets a PR of its own.** Two defaults were wrong together. The stop happens on the first unresolved slug, before anything is dispatched, because a partial run is the outcome the rule exists to prevent: "build these three" quietly becoming two leaves the missing one indistinguishable from one nobody asked for. A dry run stops on it too — reporting criteria composed from a slug list that was never valid is the misreport in question.
- **Step 5 now dispatches the two tracks on different units, and Step 6 marks each idea against its own PR.** Suggestions keep the existing grouping — one subagent per target repo, one coherent PR each, regression block leading the brief — and ideas get one subagent per *idea*, never batched with each other and never added to the suggestion brief of the repo they land in. A repo in both tracks therefore gets a suggestion subagent **and** one subagent per idea, which is the intended shape rather than duplication to be tidied away. The rule that every dispatch runs **one at a time with its result read before the next** is unchanged and now spans more subagents, with the suggestion track going first because an idea building on a just-landed suggestion fix is likelier than the reverse. Marking follows the dispatch: `ideas mark --slug <slug> -s shipped` takes **that idea's** PR, one call per idea, since there is no longer a shared run-wide URL to write — a slug pointing at a PR that built something else is a false record that reads as a true one and that no later run can detect. One idea failing now marks nothing against the others. Everything else holds: the two evidence standards, `accepted`-only reads, the tier-1/2/3 waterfall with absence falling through and a read error stopping, the Step 3 judge gate, the regression track and its escalation ladder, and the closing-turn anchor.

- **`/ideate` proposes what is worth *building*, which is the one question `/improve`'s rules structurally cannot ask.** Those rules count what a transcript did, so they measure how work was *done* and can never report a capability that is **missing** — nothing counts a command that was never written. Filling that gap needs invention, and `/improve` is forbidden from inventing on a rule that is load-bearing rather than fussy: padding a run with the agent's own ideas breaks the trace from every change back to the sessions that justified it. Relaxing it there would cost the trace on every change `/improve` makes, so invention gets its own command instead. `/ideate` is **proposal only** — it never implements, never opens a branch or worktree, never commits, and never calls `/task` — and two boundaries carry the separation: it never writes `suggestion-status.json`, and `/improve` may act only on an idea a human **accepted**. That last is an *amendment* to the "never invent" note rather than a weakening of it, because the rule is about the **trace**: a suggestion traces to the sessions it was counted in, and an accepted idea traces to the recorded sign-off. What stays forbidden is unchanged and is the whole of the rule's original force — an idea thought of mid-run, one still `proposed`, and one a human `rejected` are all invention with no trace, and none may become a criterion.

The judge-note source **may not exist**: the verbs may be absent or no bucket may carry a verdict, and the run then says so and works from the other three rather than failing. Only that source is bucketed, so `--range` narrows it alone and never the survey as a whole. Two rules keep the output from being decorative: **an Open Question restated is not a proposal** (the question is already written down — the proposal has to add a mechanism, a shape, a decision), and **work `/improve` would find is never proposed here**, since a rule tripping belongs there with its source sessions.
- **The ledger is a waterfall, read wide and written narrow, and four rules are what make that safe for a dedupe key.** Tier 1 is `<logDir>/ideas.json` in claude-proxy through its new `ideas` CLI, tier 2 the surveyed repo's own committed `docs/ideas.md`, tier 3 a device-local `~/.claude/ideas/<repo-slug>.md`. **Write to the highest available tier and name it in the report**, because a silently-different tier between two runs is exactly how a rejected idea comes back. **Dedupe reads every tier that exists**, not just the winning one, so a machine that gains claude-proxy later does not forget what `docs/ideas.md` recorded. **Fall through on absence only, never on error** — an unset `CLAUDE_PROXY_STORE`, a missing path, a checkout with no `server/package.json`, or an absent `ideas` CLI all mean tier 1 is *absent*, while a tier-1 store that exists and fails to read or write is a **stop**, since writing tier 2 behind a broken tier 1 forks the ledger into two that each look complete. And **never propose a slug already present in any tier in any status, `rejected` included**, refusing a near-duplicate under a different slug too and naming what it collides with. Then **all of them** are written as `proposed`, including the ones expected to be rejected, because dedupe only works if the ledger records what was *considered* rather than only what was liked: an idea that never reaches the file can be re-proposed next run with a straight face. Only then comes the single question of which to accept, after which every non-accepted proposal moves to `rejected` **with its reason** so nothing is left at `proposed` to be re-asked forever. A run where nothing survives dedupe and the evidence rule **stops and says so** — a real answer, exactly as `/improve` finding nothing pending is.

- **`/judge` decides whether claude-proxy's suggestions are true, and `/improve` cannot compose a criterion without it.** A suggestion rule fires from counts and node positions; it cannot see what the agent was doing, so it reports a genuine slowdown and a misread with identical confidence — fifteen serial read-only calls look the same whether they were an unbatched sweep or a probe of an unfamiliar repo where each answer decided the next. `/improve` had no way to tell those apart and composed criteria from both, which means a rule's arithmetic error could become a permanent paragraph in a repo's `AGENTS.md`. `/judge` reads the **raw transcripts** at `<logDir>/sessions/<threadId>.md` for the ten sessions behind a bucket and returns one verdict per fired suggestion: **CONFIRMED**, with a note written from the transcript at the exact `sources[].nodeIndexes` the rule matched — what workflow phase was running, what it was trying to do, and what the slow shape actually was — or **DISMISSED**, with the reason the rule misread it. A confirmation note **never restates the rule's own generated `detail`**: that string is already in the store, it is arithmetic, and paraphrasing it adds a sentence and zero evidence while reading like corroboration; where there is genuinely nothing to add, the note says so rather than padding. It judges only **dirty** buckets — complete and unjudged, from `suggestions buckets --dirty --json` — and never a partial bucket (its counts are still changing, so a verdict would describe numbers that stop existing, recorded against a bucket that is never re-read) and never one already judged (a second pass overwrites considered notes with fresh guesses). Both verdict sets go out in **one** `suggestions judge -r <bucket> --confirm … --dismiss …` call per bucket, because that call is what sets the judged flag: split into two, a run that dies between halves leaves the bucket judged with half its verdicts missing. Reading cost is deliberately not the concern — a bucket is ~55 KB of transcripts typically and ~180 KB worst case against 415 transcripts at a 5.5 KB mean and 17.8 KB largest — so all ten transcripts are read in **one batched pass** via `shared/batched-discovery.md` (now asserted for `/judge` by `check-commands.sh` invariant 8), never one `Read` per turn. The claude-proxy checkout is resolved from `CLAUDE_PROXY_STORE` exactly as `/improve` does, which is now true by construction rather than by copy: that resolution moved into the new `src/shared/claude-proxy-checkout.md` and both commands include it.

- **`/improve` orchestrates `/judge`, so no unjudged rule output can reach a PR.** A new Step 3 finds the dirty buckets in the range and judges them **before** any criterion is composed, then re-reads the suggestions so they carry their verdicts; the rest of the pipeline shifted down (criteria are Step 4, the `/task` dispatch Step 5, marking Step 6). Two properties make it a gate rather than a nicety. **A failed judge run stops the command and brings the human in** — an errored call, a bucket recording fewer verdicts than it had fired suggestions, or a `/judge` run that could not finish — and there is deliberately **no fallback to composing from unjudged output**, because the dirty flag is the record that nobody has checked these findings against reality and a silent fallback makes a failed judge run indistinguishable from a clean bill of health, producing a PR that looks exactly like a well-evidenced one and is not. And **the judging is capped at 5 buckets**: `/improve`'s default range is *every* bucket and the unjudged backlog runs to dozens, so an uncapped first run would sit there reading megabytes of transcript before composing a single criterion — over the cap it stops with the bucket count and rough read cost and the two ways forward, narrowing `--range` or `suggestions judge --amnesty` to draw a line under the history. `--dry-run` does **not** skip judging: judging records verdicts about transcripts rather than claims that a fix shipped, and criteria are only worth reporting if they came from confirmed findings.

- **Criteria come from confirmed suggestions only, and a judge note outranks the rule's own `detail`.** A dismissed row is excluded entirely — not a weaker criterion, not a note attached to another one; a dismissal is a verdict that the finding was never true, so there is nothing to fix and nothing to report as deferred. Where a confirmed row carries a judge enrichment note, **that note is the criterion's reason**: it was written from the transcripts by an agent that read the nodes the rule pointed at, which makes it better evidence than a string generated from counts. The regression track, the four-rung escalation ladder and the recurrence handling are unchanged, and a dismissal is explicitly barred from that track in both the command and its Codex skill — `regressed` means a dated fix did not hold, `dismissed` means there was never anything to fix, and conflating them escalates a rung against a finding that was never true, which is how you end up writing a mechanical gate to prevent something that did not happen. A dismissed suggestion is also never *marked*: `done` would claim a fix that does not exist and `skipped` would record a real finding deliberately deferred, and both are dated claims that later sessions get read against.

- **A defective rule now has an exit path instead of billing attention forever.** `/improve` used to declare a suggestion whose fix belongs to claude-proxy's own rule code "out of scope" and leave it `pending` — so a systematically-wrong rule was re-proposed, re-read and re-rejected on every future run, and nothing in the command was allowed to touch the thing that was actually broken. It now runs `suggestions defects` and dispatches each rule reported defective as an **ordinary criterion against claude-proxy's `packages/core/src/suggestions.ts`**, naming the buckets it was dismissed in and **the dismissal reasons themselves** as evidence — those reasons say what the rule counted versus what was happening, and that gap *is* the specification for the fix. The ask names both sides: narrow what the rule matches so the dismissed cases stop firing **without** silencing the confirmed ones in the same buckets, since a rule that stops reporting a real slowdown is not fixed. This needed no new dispatch machinery — Step 5 already runs one subagent per repo and claude-proxy is simply one of them. A suggestion whose fix belongs to claude-proxy's dashboard or recurrence model rather than its rule code still stays `pending` and is reported as out of scope; `defects` is the narrow case that now has an answer.

### Added

- **The commands that set up a worktree and delegate now tear their own down.** They previously leaned on `/pr` doing it, which would have stranded a workspace now that `/pr` declines: `/fb --target` (same-repo and cross-repo), `/review` (default mode, clean PR or not), `/task-bootstrap`, and `/revive` each finish with `ExitWorktree` (`action: "keep"` — the only action allowed for a worktree entered via `EnterWorktree({path})`) followed by `my-command-tools worktree end --branch <branch>`, which re-verifies the branch reached origin before removing.

That also actively misleads `/revive`, which treats a missing `done:` as its interruption signal and would re-pick-up finished work. The terminal step of all fifteen commands now states that the report is its own turn, delivered after the last tool call and never alongside one.

### Added

- **`improve` command** — turn claude-proxy's session suggestions into an implemented change, so the advice about how this agent works stops being something a human reads and starts being something that ships. claude-proxy scores every ten recorded sessions for ways to reach the same outcome in fewer steps — independent reads issued one at a time, an error rediscovered session after session, a guardrail refusing a call the agent had already decided to make, a file read three times in one run — and `/improve` reads those findings, keeps only the ones still **pending**, composes them into criteria, and hands them to `/task` in one fresh subagent. `--range` / `-r` picks the buckets (one `9`, a list `2,3,9`, a span `2-9`, or a mix `2-4,9`; every bucket by default), `--dry-run` / `-n` reports the pending set and the criteria without running anything, and `--here` / `-h`, `--base <branch>`, `--draft` / `-d`, `--add` / `-a` pass straight through to `/task` rather than being reinterpreted here. Grouping happens before dispatch (the same rule tripping in several buckets is one improvement with more evidence, not several), the command creates no worktree and makes no edits of its own, and it never pads the run with improvements the suggestions don't support — every change traces back to a finding with its own evidence and source sessions. ### Fixed

- **The installed toolkit is now actually callable, so commands stop silently falling back to hand-rolled git.** Every install placed the shim at `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/my-command/bin/my-command-tools` and stopped there — nothing ever put that directory on `PATH`. But a command spells the call as a bare `my-command-tools` and declares it as `allowed-tools: Bash(my-command-tools:*)`, so on a fresh device the CLI was installed and invisible at the same time: `/task`, `/god`, `/pr`, `/mc`, `/review`, `/revive`, `/merge-deps`, `/changelog`, and `/sync` found no such command, read that as "the toolkit isn't installed", and fell back to plain `git`/`gh` — losing the default-branch guard, the whole-tree-staging refusal, the unpushed-work check on `worktree end`, and the draft-only PR rule while still looking like a working run. `installToolkit()` now calls a new `linkOnPath()`, and `scripts/install-personal.sh` does the same in shell: the shim is linked into the first of `~/.local/bin`, `~/bin` **already on the user's PATH**, pointing at the fixed shim path rather than one install's payload so the link survives a later install replacing the toolkit underneath it. ### Added

- **Command toolkit** — a zero-dependency Node CLI (`my-command-tools`) that owns the deterministic half of a workflow run, so commands stop re-deriving the same git state with a slightly different volley of one-off shell calls each time. Six verbs, each returning **JSON on stdout**: `state` (branch, base, commits, tracked vs untracked changes, and a single `hasWork` boolean that settles `/task`'s no-change gate), `verify` (discovers the repo's package manager by lockfile, runs its gates fastest-failing first, and returns *no* log for a pass and a bounded tail for a failure — no more hand-rolled `2>&1 | tail -12`, and no re-running a whole build because the window was guessed too small), `commit`, `pr`, `worktree begin|end|list`, and `doctor`. The guards are the point: `commit` refuses the default branch and refuses `.`/`-A`-style whole-tree staging so carryover files from a dirty checkout stay put, `worktree end` refuses to remove a worktree whose HEAD isn't on origin without `--force`, and `pr` only ever moves a PR *toward* draft rather than silently flipping an existing draft to ready. Judgment stays with the agent — there is deliberately no comment-scoping verb, because `/clean` runs entirely as an agent pass: deciding a comment is worth cutting depends on the surrounding code, and handing the agent a pre-filtered list of comment lines would narrow its view exactly where the wider context is what the call rests on.
- **Device-wide toolkit install.** Commands must reach the tooling however MyCommand was installed, so the toolkit resolves through three roots in order: `$MY_COMMAND_TOOLKIT` (explicit override), `$CLAUDE_PLUGIN_ROOT/src/toolkit` (set by Claude Code for plugin commands), then `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/my-command/toolkit` (what the npx wizard writes). `installToolkit()` runs in **both** wizard modes — plugin and personal — copying `src/toolkit/` to the device root, placing an executable shim at `<root>/bin/my-command-tools`, and stamping a `VERSION`; `scripts/install-personal.sh` symlinks the checkout instead, so a dev clone tracks `git pull`. The toolkit ships as **raw `.mjs` under `src/`**, never build output: a plugin install is a git clone with no build step and `dist/` is gitignored, so anything requiring compilation would simply not exist in plugin mode. Type safety survives that via a separate `tsconfig.toolkit.json` running `allowJs` + `checkJs` + `noEmit` (`pnpm run check:toolkit`), and a `node --test` suite exercises the verbs against throwaway git repos — where it caught a live bug: trimming git's two-column `--porcelain` output shifted every parsed path by two characters, so status is now read raw. Ships with `docs/specs/command-toolkit.md`.

### Added

- **`god` command** — carry a plain-language task all the way to **merged into `main`**, with no human in the loop. `/god <criteria>` is `/task` plus the last mile: it forwards `--here` / `-h`, `--base <branch>`, and `--add` / `-a` untouched and lets `/task` own the branch, implementation, verification, `/clean`, `/pr`, and teardown, appending its own `--add review …` entry so the review lands **inside** `/task`'s existing `/clean` + `/pr` subagent — after `/pr`, before teardown, where that subagent is already on the PR's branch with the PR pushed, so `/review --here` is correct and its `/fb` chain updates the same PR instead of nesting a worktree. Both review outcomes resolve in that subagent (findings → it runs the `/fb` line itself; a clean sign-off → it returns without one), so nothing comes back as pending work. The merge stage then re-resolves the PR from `gh` and refuses any PR whose head isn't this run's branch, detects conflicts **locally** with `git merge-tree --write-tree` rather than trusting GitHub's lazy `mergeable` field and delegates them to `/mc -t <branch>`, watches CI with `gh pr checks --watch --fail-fast`, spends up to `--fix <n>` rounds (default 1) of `/fb -t <branch>` against the failing job's log when it goes red, merges with `gh pr merge --delete-branch` (falling back to `--auto` on pending checks, looping back to the conflict stage once if `main` moved), and finally fast-forward pulls `main` in the **main checkout** — recorded up front, since `/task` tears its worktree down before this stage. `--squash` (default) / `--merge` / `--rebase` pick the method, `--auto` skips the CI wait and queues auto-merge, `--no-review` drops the woven-in review, and `--draft` / `-d` is rejected because a draft can't merge. Four situations stop the run instead of being driven through — an unresolvable `/mc` conflict, CI still red after the repair budget, a diverged local `main`, and a PR that isn't this run's — and it never merges with `--admin`, never force-pushes, and never pushes to `main` directly. - **`revive` command** — resume a session that stopped mid-flight (cleared, compacted away, killed, or abandoned) and left its work half-applied on a branch. `/revive <session-id>` resolves the id against **claude-proxy's transcript store by default** — `$CLAUDE_PROXY_STORE/<threadId>.md`, where the thread id is `sha256(sessionId + "\n" + first-user-text).slice(0, 16)` — searching the live store and then globbing the relocated days under `$CLAUDE_PROXY_ARCHIVE`; a 36-char UUID or `--source cli` reads the Claude Code JSONL instead, and `--source <path>` reads a file directly. It walks between the two stores through the transcript's `- session: <uuid>` header, and knows one session id can own several thread ids because each subagent gets its own conversation root. The transcript is treated as a **lossy digest**: read for the ask, the (often nested) slash-command workflow that was running, the human's already-settled mid-run decisions, the `- ✗` errors, and the point where it stops — the transcript simply *ending* being the interruption signal. Workspace recovery reads `cwd`/`gitBranch` from the CLI transcript and resumes that directory in place, or recreates a worktree checking out the **existing** branch, never a fresh branch off `main`. Then `git status`/`diff`/`log` plus the repo's own gate scripts establish what actually landed, and only the remainder is worked — each claim re-verified against source, since the digest's reasoning lines are truncated summaries. The run finishes on the *original* workflow's terms (for anything wrapped in `/task`: commit, `/clean`, `/pr`, teardown) without nesting a new `/task`. `--dry-run` / `-n` reports where it stopped and what remains, changing nothing. Ships with `docs/features/revive.md` and README entries.
- **`docs` command** — reconcile a repo's [okq](https://github.com/mikevalstar/okq) doc bundle with the code it describes, covering all three directions docs rot: **stale** (a doc that no longer matches the code), **missing** (a feature with no doc), and **obsolete** (a doc for something that was removed). It discovers the bundle, reads the bundle's *own* contract first (frontmatter keys, generated `index.md`s, folder templates, the 1:1 unit it documents, any docs gate script) and lets those rules win, then reconciles concepts against documentable units into CHECK / MISSING / OBSOLETE before editing anything. The staleness pass audits docs **one at a time** in fresh subagents, using git recency only to rank suspicion and claim-level comparison (flags, defaults, paths, exit codes, behavior — `old → current`) as the real verdict; drift found in one doc is re-checked across its `neighbors`/`backlinks`. Code that looks like the regression is flagged for the user rather than blessed by rewriting the doc, a wrong ADR is superseded rather than edited, a rename is repointed rather than deleted, and every deletion is confirmed with evidence and made with `git rm`. Pass flags `--refresh` / `-r`, `--add` / `-a`, `--prune` / `-p` combine (all three by default); `--dry-run` / `-n` plans without writing, `--bundle` / `-b <dir>` picks the bundle, `--yes` / `-y` skips confirmations, and trailing text scopes the run to a concept, path, or topic. Ships with `docs/features/docs.md` and README entries.

Paired with branch protection on `main` (require branches up to date + required checks) so the origin blocks merging a conflicting or stale branch.

## 2026-07-15

### Fixed

- `task` now branches worktrees off the *latest* `main` instead of whatever `origin/main` the local checkout last saw. Step 1 fetches (`git fetch origin`) before creating the worktree and, after entering, verifies the base matches `origin/<default>` — resetting the fresh (commit-less) branch onto it when `EnterWorktree` planted it on a stale local HEAD. Previously a task could silently build on out-of-date code.
- `npx github:llevasseur/my-command` ran but did nothing (exited silently). The wizard's "invoked directly" guard compared `import.meta.url` against `process.argv[1]`, but `npx` runs the bin through a `node_modules/.bin` symlink — so `argv[1]` was the symlink path while `import.meta.url` was the resolved real path, and they never matched, so `main()` never ran. The guard now resolves `argv[1]` with `realpathSync` before comparing, so both `node bin/my-command.mjs` and the `npx` symlink invocation start the wizard.

### Added

- `trim` command — apply an evidence-backed safety rubric to the current conversation and, when safe, provide focused instructions for Claude Code's built-in `/compact`.
- README gains a **Use cases** section — a command/example table for `task`, `fb`, and `mc` that highlights how each parameter (`--here`, `--base`, `--draft`, `--add`, `--target`) changes what the command does.
- `docs/` [okq](https://github.com/mikevalstar/okq) spec bundle — process specs ([Adding a command](docs/specs/adding-a-command.md), [Install wizard](docs/specs/install-wizard.md)) plus one feature doc per command in `docs/features/`, indexed with `okq --bundle docs index`. The specs codify two invariants: a new command needs a feature doc and wizard inclusion (with overwrite), and a command's feature doc must be updated whenever its flags or params change. README now references the specs and documents `docs/` in the repository layout.

### Changed

- Personal install (the `npx` wizard) no longer silently skips commands that already exist. When there are conflicts it now shows an interactive checkbox — with a **Select all / Deselect all** toggle pinned at the top — so you pick exactly which existing commands to overwrite. Conflicts start unchecked (nothing is clobbered by default), and non-interactive shells keep the old safe behavior of leaving existing files untouched.
- Personal install now warns instead of doing nothing when you already have every command and confirm the overwrite prompt with none selected. Pressing Enter on an empty selection used to report a hollow `Copied 0 new, overwrote 0`; it now tells you to pick commands to overwrite (or press Esc to cancel). Cancelling with Esc, and runs that still install fresh commands, are unaffected.
- The overwrite prompt no longer closes when you confirm with nothing selected. Instead of exiting, it keeps you in the checkbox and shows a yellow "Select at least one command to overwrite, or press Esc to cancel" alert — so an accidental Enter can't drop you out of the wizard. Esc still closes it whenever you want, and cancelling that way now reports `Nothing changed` rather than a hollow `Copied 0`.
- `task` Step 3 now runs `/clean` and `/pr` in **fresh subagents** (via the `Agent` tool) instead of inline. Both stages derive their inputs entirely from git, so an isolated context loses nothing while shedding the large, stale file reads a long task accumulates by its final stages. Worktree teardown moves to the task agent itself, since `ExitWorktree` only works in the session that created the worktree.
