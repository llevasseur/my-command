# Changelog

All notable changes to MyCommand are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com). There are no fixed release
versions — the plugin publishes continuously and installed copies track the
latest commit (SHA-based versioning), so changes are grouped by date.

## 2026-08-02

### Added

- **`/cp <command> <prompt>` — compose another command's invocation and copy it to the clipboard instead of running it.** The use case is handing a prompt to a *different* agent: you want `/task <criteria>` on the clipboard, not a task run. The cost of that today is a full round trip where the agent prints the command back and you copy it out of the transcript. `/cp` writes it straight to the clipboard in one heredoc-quoted `pbcopy` call (`wl-copy`, `xclip -selection clipboard`, or `clip.exe` off macOS) and replies `Done!` plus at most one line naming the direction it took — the composed text is never printed, because printing it is the cost the command exists to avoid. Minimizing tokens is the feature, so the constraints are all negative: it never invokes the target command, never loads its instructions, never checks that it exists (an unrecognized name is copied as typed and the receiving agent reports it), and never reads files, greps, or touches git to enrich the prompt. What it *does* do is shape the prompt to stand alone for an agent that cannot see this conversation — pronouns resolved, files, branches, and PR numbers named, stated constraints kept, the user's own flags preserved as typed. `--verbatim` / `-v` skips that shaping. Arguments too vague to compose get one focused question and no clipboard write. Ships with the Codex skill (`$cp`, composing `$<skill>` invocations) and a feature doc.

## 2026-08-01

### Added

- **Four environment rules moved out of claude-proxy's always-on `AGENTS.md` and into the commands that need them mid-task.** They only matter while a task is running, so they were costing every session's context to serve a handful of steps. **1Password signing** (`failed to fill whole buffer` + `fatal: failed to write commit object` is an unapproved prompt, not a repo problem — retry once, never `--no-gpg-sign`) lands beside the commit call in `/task` Step 2 and `/task-bootstrap` Step 7 — the only two commands that commit directly. `/pr` and `/clean` both state that they never commit, so a signing failure cannot fire in either; they keep their existing do-not-commit rules and carry no copy of this one. **gh GraphQL collaborator identity** (`must be a collaborator` means the wrong account, not a permission to request) lands in `/pr` Step 3 and `/task`'s Notes. **Worktree ownership** (remove a worktree through the same mechanism that created it; a worktree merely *entered* with `EnterWorktree({path})` is not owned by `ExitWorktree`) lands at the four sites that actually enter one they didn't create — `/task` Step 3's teardown, `/pr`, `/review`, and `/task-bootstrap` — and **not** in `/clean`, which has no worktree tool and never tears one down. The device-wide `~/.claude/CLAUDE.md` already carries the "inspect locked state, uncommitted changes, unpushed commits" precondition always-on, so no command restates it. **Classifier-sensitive Git calls** (the narrow-retry rule, and approval-prone commands issued in their own call) land in `/task`, `/pr`, `/god`, `/merge-deps`, and `/mc`'s Notes; the **final refusal on PR merge and remote-ref deletion** lands only in `/god` and `/merge-deps`, the two commands that merge a PR or delete a branch, anchored to the exact steps that do it. Each rule sits at the step it governs rather than in an appendix, and `/task`'s pre-existing approval-call bullet was reconciled into one merged rule instead of gaining a second copy. The Codex skills carry the same rules.

### Changed

- **`/mc -t <branch>` now merges inside an isolated worktree instead of checking the branch out in place.** Target mode used to run the same in-place loop as the other two modes: fast-forward local `main`, `git checkout <branch>`, merge, push, `git checkout` back — which moved the user's `HEAD`, refused to run at all against a dirty tree, and left the checkout on the wrong branch if the run died mid-loop. It now runs `worktree begin --branch <branch> --existing --bootstrap` and does every git call as `git -C <path>`, reading and editing conflicted files under that path. `--existing` is the load-bearing flag — without it the verb would create a fresh branch and abandon the very work being merged into — and it resolves a branch that exists only on `origin`, so `/merge-deps`' `git branch -D B` refresh step still works. Three deliberate choices: the merge takes `origin/main` rather than local `main`, so no fast-forward of the user's checkout is needed; the clean-tree precondition no longer applies to target mode, since uncommitted work in the current tree is now irrelevant to it; and the session does **not** enter the worktree (`git -C` throughout), because `/mc` is usually a step inside `/god` or `/merge-deps` and relocating the session would move the ground under its caller. Teardown runs on every exit path including the aborted-merge one, and `worktree end`'s refusal-while-unpushed is treated as a signal to push or report the path, never to `--force`. `--here` still operates on the current checkout by definition, and default (all-PR) mode is unchanged.

- **Density pass over every command in `src/commands/`.** Same rubric as `/truncate` but applied to behavioral specs: a line earns its tokens by naming what the agent must do or must not do — a flag, a default, a constraint, a failure mode. Narration, rationale nobody asked for, and mechanisms re-explained across sections were cut; every flag, step number, ordering rule, and never/always constraint survives verbatim. Cross-file duplication was the main lever, but only where it is safe: a rule may be dropped from command A only when A always loads B's file, so the delegating commands (`/docs`, `/truncate`, `/fb`, `/god`) stop restating `/task`'s commit and read-before-edit rules, while standalone-invocable commands keep theirs. 3,486 bytes of packaging removed across 11 files; `changelog` and `trim` had none to cut and were left alone.

- **A rule shared by several commands now lives once, in `src/shared/`.** Each installed command file is loaded standalone, so there is no *runtime* include — the text has to be physically present in every copy, and per-invocation token cost is identical however it gets there. What was missing was a single edit point. `src/shared/<name>.md` holds one line of canonical text; a command writes `<!-- include: shared/<name>.md -->` and `scripts/expand-includes.mjs` expands it **in place** in `src/commands/`, inline on the directive's own line (so it survives inside a nested bullet at any depth) and closed with `<!-- /include -->`. Re-running replaces that body rather than nesting a second copy. `build-plugin.sh` expands before copying, so the generated plugin can never carry a stale rule; `check-commands.sh` runs `expand-includes.mjs --check` **before** the build, so a hand-edit between the markers fails CI instead of being silently repaired by the next build. Expanding in place rather than into a new output tree is what keeps all three install surfaces — `build-plugin.sh`, `install-personal.sh`'s symlinks, `install-marketplace-personal.sh` — and the `npx` wizard unchanged. Seven snippets ship: `text-only-turn` (previously restated in all 16 commands), `signing-retry`, `gh-identity`, `approval-own-call`, `classifier-refusal`, `refusal-final`, and `worktree-ownership`. Codex skills deliberately opt out — `AGENTS.md` requires them to be translations, not copies.

### Fixed

- **Rules that could never fire were removed from the commands that carried them.** `/pr` never commits, so its residual "never rewrite a commit, pass `--no-gpg-sign`, or change the repo's signing configuration here" clause was unreachable and contradicted its own do-not-commit rule; it is gone, and the signing rule stays where a commit actually happens. `/clean` is comments-only with no worktree tool, and its teardown procedure handed the agent a permitted `git worktree remove <exact-path>` directly under its own "Teardown is never yours" headline — the procedure is gone and the headline now says plainly that `/clean` never removes a worktree by any route. Neither `/pr` nor `/task` merges a PR or deletes a remote ref, so the "a merge or remote-ref-deletion refusal is final" rule moved out of both and into `/god` and `/merge-deps`.
- **`/clean`'s "do not commit" no longer escapes its own scope.** The rule read as an unqualified `Do not commit.` at the end of the Finish section, so an agent running `/clean` nested inside `/task` carried it up to the caller and stopped with the cleanup edits sitting uncommitted — one step short of `/task` Step 3, which says the opposite for the invoker ("commit any edits it makes, then run `/pr`"). Since `/pr` never commits, those edits would have shipped as nothing at all. The line now states what it is scoped to: `/clean` leaves the edits uncommitted **for the invoker to own**, uncommitted is the deliverable only for a direct run, a nesting workflow commits them and isn't finished until it has, and a nested run hands back and continues that workflow at its next step instead of reporting the branch done. When an invoker's instructions never say who commits, the summary flags the uncommitted edits rather than `/clean` committing them itself. Phrasing follows the boundary `/changelog` already drew ("Don't commit unless the repo's flow expects the changelog committed with the work"), and the Codex skill and feature doc carry the same scoping.
- **`/task-bootstrap` Step 7 now commits the cleanup it asks for.** It ran `/clean` between its own commit step and `/pr`, which left it as the one `/clean` invoker with no instruction to commit what the pass produced — the same silent loss, reachable even with `/clean`'s rule correctly scoped. Both the command and its Codex skill now commit whatever `/clean` leaves behind before invoking `/pr`.

## 2026-07-30

### Changed

- **Subagent delegation is opt-in: `/task` gained `--sub` / `-s` and spawns nothing by default.** `/task` Step 3 always dispatched `/clean` + `/pr` into a fresh subagent, which costs a handoff and a second context on every run — including the many where the caller is already sitting in the right worktree and wants to watch the cleanup and the PR description land. That stage now runs **inline** in the calling session unless `--sub` / `-s` asks for the subagent form. Everything else about the stage is unchanged in both modes: `/clean` first and its edits committed, then `/pr` in the same run, `--draft` passed through, teardown owned by Step 3 rather than the pair, and the `hasWork` gate still skipping both on an empty diff. A Step 0 `--add` command scheduled at that point follows the pair, so it runs inline by default and inside the subagent under `--sub`. `--sub` still dispatches **one** subagent for both, never one each, because `/pr`'s description has to see what `/clean` touched without a second handoff.
- **`/god` always invokes `/task --sub`.** Its woven-in `--add review …` entry runs `/review --here` "in that same subagent", which only exists in the `--sub` form — so `god` sets the flag unconditionally rather than inheriting the new inline default and leaving that entry pointing at nothing. Passing `--sub` / `-s` to `/god` yourself is accepted and redundant. An unattended run also has the most to gain from the fresh context, since the reviewer's reads never enter the merge stage's conversation.
- **`/review` runs its `/fb` inline, explicitly.** The independence a spawned agent buys belongs to the *review*, and Step 3 already spent it; applying findings that are already written down is ordinary work on the PR's branch, and running it in the session that just read them keeps them in context. The command now says so rather than leaving it implied by the `Skill` invocation, and the Codex skill matches.
- **`/pr` skips teardown for an inline caller too.** Its rule was "teardown is yours only if this session created the worktree", which the new inline `/task` path satisfies — `/pr` would have removed the workspace out from under `/task`'s own Step 3, which has a push check to run first. Ownership is now scoped to "this session created it **and** no command that invoked you owns its teardown", with the inline case called out beside the dispatched-as-a-subagent one.

## 2026-07-29

### Changed

- **`docs` now finishes with the `truncate` density pass in the same task and PR.** Both Claude `/docs` and Codex `$docs` still reconcile stale, missing, and obsolete documentation first, but they no longer stop after marking updated or added docs `dirty: true`. The final in-workflow phase consumes the complete dirty queue, inventories and preserves every claim, cuts narration and repetition, applies the existing 40% size guard, clears evaluated flags, and runs the final docs gates. It executes truncate's rules inline instead of nesting another task. Standalone `/truncate` and `$truncate` remain available for hand edits, explicit scopes, interrupted queues, and whole-bundle sweeps. ADR 0004 supersedes the earlier separate-PR decision, and `check-commands.sh` guards the phase on both command surfaces.

## 2026-07-28

### Added

- **`truncate` command** — the rewrite-for-style pass `/docs` deliberately refuses to run. `/docs` stops at correctness ("edit prose only where a claim changed"), and `/clean` is scoped to comments in code, which Markdown prose doesn't have — so a doc could be perfectly accurate and still cost three times the tokens it needed, with nothing in the suite ever noticing. `/truncate` cuts the packaging — narration and ceremony, justification a reader can't act on, the same mechanism re-explained across Summary/Behavior/Notes, content duplicated from a linked doc (replaced by the link), hedging, redundant examples — and preserves **every claim exactly**. Each doc is evaluated in its own fresh subagent (parallel batches of ~4) starting from a **claim inventory** (commands, flags, defaults, exit codes, paths, env vars, described ordering, guardrails, links); applying re-derives that inventory from the edited doc and requires it to match one for one, because a missing claim is a bug in the edit and not a successful truncation. What it will not touch: ADR reasoning (Context and Consequences are an ADR's payload — a decision without its reasoning can't be revisited), anything non-obvious like a gotcha or external constraint, required template sections, frontmatter `description`, and code blocks/command lines/tables, which are kept verbatim. It never adds, never rewrites for voice, and never fixes a claim it believes is wrong — drift is reported as a `/docs` finding and the words are left alone. A doc losing more than 40% of its body is confirmed first unless `--yes` / `-y`; `--all` / `-A` sweeps the whole bundle (spelled `-A` because `-a` already means the missing-docs pass in `/docs` and woven-in commands in `/task`), `--dry-run` / `-n` plans without writing, `--bundle` / `-b <dir>` picks the bundle, and trailing text scopes the run to a concept, path, or topic, overriding the dirty filter. Like `/docs`, it delegates the worktree, commits, `/clean`, `/pr`, and teardown to `/task`. Ships with `docs/features/truncate.md`, `docs/adrs/0003-dirty-flag-for-doc-density.md`, and README entries.
- **A `dirty: true` frontmatter flag hands changed docs from `/docs` to `/truncate`.** `/docs` now marks every doc it **updates** or **adds** — never one it audited and found fresh — meaning "claims correct, prose not evaluated for density since it changed". It is a work queue, not a defect: `/truncate` selects on it (`okq --bundle docs find --where dirty=true`) and is the only command that clears it. Merging the density rewrite into `/docs` instead was rejected because the two passes have opposite relationships to a claim — the correctness pass changes claims and may make a doc longer, the density pass must preserve them all — so a combined diff makes a genuine correction indistinguishable from a paraphrase. Git recency was rejected as the queue signal because it can't tell a claim edit from a whitespace fix or a link repoint. **okq needs no change**: `find --where <FIELD=VALUE>` (0.5.0) matches arbitrary frontmatter keys, `validate` accepts keys beyond the OKF core, and an unset key matches nothing rather than erroring. Truncating deliberately does **not** bump `updated`/`timestamp` — no claim changed, and those dates feed `/docs`' staleness ranking, so bumping them would push a doc down the audit queue on the strength of a style edit. `/clean` gained the matching boundary (doc prose is out of scope even when the diff touches it; comments inside a doc's fenced code blocks still aren't), `docs/README.md` documents the key as bundle contract, and `docs/specs/adding-a-command.md` extends it to hand-edits — a hand-edited doc that skips the flag silently misses the queue, which is what `--all` / `-A` exists to recover from.

### Fixed

- **Task-style workflows now guard the exact shell failures found in later claude-proxy sessions.** `/task` batches independent reads and probes while reading unchanged targeted regions only once; handles expected nonzero `printenv` / count / search probes locally; quotes program-owned globs for zsh; re-resolves live cwd/worktree context when a previously valid relative path disappears; backgrounds dev servers and watchers with logs and a bounded harness wait; and explicitly forbids the tight `until …; do :; done` loops that produced repeated exit 143 timeouts and one exit 137 kill. `/fb --target` no longer retries a branch already owned by a worktree: it validates the existing owner checkout or stops for another live session. The completion contract now names the proxy's exact `- done: <outcome>` record, reserves completion for an existing PR plus teardown, and leaves `/revive <thread id>` as the recovery path for an interrupted run.
- **`pr` no longer deletes the assets already in a PR description.** Updating a PR replaces its body wholesale, and the replacement is authored from the branch's commits and diff — which know nothing about a screenshot, a screen recording, or a diagram someone pasted into the PR by hand. So every `/pr` re-run silently wiped them, and the loss only showed up when a human went looking for the demo clip. `my-command-tools pr` now reads the current body before editing (`gh pr view --json …,body`) and carries its assets forward: markdown images, `<img>`/`<video>`/`<audio>`/`<picture>` elements, links to GitHub-hosted attachments (`user-attachments/assets/`, `user-images.githubusercontent.com`), and a bare attachment URL, which GitHub embeds on its own. Each is reinserted **verbatim**, so alt text and sizing attributes survive the round trip; anything the rewritten body already references is matched by URL and left where the new body put it, and the rest is appended under an `## Assets` heading that is reused rather than re-added, so repeated updates collect into one section instead of stacking. Nesting resolves outermost-first, so a `<picture>` is kept whole rather than shredded into its `<img>`. Updates report the carry-over count as `assetsPreserved`, and `/pr` Step 3 now tells the agent plainly to write the description from the diff and never drop an asset because it isn't in the bullets. Four toolkit tests lock it in: assets absent from the rewrite are carried over, one already present is not duplicated, a bare attachment URL counts and a second pass does not stack a second heading, and an asset-free description gains nothing.
- **`pr` no longer tries to remove a worktree it doesn't own.** `/task` Step 3 dispatches `/clean` + `/pr` into a fresh subagent, and `/pr` Step 4 then attempted teardown from inside a workspace the parent session created — so every shipped run ended on `This session is not the owner of the worktree at … — it either entered a pre-existing worktree via EnterWorktree({path}) or resumed into a checkout whose liveness lock another running Claude Code session still holds`. The old fallback made it worse by reaching for `git worktree remove`, which git also refuses while the owner's lock is live. Teardown is now ownership-scoped: `/pr` removes the worktree only when its own session created it, skips it outright when dispatched as a subagent, and on an unexpected refusal steps out with `action: "keep"`, tries `my-command-tools worktree end`, and leaves the path in place — reporting it — rather than forcing past a live lock.
- **The commands that set up a worktree and delegate now tear their own down.** They previously leaned on `/pr` doing it, which would have stranded a workspace now that `/pr` declines: `/fb --target` (same-repo and cross-repo), `/review` (default mode, clean PR or not), `/task-bootstrap`, and `/revive` each finish with `ExitWorktree` (`action: "keep"` — the only action allowed for a worktree entered via `EnterWorktree({path})`) followed by `my-command-tools worktree end --branch <branch>`, which re-verifies the branch reached origin before removing.
- **`pr` says explicitly that a draft stays a draft.** The `pr` verb already only ever moved a PR *toward* draft, but nothing said so to the agent driving it; Step 3 now forbids `gh pr ready` and "helpfully" marking a finished-looking draft ready — only `/god` promotes a draft, right before merging. Two toolkit tests lock the behavior in: an update to an existing draft never calls `pr ready`, and `--draft` on a non-draft PR still converts it.
- **Toolkit tests no longer hang on commit signing.** The throwaway repos inherited the developer's global `commit.gpgsign`, so an agent- or hardware-backed key turned `git commit` into a prompt that never comes — the suite blocked, then failed with `1Password: agent returned an error`. Each test repo now disables `commit.gpgsign`/`tag.gpgsign` locally.

## 2026-07-26

### Changed

- **Evidence-derived workflow guardrails** — exploratory shell probes now run independently and tolerate expected read-only misses without hiding corrective failures; files are read immediately before editing and again after possible external changes; Read pagination uses numeric offsets and limits; and cross-repo `/task`, `/god`, and `/fb` runs avoid `EnterWorktree` in favor of helper-managed absolute-path worktrees.
- **Four evidence-derived rules across the command suite**, each traced to claude-proxy's suggestions over 114 recorded sessions rather than to taste. **Discovery discipline** (`/task` Step 2, `/review` Step 3, `/revive`'s notes): independent reads and greps go out in one turn instead of one per turn — 100 serial runs covering 655 read/grep calls were runs of four or more with no decision between them, which makes them independent by construction — and a file already read this session is already in context, so it gets re-read only after it changed, with a targeted `offset`/`limit` rather than whole (47 files were read three or more times in a single session, 285 reads in total). **No sleeping to wait** (`/task` notes, `/god` Step 5, `/pr` Step 3): a foreground `sleep` is blocked by the harness and so is `sleep N && <check>`, so waiting is `gh pr checks --watch` or the `Monitor` tool with an until-loop — the recorded runs show three blocked `sleep` polls and one that burned a full three-minute timeout to exit 143. **Approval-needing commands stand alone** (`/god` Step 4, `/merge-deps` preconditions, `/sync` Step 2): `git fetch`, `git config` and friends get their own Bash call, because folding one into an `&&` chain escalates approval to the entire compound command and costs a turn plus a retry. **Quote glob-bearing arguments** (`/revive` Step 1, `/docs` notes): the shell is zsh, which aborts the whole eval on an unquoted glob that matches nothing — `--include='*.tsx'`, `'docs/adrs/*'` — so the argument the invoked program was meant to expand never reaches it.
- **Every pipeline now ends with a text-only outcome turn.** A transcript records a `done:` node only for an assistant turn that has text and no tool calls; a run whose final act is a tool call is recorded as a `decision` instead, so it reads as unfinished even when the work landed — 351 of 457 recorded tasks carry no outcome line. That also actively misleads `/revive`, which treats a missing `done:` as its interruption signal and would re-pick-up finished work. The terminal step of all fifteen commands now states that the report is its own turn, delivered after the last tool call and never alongside one.

### Added

- **`improve` command** — turn claude-proxy's session suggestions into an implemented change, so the advice about how this agent works stops being something a human reads and starts being something that ships. claude-proxy scores every ten recorded sessions for ways to reach the same outcome in fewer steps — independent reads issued one at a time, an error rediscovered session after session, a guardrail refusing a call the agent had already decided to make, a file read three times in one run — and `/improve` reads those findings, keeps only the ones still **pending**, composes them into criteria, and hands them to `/task` in one fresh subagent. `--range` / `-r` picks the buckets (one `9`, a list `2,3,9`, a span `2-9`, or a mix `2-4,9`; every bucket by default), `--dry-run` / `-n` reports the pending set and the criteria without running anything, and `--here` / `-h`, `--base <branch>`, `--draft` / `-d`, `--add` / `-a` pass straight through to `/task` rather than being reinterpreted here. The claude-proxy dependency follows `/revive`'s pattern exactly: **`CLAUDE_PROXY_STORE`** is read from the environment and its parent/grandparent give the log directory and the checkout — an unset variable is a stop with an explanation, never a filesystem search or a hardcoded fallback. Suggestions are read via `LOG_DIR=… pnpm --filter server suggestions list -s pending -d --json`, which reads the log directory directly and so needs **no running proxy server**. The loop closes at the end: only the criteria the subagent reports as *implemented* are marked `done` with the PR as the note (`suggestions mark -r <bucket> -i <ids> -s done -n <url>`), so a dropped or deferred suggestion stays `pending` and returns on the next run instead of being quietly lost — and a later `/improve` over the same range never re-proposes what already shipped. Grouping happens before dispatch (the same rule tripping in several buckets is one improvement with more evidence, not several), the command creates no worktree and makes no edits of its own, and it never pads the run with improvements the suggestions don't support — every change traces back to a finding with its own evidence and source sessions. Ships with `docs/features/improve.md` and README entries.

### Fixed

- **The installed toolkit is now actually callable, so commands stop silently falling back to hand-rolled git.** Every install placed the shim at `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/my-command/bin/my-command-tools` and stopped there — nothing ever put that directory on `PATH`. But a command spells the call as a bare `my-command-tools` and declares it as `allowed-tools: Bash(my-command-tools:*)`, so on a fresh device the CLI was installed and invisible at the same time: `/task`, `/god`, `/pr`, `/mc`, `/review`, `/revive`, `/merge-deps`, `/changelog`, and `/sync` found no such command, read that as "the toolkit isn't installed", and fell back to plain `git`/`gh` — losing the default-branch guard, the whole-tree-staging refusal, the unpushed-work check on `worktree end`, and the draft-only PR rule while still looking like a working run. `installToolkit()` now calls a new `linkOnPath()`, and `scripts/install-personal.sh` does the same in shell: the shim is linked into the first of `~/.local/bin`, `~/bin` **already on the user's PATH**, pointing at the fixed shim path rather than one install's payload so the link survives a later install replacing the toolkit underneath it. No shell profile is ever edited — linking into a directory the user already has on PATH takes effect in the next shell with nothing to undo, where rewriting dotfiles guesses at the shell and leaves a mess behind; when neither candidate is on PATH the installer prints the `ln -s` and `export PATH=…` lines and says plainly that commands can't reach the CLI yet. Re-running is idempotent (an existing symlink is repointed, a real file under that name is left alone as something else's), and the absolute-path workaround is explicitly *not* the fix: it doesn't match `Bash(my-command-tools:*)`, trading a missing command for a permission prompt on every call. `doctor` gained an **`onPath`** block — whether a bare call resolves, whether it resolves to *this* install's shim, and the exact `ln -s` when it doesn't — which is what makes the state visible instead of silent, and finally delivers the "what's on PATH" its own docs already advertised. `check-commands.sh` gained the matching invariant (dropping `linkOnPath()` reinstates the silent fallback), plus a `paths.test.mjs` suite covering PATH splitting, trailing-slash normalization, and the two shadowing cases a naive lookup gets wrong: a present-but-non-executable file, and a directory that merely shares the name.

## 2026-07-25

### Added

- **Command toolkit** — a zero-dependency Node CLI (`my-command-tools`) that owns the deterministic half of a workflow run, so commands stop re-deriving the same git state with a slightly different volley of one-off shell calls each time. Six verbs, each returning **JSON on stdout**: `state` (branch, base, commits, tracked vs untracked changes, and a single `hasWork` boolean that settles `/task`'s no-change gate), `verify` (discovers the repo's package manager by lockfile, runs its gates fastest-failing first, and returns *no* log for a pass and a bounded tail for a failure — no more hand-rolled `2>&1 | tail -12`, and no re-running a whole build because the window was guessed too small), `commit`, `pr`, `worktree begin|end|list`, and `doctor`. The guards are the point: `commit` refuses the default branch and refuses `.`/`-A`-style whole-tree staging so carryover files from a dirty checkout stay put, `worktree end` refuses to remove a worktree whose HEAD isn't on origin without `--force`, and `pr` only ever moves a PR *toward* draft rather than silently flipping an existing draft to ready. Judgment stays with the agent — there is deliberately no comment-scoping verb, because `/clean` runs entirely as an agent pass: deciding a comment is worth cutting depends on the surrounding code, and handing the agent a pre-filtered list of comment lines would narrow its view exactly where the wider context is what the call rests on.
- **Device-wide toolkit install.** Commands must reach the tooling however MyCommand was installed, so the toolkit resolves through three roots in order: `$MY_COMMAND_TOOLKIT` (explicit override), `$CLAUDE_PLUGIN_ROOT/src/toolkit` (set by Claude Code for plugin commands), then `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/my-command/toolkit` (what the npx wizard writes). `installToolkit()` runs in **both** wizard modes — plugin and personal — copying `src/toolkit/` to the device root, placing an executable shim at `<root>/bin/my-command-tools`, and stamping a `VERSION`; `scripts/install-personal.sh` symlinks the checkout instead, so a dev clone tracks `git pull`. The toolkit ships as **raw `.mjs` under `src/`**, never build output: a plugin install is a git clone with no build step and `dist/` is gitignored, so anything requiring compilation would simply not exist in plugin mode. Type safety survives that via a separate `tsconfig.toolkit.json` running `allowJs` + `checkJs` + `noEmit` (`pnpm run check:toolkit`), and a `node --test` suite exercises the verbs against throwaway git repos — where it caught a live bug: trimming git's two-column `--porcelain` output shifted every parsed path by two characters, so status is now read raw. Ships with `docs/specs/command-toolkit.md`.

### Changed

- **The workflow commands now call the toolkit instead of hand-rolling their git plumbing.** Shipping the CLI was only half the job — the commands still opened with their own volley of one-off shell calls, so the guards the toolkit exists to enforce were sitting unused. Rewritten across the suite: `/task` sets up its workspace with `worktree begin --bootstrap` (which fetches first, so a stale `origin/main` can no longer silently plant work on old code) and reads the bootstrap result off the same JSON instead of hunting for `scripts/bootstrap-worktree.sh` itself, runs `verify` for its gates, `commit`s an explicit path list per logical commit, and settles its no-change gate on `state`'s single `hasWork` boolean rather than reading `git log` and `git status --porcelain` separately. `/pr` collapses push + detect + create-or-edit into one `pr` call, and picks up `--retitle` so an existing PR's title is no longer edited on a judgment call. `/god`, `/mc`, and `/merge-deps` take their preconditions from `state` and `doctor`; `/mc` and `/merge-deps` sanity-check with `verify`; `/merge-deps` manages its throwaway worktrees with `worktree begin`/`end`. `/changelog` and `/revive` derive what changed from `state`. `/sync` finishes with `doctor`, since a sync that refreshed the Markdown but left the toolkit stale is only half applied. `/clean`, `/docs`, and `/trim` are unchanged — `/clean` stays a pure agent pass that derives its own scope (see above), `/docs` delegates all git work to `/task` and its remaining `git log` calls are history queries no verb covers, and `/trim` never touches git at all.
- **`worktree begin` gained `--existing`, for checking out a branch instead of creating one.** Four commands apply work *onto* a branch that already has commits — `/fb --target`, `/review`, `/revive`'s workspace recovery, and `/merge-deps`' verification worktree — and the verb could only create branches, which would have silently abandoned that work. `--existing` checks the branch out at its own tip (creating a local tracking branch from `origin/<branch>` when only the remote has it), and the two directions are now guarded against being confused: an existing branch without `--existing` is refused with a message naming the flag, a `--existing` branch that exists nowhere is refused rather than quietly created, and `--base` alongside `--existing` is a usage error since a branch that already exists already has a base.
- **`check-commands.sh` and PR CI now cover the toolkit.** The invariant script gained a fourth section — entrypoint and shim present, shim still executable (a lost mode bit fails only at call time), every `verbs/*.mjs` registered in `cli.mjs` (an unregistered verb is dead code the CLI can never reach), and the wizard still calling `installToolkit()` (dropping it from either mode would ship commands whose tooling isn't there). A new `toolkit` CI job runs `check:toolkit` and `pnpm test`, since the main `typecheck` never sees the shipped `.mjs`.
- **`review --here` / `review -h` now performs the independent review in the current agent.** Here mode assumes it is already running inside the fresh review agent, so it creates no worktree and spawns no nested reviewer; the default and `--target` flows still use a fresh worktree and fresh agent. The inline review follows the same diff, verification, convention, output, and `/fb` application contract as the default flow.

## 2026-07-24

### Added

- **`god` command** — carry a plain-language task all the way to **merged into `main`**, with no human in the loop. `/god <criteria>` is `/task` plus the last mile: it forwards `--here` / `-h`, `--base <branch>`, and `--add` / `-a` untouched and lets `/task` own the branch, implementation, verification, `/clean`, `/pr`, and teardown, appending its own `--add review …` entry so the review lands **inside** `/task`'s existing `/clean` + `/pr` subagent — after `/pr`, before teardown, where that subagent is already on the PR's branch with the PR pushed, so `/review --here` is correct and its `/fb` chain updates the same PR instead of nesting a worktree. Both review outcomes resolve in that subagent (findings → it runs the `/fb` line itself; a clean sign-off → it returns without one), so nothing comes back as pending work. The merge stage then re-resolves the PR from `gh` and refuses any PR whose head isn't this run's branch, detects conflicts **locally** with `git merge-tree --write-tree` rather than trusting GitHub's lazy `mergeable` field and delegates them to `/mc -t <branch>`, watches CI with `gh pr checks --watch --fail-fast`, spends up to `--fix <n>` rounds (default 1) of `/fb -t <branch>` against the failing job's log when it goes red, merges with `gh pr merge --delete-branch` (falling back to `--auto` on pending checks, looping back to the conflict stage once if `main` moved), and finally fast-forward pulls `main` in the **main checkout** — recorded up front, since `/task` tears its worktree down before this stage. `--squash` (default) / `--merge` / `--rebase` pick the method, `--auto` skips the CI wait and queues auto-merge, `--no-review` drops the woven-in review, and `--draft` / `-d` is rejected because a draft can't merge. Four situations stop the run instead of being driven through — an unresolvable `/mc` conflict, CI still red after the repair budget, a diverged local `main`, and a PR that isn't this run's — and it never merges with `--admin`, never force-pushes, and never pushes to `main` directly. Ships with `docs/features/god.md` and README entries.
- **`revive` command** — resume a session that stopped mid-flight (cleared, compacted away, killed, or abandoned) and left its work half-applied on a branch. `/revive <session-id>` resolves the id against **claude-proxy's transcript store by default** — `$CLAUDE_PROXY_STORE/<threadId>.md`, where the thread id is `sha256(sessionId + "\n" + first-user-text).slice(0, 16)` — searching the live store and then globbing the relocated days under `$CLAUDE_PROXY_ARCHIVE`; a 36-char UUID or `--source cli` reads the Claude Code JSONL instead, and `--source <path>` reads a file directly. It walks between the two stores through the transcript's `- session: <uuid>` header, and knows one session id can own several thread ids because each subagent gets its own conversation root. The transcript is treated as a **lossy digest**: read for the ask, the (often nested) slash-command workflow that was running, the human's already-settled mid-run decisions, the `- ✗` errors, and the point where it stops — the transcript simply *ending* being the interruption signal. Workspace recovery reads `cwd`/`gitBranch` from the CLI transcript and resumes that directory in place, or recreates a worktree checking out the **existing** branch, never a fresh branch off `main`. Then `git status`/`diff`/`log` plus the repo's own gate scripts establish what actually landed, and only the remainder is worked — each claim re-verified against source, since the digest's reasoning lines are truncated summaries. The run finishes on the *original* workflow's terms (for anything wrapped in `/task`: commit, `/clean`, `/pr`, teardown) without nesting a new `/task`. `--dry-run` / `-n` reports where it stopped and what remains, changing nothing. Ships with `docs/features/revive.md` and README entries.
- **`docs` command** — reconcile a repo's [okq](https://github.com/mikevalstar/okq) doc bundle with the code it describes, covering all three directions docs rot: **stale** (a doc that no longer matches the code), **missing** (a feature with no doc), and **obsolete** (a doc for something that was removed). It discovers the bundle, reads the bundle's *own* contract first (frontmatter keys, generated `index.md`s, folder templates, the 1:1 unit it documents, any docs gate script) and lets those rules win, then reconciles concepts against documentable units into CHECK / MISSING / OBSOLETE before editing anything. The staleness pass audits docs **one at a time** in fresh subagents, using git recency only to rank suspicion and claim-level comparison (flags, defaults, paths, exit codes, behavior — `old → current`) as the real verdict; drift found in one doc is re-checked across its `neighbors`/`backlinks`. Code that looks like the regression is flagged for the user rather than blessed by rewriting the doc, a wrong ADR is superseded rather than edited, a rename is repointed rather than deleted, and every deletion is confirmed with evidence and made with `git rm`. Pass flags `--refresh` / `-r`, `--add` / `-a`, `--prune` / `-p` combine (all three by default); `--dry-run` / `-n` plans without writing, `--bundle` / `-b <dir>` picks the bundle, `--yes` / `-y` skips confirmations, and trailing text scopes the run to a concept, path, or topic. Ships with `docs/features/docs.md` and README entries.

### Changed

- **`revive` now reads the claude-proxy store location from the environment instead of hardcoded paths.** Step 1 named one device's checkout (`~/Documents/ghub/personal/claude-proxy/logs/sessions/`) and one archive root (`~/Documents/logs/claude/<date>/`), so the default `--source proxy` path only resolved on a machine where claude-proxy happened to live there. The store is now **`$CLAUDE_PROXY_STORE`** — the directory holding `<id>.md` transcripts, read from the environment, never guessed and never derived from a repo checkout — with an optional **`$CLAUDE_PROXY_ARCHIVE`** searched recursively for relocated days (unset means the archive is skipped and the command says so). When `CLAUDE_PROXY_STORE` is unset or its path is missing, `/revive` **fails fast**: it reports the missing variable, shows the `export` to add, and offers `--source cli` / `--source <path>` rather than searching for the store or silently falling back. The cross-walk grep and the retention note follow the variables, and the two references to claude-proxy's own source files (`proxy/session.mjs`, `packages/core/src/sessions.ts`) are gone — the thread-id derivation and transcript shape are stated directly. Feature doc gained an **Environment** section; README gained the `export` snippet.
- **`task` now skips `/clean` and `/pr` when a run produced no changes.** Step 3 dispatched both subagents unconditionally, so criteria that turned out to be already satisfied ("do X if it isn't already the case") still burned two subagents and ended with `/pr` pushing a branch and opening a PR with an empty diff. Step 3 now opens with a gate: check this run's commits (`<base>..HEAD`, where the base is `origin/<default>`, `--base <branch>`, or the pre-run commit under `--here`) and `git status --porcelain`, discounting pre-existing untracked files carried over from the original workspace. When both are empty it skips straight to teardown and reports what it checked and that no PR was opened; under `--here` it leaves any pre-run unpushed commits alone rather than shipping them as this run's work. Step 2 gained the matching instruction not to manufacture edits when inspection shows the criteria already hold.
- **`task` now states outright that step 3's teardown removes the worktree even when the PR is a draft.** `--draft` / `-d` was documented only as a flag passed through to `/pr`, which left room to read a draft PR as unfinished work worth keeping a local worktree for. The teardown step and the flag description now say the opposite explicitly: `--draft` controls the PR's review state on GitHub, not the local workspace, and a draft's commits are on origin just the same — `--here` is the only thing that skips teardown.
- **`task` now expects `ExitWorktree`'s commit guard at teardown and calls the form that satisfies it.** On the shipped path the branch always carries commits, so `ExitWorktree` with `action: "remove"` alone refuses — `Worktree has N commits on <branch>. Removing will discard this work permanently.` — and asks for a second invocation with `discard_changes: true`, making a failed tool call part of every successful run. Step 3's teardown now says to confirm `git rev-parse HEAD` matches `git rev-parse origin/<branch>` once `/pr` has pushed and then pass `action: "remove"` **and** `discard_changes: true` on the first attempt, since with every commit on origin the "discard" drops only the local worktree. HEAD ahead of origin means push before tearing down rather than discarding, and the no-change path still uses plain `action: "remove"` because it has no commits to guard.
- **`docs` now runs inside a `/task` workflow and takes workspace flags.** Previously it edited docs in the current checkout and left committing to whatever invoked it, so a direct `/docs` run ended with uncommitted edits and no PR. A new Step 0 resolves *where* the work happens and hands the passes to `/task` as plain-language criteria, so `/task` owns worktree setup, commits, `/clean`, `/pr`, and teardown — exactly how `/fb` wraps `/task`, but defaulting the other way: `/docs` with no flags gets a fresh worktree off the latest `main` on a `docs/<summary>` branch, matching `/task`'s own default. `--here` / `-h` reconciles on the current branch and `--base <branch>` branches off something other than `main`, both passed straight through. `--dry-run` / `-n` short-circuits the handoff entirely — it stays in the current checkout and creates no worktree, commit, or PR. The command still creates no worktree itself (that would nest one inside another), and the pass flags stay local: `-a` is the missing-docs pass here but registers commands in `/task`, so they are never forwarded as flags.
